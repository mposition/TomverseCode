# 제품 전략: GitHub Copilot 대비 포지셔닝

status: accepted (2026-07-25) — 단, 2절의 **가설 게이트**를 통과하는 것을 전제로 함
관련: [multi-engine-routing.md](./multi-engine-routing.md), [state-machine-and-protocol.md](./state-machine-and-protocol.md), [ui-wireframes.md](./ui-wireframes.md)

## 1. 전략의 핵심 명제

> 기능 개수로 Copilot을 이길 수 없다. **"Copilot보다 결과를 더 신뢰할 수 있다"를 측정 가능하게 증명**하는 것이 유일한 승산이다.

이 명제에 동의한다. 기능 폭에서는 GitHub의 리소스를 이길 수 없고, 애초에 그 싸움을 하면 우리의 유일한 구조적 우위(모든 것이 로컬 오케스트레이터를 통과하므로 무엇이 어디로 갔고 무엇이 검증됐는지 정확히 안다)를 활용하지 못한다.

**전략의 4개 기둥:**
1. 투명한 공급자 간 교차 검증 (모델 간 불일치를 숨기지 않고 보여준다)
2. 결정론적 테스트 판정 (LLM이 아니라 테스트가 최종 판정자)
3. Candidate Arena (여러 구현을 실제로 실행시켜 경쟁)
4. 실제 성공률 기반 라우팅 (범용 벤치마크가 아닌 이 저장소의 실측)

## 2. 가설 게이트 — 이 전략 전체의 전제

**P1·P2 전체가 "교차 검증이 실제로 가치 있다"는 미검증 가설 위에 서 있다.**

우리 Phase 0 스파이크의 실측 결과를 잊으면 안 된다:

| | 통과율 | 총비용 | 총지연 |
|---|---|---|---|
| 교차검증 (OpenAI 초안 + Claude 검수) | 100% (5/5) | $0.0324 | 24.7s |
| 단일 모델 (Claude 단독) | 100% (5/5) | $0.0198 | 14.5s |

쉬운 태스크에서 교차검증은 **정확도 이득 0%에 비용 1.63배·지연 1.70배**였다. 우리는 이것이 "픽스처가 너무 쉬웠기 때문"이라고 해석했지만, **아직 어려운 태스크로 재검증하지 않았다.**

```
게이트: multi-engine-routing.md 9절 2단계
       "어려운 픽스처 세트로 스파이크 재실행"

  통과 → P1(투명한 교차 검증) 및 P2(Candidate Arena)로 진행
  실패 → 이 전략 문서의 기둥 1·3이 무너짐. 제품 포지셔닝을 재수립해야 함
         (남는 것: 기둥 2 결정론적 판정 + Windows 특화 + 전송 투명성)
```

**이 게이트를 통과하기 전에 P1/P2에 큰 투자를 하지 않는다.** 이건 비관이 아니라, 우리가 이미 한 번 실측으로 배운 것을 두 번 무시하지 않겠다는 뜻이다. 게이트가 실패해도 제품이 죽는 건 아니다 — 결정론적 검증, Windows 특화, 데이터 전송 투명성은 교차검증과 무관하게 유효하다.

## 3. 우리가 이미 갖고 있는 것

전략 문서가 요구하는 것 중 상당 부분이 이미 설계·구현되어 있다. 새로 만들 것과 이미 있는 것을 구분해야 낭비가 없다.

| 전략 문서 요구 | 현재 상태 |
|---|---|
| §4 테스트가 최종 판정 | **설계 완료** — 최초 아키텍처 원칙부터 `VERIFYING`이 tier와 무관하게 항상 실행 |
| §5 위험도 기반 적응형 검증 | **구현 완료(2단계)** — `TRIAGE` + `complexityTier`, `packages/sidecar/src/triage.ts`. 4단계로 확장 필요(5절) |
| §6 실제 성과 학습 라우터 | **설계 완료** — multi-engine-routing.md 8절이 동일 결론에 독립적으로 도달(부트스트랩 순환 포함) |
| §7 검수 독립성 | **부분** — 공급자 독립성은 불변식으로 강제(multi-engine 5절). **narrative 독립성은 없음 → 4절에서 추가** |
| §9 데이터 전송 투명성 | **부분** — context-engine.md 7절에 secret/바이너리/대용량 하드 제외. 감사·표시 UI 없음 |
| §10 재현 가능한 Agent Trace | **약 80% 완료** — `task_events` append-only, `tool_requests`/`tool_results`/`file_mutations`/`verification_reports`/`snapshots(git_head)`. workspace hash·모델 버전·export/replay만 추가하면 됨(6절) |
| §2 모델 불일치 화면 | **미착수** — ui-wireframes.md에 검증 결과 패널은 있으나 불일치 표는 없음 |
| §3 Candidate Arena | **미착수** — worktree 격리 자체가 없음 |

**놓치기 쉬운 사실: Agent Trace는 거의 다 됐다.** 전략 문서는 이걸 P2로 뒀지만, 우리에겐 append-only 이벤트 로그가 이미 진실의 원천이므로 남은 건 작은 델타다. Copilot이 이걸 사후 추가하려면 아키텍처를 고쳐야 하지만 우리는 이미 그렇게 설계돼 있다 — 저비용 고가치 항목이므로 우선순위를 올린다.

## 4. 채택: Blind Review — 그리고 현재 코드의 실제 결함

전략 문서에서 **가장 가치 있는 단일 제안**이다. 그리고 이건 개선 제안이 아니라 **현재 코드의 버그 지적**이다.

multi-engine-routing.md 5절에서 우리는 "검수자는 실행자와 다른 공급자여야 한다"를 불변식으로 만들었다. 하지만 그건 *공급자* 독립성일 뿐이고, **서사(narrative) 독립성은 전혀 보장하지 않는다.**

현재 스파이크 코드(`spike/src/providers/anthropic.ts`)의 검수 프롬프트는 초안 작성자의 자기 설명을 그대로 전달한다:

```
## Draft author's interpretation
{draft.interpretation}

## Draft author's proposed file
```

검수 모델은 "이 코드가 요구사항을 만족하는가"를 판단하기 전에 **초안 작성자가 무엇을 의도했다고 주장하는지를 먼저 읽는다.** 이건 교과서적인 anchoring이고, 교차 검증의 가치를 구조적으로 깎아먹는다. 다른 공급자를 쓰는 비용은 다 내면서 독립성은 일부만 얻고 있는 셈이다.

**채택할 두 가지 검수 모드:**

```typescript
type ReviewMode = "informed" | "blind";

// blind: 검수 모델에게 제공하는 것
//   - 원래 사용자 요구사항
//   - 변경된 코드 (diff)
//   - 관련 저장소 컨텍스트
//   - 테스트 결과
// blind: 숨기는 것
//   - 실행 모델의 이름·공급자
//   - 실행 모델의 interpretation / rationale / 자기평가
```

- `complexityTier`가 `verified` 이상이면 **blind가 기본값.**
- `informed`는 FIX_LOOP 재시도처럼 "직전 시도가 왜 실패했는지"의 맥락이 실제로 필요한 경우에만.
- 두 모드로 같은 태스크를 돌려 판정이 갈리는 빈도는 그 자체로 anchoring의 크기를 측정하는 지표가 된다(14절).

**구현 비용은 프롬프트 빌더 분기 하나이고, 얻는 것은 핵심 차별화의 신뢰성이다.** 우선순위를 P1 최상단에 둔다.

## 5. 채택: `complexityTier` 2단계 → 4단계 확장

현재 `simple | standard`를 전략 문서의 4단계로 확장한다. 사용자에게 노출되는 품질 정책 이름과 내부 tier를 일치시킨다.

```typescript
type ComplexityTier = "fast" | "balanced" | "verified" | "critical";
```

| tier | 실행 방식 | 예시 |
|---|---|---|
| `fast` | 단일 저비용 모델, 검수 없음 | 설명, 주석, 이름 변경 |
| `balanced` | 실행 모델 + 조건부 검수 | 단일 파일 버그, 작은 기능 |
| `verified` | 실행 + **다른 공급자** 독립 검수(blind 기본) | 다중 파일 리팩터링 |
| `critical` | 복수 구현 경쟁(Arena) + 검수 + 보안 검사 + 사용자 승인 | 인증·결제·마이그레이션 |

- 기존 `simple` → `fast`/`balanced`, `standard` → `verified`로 매핑. `critical`은 Arena(P2)가 준비될 때까지 `verified`와 동일하게 동작하되 승인 요구만 강화.
- **사용자가 태스크별로 tier를 올릴 수 있어야 한다**(내리는 것도). 라우터의 자동 분류는 기본값 제안이지 강제가 아니다.
- TRIAGE 판정 신호에 전략 문서 §5의 항목을 추가: 인증·결제·암호화 코드 경로 여부, DB migration 여부, public API 변경 여부. 단 **임계값 튜닝은 여전히 미해결**(어려운 픽스처 세트 필요).
- 워크스페이스 정책의 `forceComplexityTier`는 하한선으로 동작(예: 결제 저장소는 최소 `verified`).

## 6. 채택: Agent Trace 완성 (기존 자산의 작은 델타)

3절에서 봤듯 이미 대부분 있다. 추가할 것:

| 항목 | 상태 |
|---|---|
| workspace hash (태스크 시작 시점 전체 상태 지문) | 추가 필요 — `snapshots`에 `git_head`는 있으나 uncommitted 상태 미반영 |
| 모델 정확한 버전 문자열 | 추가 필요 — `DraftProposal.model`은 있으나 API가 반환한 실제 버전 미기록 |
| export / replay | 추가 필요 |
| 나머지 (tool call, patch, 승인·거부, 테스트, 검수, 비용·토큰, 최종 커밋) | **이미 스키마에 존재** |

**replay의 의미를 정확히 정의해야 한다.** LLM은 결정론적이지 않으므로 "같은 입력으로 다시 돌리면 같은 결과"는 보장할 수 없다. 우리가 보장할 수 있는 것은:
- **재현(reproduce)**: 기록된 patch·명령을 그대로 재적용해 최종 상태를 정확히 복원 — 결정론적, 보장 가능
- **재실행(re-run)**: 같은 프롬프트로 모델을 다시 호출 — 비결정론적, 비교 분석용

이 둘을 UI와 문서에서 섞어 쓰면 안 된다. 기업 감사에 필요한 건 전자다.

## 7. 채택: 데이터 전송 투명성 — 구조적으로 우리에게 저렴하다

전략 문서 §9는 기업 확보의 핵심인데, **우리 아키텍처에서는 이게 거의 공짜다.** Context Engine이 어떤 파일을 패키징했는지 정확히 알고(context-engine.md 4절 `relevantFiles[].reason`), 모든 공급자 호출이 Node sidecar 한 곳을 통과하며, 모든 것이 이벤트 로그에 남는다.

Copilot이 이 기능을 사후 추가하려면 컨텍스트 수집 경로 전체를 계측해야 하지만, 우리는 이미 그 경로가 단일하고 명시적이다. **적은 구현 비용으로 큰 차별화가 나오는 항목이므로 P1에 둔다.**

구현: 태스크별로 `(공급자, 파일 목록, 토큰 수, 마스킹된 secret 수)`를 집계해 UI에 표시. `.env`·인증서 등은 이미 인덱스 진입 자체가 차단돼 있으므로(context-engine.md 7절) "Local only"로 표시만 하면 된다.

## 8. 조정: §1 "동등 기능 기본선" 표를 그대로 받으면 안 된다

전략 문서는 30여 개 기능을 "시장 진입을 위한 기본선"으로 나열하는데, **이는 문서 자신의 명제와 충돌한다.** "기능을 더 많이 넣기보다 신뢰성을 증명하라"고 해놓고 Copilot의 기능 목록을 진입 요건으로 제시하면, 결국 차별화에 도달하기 전에 1년을 패리티 구축에 쓰게 된다. 그건 GitHub의 리소스와 정면으로 싸우는 것이다.

**기준을 바꾼다: "Copilot이 가진 것"이 아니라 "우리 차별화가 요구하는 것".**

| 전략 문서의 기본선 항목 | 우리 판단 |
|---|---|
| 파일 읽기·수정·patch·터미널·테스트 | **필수** — 변경을 만들고 검증하려면 반드시 필요 |
| 테스트·빌드 실행 및 결과 파싱 | **필수** — 이게 판정자 본체다 |
| diff 미리보기·승인·되돌리기·체크포인트 | **필수** — 신뢰의 전제 |
| 멀티프로바이더 + BYOK | **필수** — 공급자 독립성이 차별화의 정의 |
| 저장소 인덱싱·토큰 사용량 | **필수** — 전송 투명성의 전제 |
| Git worktree | **P2에서 필수** (Arena가 요구), P1엔 불필요 |
| Windows 특화 | **필수** — 우리의 유일한 플랫폼 |
| Plan 모드 | **필수** — 검증 전 계획 제시가 투명성의 일부 |
| Autopilot 모드 | **후순위** — 검증 투명성에 기여하지 않음. 오히려 "사용자가 판정을 본다"는 컨셉과 긴장 관계 |
| MCP·Skills·Hooks·커스텀 에이전트 | **후순위** — 확장 표면이지 차별화 아님 |
| 병렬 서브에이전트(Fleet) | **Arena가 요구하는 만큼만** — 문서 스스로 "병렬 실행 자체는 차별점 아님"이라고 인정 |
| 클라우드 실행 | **범위 밖** — 로컬 우선 원칙과 정면 충돌 |
| PR 연동 | **후순위** — 있으면 좋음 |
| 인라인 자동완성 | **범위 밖** — 문서도 동의 |

이 재분류의 요점: **좁고 깊은 제품을 먼저 출시한다.** 검증 투명성 하나를 Copilot보다 확실히 잘하는 제품이, 모든 걸 어중간하게 하는 제품보다 낫다.

## 9. 위험: Candidate Arena의 순환 의존 (문서가 다루지 않은 최대 리스크)

Arena는 "여러 구현을 **동일한 acceptance test**로 판정"한다. 그런데 §4는 그 테스트를 "사용자 요청으로부터 acceptance criteria 추출"로 만들라고 한다. 즉:

```
LLM이 쓴 테스트가  →  LLM이 쓴 코드를 판정한다
```

**테스트 생성기가 요구사항을 잘못 이해하면, Arena는 "틀린 테스트를 가장 잘 만족하는 구현"을 자신 있게 선택한다.** 그리고 그 결과에 "Tomverse Verified" 배지가 붙는다. 이건 검증 없는 것보다 나쁘다 — 틀린 확신을 주기 때문이다.

"결정론적 판정자"는 테스트가 주어졌을 때만 결정론적이고, **테스트 자체는 결정론적 산출물이 아니다.** 문서는 이 구분을 하지 않는다.

**완화책 (Arena 설계 시 필수):**
1. **기존 저장소 테스트를 1차 판정자로 우선한다.** 생성된 테스트는 보조. 기존 테스트가 없는 저장소에서는 Arena의 신뢰도를 낮춰 표시한다.
2. **생성된 acceptance criteria는 실행 전에 사용자 승인을 받는다.** Arena는 이미 고위험 태스크(`critical`)에만 적용되므로 사용자가 개입해 있는 상태다 — 승인 한 단계 추가가 부담이 아니다.
3. **생성된 테스트를 독립적인 리뷰 대상으로 취급한다** — 코드 검수와 별개로 "이 테스트가 요구사항을 맞게 표현했는가"를 검수한다.
4. **"테스트 생성기가 틀렸던 비율"을 별도 지표로 측정한다**(14절). 이 값이 높으면 Arena 자체의 근거가 무너진다.
5. 기존 테스트를 **깨뜨리지 않았는가**(회귀)는 생성된 테스트와 무관하게 항상 유효한 판정이므로, Arena 점수에서 가중치를 높게 둔다.

## 10. 위험: 경쟁사 기능 주장은 검증 후 반영

전략 문서는 Copilot의 구체적 기능(Fleet 모드, Rubber Duck 비평 에이전트, 커스텀 에이전트 자동 위임 등)을 사실로 전제하고 "그러므로 우리도 X가 필요하다"고 전개한다.

**우리는 이 주장들을 독립적으로 검증하지 않았고, 이 문서를 작성한 시점의 지식에도 한계가 있다.** "경쟁사가 X를 가졌으니 우리도"라는 형태의 로드맵 항목은 X가 부정확하면 통째로 잘못된 투자가 된다.

다만 **방향성 결론(기능 개수가 아니라 검증 신뢰성으로 차별화)은 경쟁사 세부 기능의 정확성과 무관하게 타당하다.** 따라서:
- 방향성은 지금 채택한다.
- "Copilot이 이미 X를 한다"에 근거한 개별 기능 항목은 **실제 제품을 확인한 뒤** 로드맵에 넣는다.
- 특히 P0 범위를 정할 때 미검증 경쟁사 주장을 진입 요건으로 삼지 않는다(8절과 같은 이유).

## 11. "Tomverse Verified" 배지의 의미론적 제약

배지는 마케팅 자산인 동시에 **책임 발생 지점**이다. "Verified"라고 찍은 변경이 프로덕션을 깨뜨리면, 이는 "제안입니다"보다 훨씬 강한 약속을 어긴 것이다.

**배지는 "이 코드가 옳다"가 아니라 "어떤 검사가 실행되어 통과했다"만 인증한다.** 전략 문서의 예시가 이미 옳은 방향을 보여준다:

```
Tomverse Verified
✓ Build          ✓ 128 tests      ✓ Type check
✓ Security scan  ✓ Independent model review
△ Performance test not configured     ← 실행하지 않은 것을 반드시 명시
```

규칙:
- **실행하지 않은 검사는 침묵하지 않고 명시한다.** 없는 항목을 숨기면 완결성을 암시하게 된다.
- 테스트 커버리지가 낮은 저장소에서는 "128 tests 통과"가 주는 인상을 조정해야 한다(변경된 코드를 실제로 커버하는 테스트가 몇 개인지가 진짜 정보다).
- 검수 모델이 통과시켰다는 사실은 결정론적 검사와 **동급으로 표시하지 않는다** — 4절 판정 우선순위가 UI에도 반영돼야 한다.

## 12. Windows 특화 — 약점이 아니라 해자

전략 문서 §8에 동의하며, 여기에 **우리가 이번 개발 과정에서 직접 겪은 근거**를 덧붙인다. Tomverse Code를 개발하면서 이 환경에서 실제로 발생한 마찰:

- Rust 설치 후 winget이 PATH를 갱신하지 않아 기존 셸에서 `cargo`를 못 찾음
- MSVC 링커 부재로 Rust 컴파일 실패 → VS Build Tools 설치 → **첫 설치가 불완전하게 끝나 Windows SDK 누락** → `vs_installer.exe modify`로 복구
- `vcvarsall.bat` 환경 없이는 `cargo build`가 링크 단계에서 실패
- Bash→cmd.exe 경유 시 경로 인용이 깨져 `.bat` 래퍼가 필요했음

**이건 정확히 Copilot이 세밀하게 다루지 못할 종류의 문제다.** 모든 플랫폼을 지원해야 하는 제품은 Windows 툴체인의 이런 함정에 깊이 투자하기 어렵다. 우리는 Windows만 하므로 여기에 전부 투자할 수 있고, 이 마찰들은 실제 Windows 개발자가 매일 겪는 것이다.

우선순위: PowerShell 명령 의미 분석 → Developer PowerShell 환경 자동 구성 → Visual Studio/MSBuild 인식 → 파일 잠금·긴 경로 처리 → Windows Credential Manager(이미 설계됨) → 관리자 권한 분리(이미 Policy Gate deny 규칙에 있음).

## 13. 로드맵 (재구성)

전략 문서의 P0~P3을 8절 기준(차별화가 요구하는 것)으로 재배치하고, 2절 가설 게이트를 명시적 단계로 삽입한다.

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| **M0 — 코어 루프** | Tool Runtime, Policy Gate, Context Engine, VERIFYING, 이벤트 로그. 공급자 2개(OpenAI/Anthropic). Model Registry + Role 추상화(multi-engine 0단계) | 실제 저장소에서 버그 수정 1건이 승인→실행→검증→커밋까지 완주 |
| **M1 — 가설 게이트** | 어려운 픽스처 세트(다중 파일·모호한 요구사항·미묘한 경계값)로 스파이크 재실행 | 교차검증이 단일 모델 대비 유의미한 이득을 보이는가에 대한 **데이터 기반 답** |
| **M2 — 차별화 (게이트 통과 시)** | Blind Review(4절), 4단계 tier(5절), 모델 불일치 화면, Verified 리포트(11절), 전송 투명성(7절), Agent Trace 완성(6절) | 불일치 화면이 실제 태스크에서 의미 있는 정보를 보여줌 |
| **M3 — Arena** | Git worktree 격리, 복수 구현 경쟁, 9절 완화책 전체 포함 | `critical` tier에서 Arena가 기존 테스트 기준으로 최적 구현 선택 |
| **M4 — 학습 라우터** | 축적된 실측 데이터로 라우팅 전환(multi-engine 8절) | 표본이 통계적으로 유의미한 수준 |
| **M5 — 기업** | 조직 정책, 모델 허용 목록, 데이터 지역, 감사 export | — |

**Windows 특화(12절)는 별도 트랙으로 M0부터 지속 진행한다** — 한 마일스톤에 몰아넣을 성격이 아니라 모든 단계에서 조금씩 쌓이는 품질이다.

**범위 밖(현 시점):** 자체 에디터, 클라우드 샌드박스, 인라인 자동완성, 자체 모델 훈련, 음성 입력, 플러그인 마켓. 에디터 대신 diff·리뷰 화면에 집중하고 기존 IDE 연동을 검토한다.

## 14. 북극성 지표와 계측

**북극성: 검증을 통과하고 사용자가 승인한 작업 한 건당 비용과 시간.**

이 지표를 채택하는 이유는 그것이 "좋아 보인다"가 아니라 **결정론적으로 관측 가능**하고, 우리 이벤트 로그가 이미 필요한 데이터를 전부 갖고 있기 때문이다(`VERIFYING` 결과 + 승인 이벤트 + 비용·시간).

보조 지표 — **M0부터 전부 기록한다**(나중에 붙이면 몇 달의 데이터를 잃는다):

| 지표 | 출처 |
|---|---|
| 첫 시도 테스트 통과율 | `verification_reports.attempt_number = 0` |
| 사용자 승인율 / 거부율 | `APPROVAL_GRANTED` / `APPROVAL_DENIED` |
| 되돌리기 비율 | 롤백 `ToolRequest` 발생 |
| 작업당 비용·green까지 시간 | 이벤트 타임스탬프 + 토큰 사용량 |
| **검수 모델이 실제 결함을 발견한 비율** | 검수 지적 항목 중 테스트로 확인된 것 |
| **잘못된 검수 경고 비율** | 검수가 지적했으나 검증이 반박한 것 |
| **blind vs informed 판정 불일치율** | 4절 — anchoring 크기의 직접 측정 |
| **생성된 테스트가 틀렸던 비율** | 9절 — Arena 근거의 건전성 |
| 위험 명령 차단률 | Policy Gate `deny` |

굵게 표시한 4개는 **경쟁사가 측정하지 않는 것**이고, 우리 차별화가 실제로 작동하는지 판별하는 핵심이다. 특히 마지막 두 개는 우리 자신의 전략이 틀렸는지를 알려주는 지표이므로 반드시 봐야 한다.

## 15. 미해결

- 어려운 픽스처 세트의 구체적 구성 (M1의 전제) — 무엇을 "어렵다"고 정의할 것인가
- Arena의 구현 결합(merge) 전략 — "최적 선택"은 명확하나 "결합"은 훨씬 어려움. 초기엔 선택만 지원할지
- `critical` tier에서 Arena 실행 비용을 사용자가 사전에 승인하는 UX (3개 구현 = 3배 비용)
- 검수 모델의 지적을 "실제 결함"으로 판정하는 자동 기준 (14절 지표의 전제)
- IDE 연동 범위 (VS Code / Visual Studio) 및 데스크톱 앱과의 역할 분담
