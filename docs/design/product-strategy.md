# 제품 전략: GitHub Copilot 대비 포지셔닝

status: accepted (2026-07-25) — 단, 2절의 **가설 게이트**를 통과하는 것을 전제로 함
관련: [multi-engine-routing.md](./multi-engine-routing.md), [state-machine-and-protocol.md](./state-machine-and-protocol.md), [ui-wireframes.md](./ui-wireframes.md)

## 1. 전략의 핵심 명제

> 기능 개수로 Copilot을 이길 수 없다. **"Copilot보다 결과를 더 신뢰할 수 있다"를 측정 가능하게 증명**하는 것이 유일한 승산이다.

이 명제에 동의한다. 기능 폭에서는 GitHub의 리소스를 이길 수 없고, 애초에 그 싸움을 하면 우리의 유일한 구조적 우위(모든 것이 로컬 오케스트레이터를 통과하므로 무엇이 어디로 갔고 무엇이 검증됐는지 정확히 안다)를 활용하지 못한다.

**전략의 4개 기둥 (차별화):**
1. 투명한 공급자 간 교차 검증 (모델 간 불일치를 숨기지 않고 보여준다)
2. 결정론적 테스트 판정 (LLM이 아니라 테스트가 최종 판정자)
3. Candidate Arena (여러 구현을 실제로 실행시켜 경쟁)
4. 실제 성공률 기반 라우팅 (범용 벤치마크가 아닌 이 저장소의 실측)

**그리고 기능 범위(8절):** 위 차별화는 "기능이 부족해도 된다"는 뜻이 **아니다.** Tomverse Code는 Copilot이 제공하는 기능을 기본적으로 모두 커버하는 것을 제품 명제로 삼는다. 사용자가 검증 우위를 얻기 위해 쓰던 기능을 포기해야 한다면, 차별화 화면을 볼 기회 자체가 없어지기 때문이다. 단 **커버(범위)와 패리티(깊이)를 분리**해 달성 가능하게 만든다 — 자세한 것은 8절.

## 2. 가설 게이트 — 이 전략 전체의 전제

**차별화(M1)와 Arena(M4) 전체가 "교차 검증이 실제로 가치 있다"는 미검증 가설 위에 서 있다.**

우리 Phase 0 스파이크의 실측 결과를 잊으면 안 된다:

| | 통과율 | 총비용 | 총지연 |
|---|---|---|---|
| 교차검증 (OpenAI 초안 + Claude 검수) | 100% (5/5) | $0.0324 | 24.7s |
| 단일 모델 (Claude 단독) | 100% (5/5) | $0.0198 | 14.5s |

쉬운 태스크에서 교차검증은 **정확도 이득 0%에 비용 1.63배·지연 1.70배**였다. 우리는 이것이 "픽스처가 너무 쉬웠기 때문"이라고 해석했지만, **아직 어려운 태스크로 재검증하지 않았다.**

```
게이트: multi-engine-routing.md 9절 2단계
       "어려운 픽스처 세트로 스파이크 재실행"

  통과 → M1(투명한 교차 검증) 및 M4(Candidate Arena)로 진행
  실패 → 이 전략 문서의 기둥 1·3이 무너짐. 제품 포지셔닝을 재수립해야 함
         (남는 것: 기둥 2 결정론적 판정 + Windows 특화 + 전송 투명성)
```

**이 게이트를 통과하기 전에 교차검증 의존 기능에 큰 투자를 하지 않는다.** 이건 비관이 아니라, 우리가 이미 한 번 실측으로 배운 것을 두 번 무시하지 않겠다는 뜻이다. 게이트가 실패해도 제품이 죽는 건 아니다 — 결정론적 검증, Windows 특화, 데이터 전송 투명성, 그리고 8절의 기능 커버리지 전체는 교차검증과 무관하게 유효하다.

## 3. 우리가 이미 갖고 있는 것

전략 문서가 요구하는 것 중 상당 부분이 이미 설계·구현되어 있다. 새로 만들 것과 이미 있는 것을 구분해야 낭비가 없다.

**각 행은 상태를 주장할 때 그 주장을 반증할 파일을 함께 적는다**(3.1절). 손으로 적은 상태표는
반드시 낡고, 낡은 표는 "있는 것을 없다"고 말해 같은 것을 두 번 만들게 한다 — 실제로 그렇게
낡아 있었다.

### 3.1 상태표가 낡는 것을 검사로 막는다

이 표는 **"새로 만들 것과 이미 있는 것을 구분해야 낭비가 없다"**는 목적으로 있다. 그런데 손으로
적은 상태는 코드가 앞서가면 조용히 낡고, **낡은 상태표는 자기 목적을 정면으로 배신한다** —
"미착수"라고 적힌 것을 읽고 이미 있는 것을 다시 만들게 된다.

실제로 그랬다. 위 표는 네 행이 틀려 있었고 **전부 같은 방향으로** 틀렸다: 불일치 화면(3.9절
카드로 구현됨), narrative 독립성(`blind` 모드로 구현됨), 전송 투명성 표시(`TransmissionPanel`과
`tomverse-host transmission`), 재현 러너(`reproduce --apply`). 넷 다 **있는 것을 없다고** 말하고
있었다.

그래서 각 행에 **그 주장을 반증할 파일**을 마커로 적는다.

- `<!-- present: 경로, 경로 -->` — 있다고 주장했으므로 그 경로가 **있어야** 한다.
- `<!-- absent: 경로 -->` — 없다고 주장했으므로 그 경로가 **없어야** 한다.

`packages/toolchain/test/docStatus.test.ts`가 대조한다. 마커가 없는 행도 실패다 — 근거 없이
상태만 적는 행이 다시 생기면 그 행은 처음부터 검사 밖에 있게 된다.

**이 검사가 잡는 것과 못 잡는 것을 구별해 둔다.** 파일이 생기거나 사라진 것은 잡지만, 파일이
남아 있는데 그 안의 기능이 무의미해진 것은 못 잡는다. 그건 원리적으로 문장을 읽어야 아는
일이다 — 검사의 목적은 판정을 대신하는 것이 아니라, **가장 자주 일어나는 낡는 방식**(만들어
놓고 표를 안 고침)을 자동으로 막는 것이다.

## 4. 채택: Blind Review — 그리고 현재 코드의 실제 결함

전략 문서에서 **가장 가치 있는 단일 제안**이다. 그리고 이건 개선 제안이 아니라 **현재 코드의 버그 지적**이다.

multi-engine-routing.md 5절에서 우리는 "검수자는 실행자와 다른 공급자여야 한다"를 불변식으로 만들었다. 하지만 그건 *공급자* 독립성일 뿐이고, **서사(narrative) 독립성은 전혀 보장하지 않는다.**

현재 스파이크 코드(`spike/src/providers/anthropic.ts`)의 검수 프롬프트는 초안 작성자의 자기 설명을 그대로 전달한다:

```
## Draft author's interpretation
{draft.interpretation}

## Draft author's proposed file
```

검수 모델은 "이 코드가 요구사항을 만족하는가"를 판단하기 전에 **초안 작성자가 무엇을 의도했다고 주장하는지를 먼저 읽는다.** 이건 교과서적인 anchoring이고, 교차 검증의 가치를 구조적으로 깎아먹는다. 다른 공급자를 쓰는 비용은 다 내면서 독립성은 일부만 얻고 있는 셈이다.

**채택할 두 가지 검수 모드:**

```typescript
type ReviewMode = "informed" | "blind";

// blind: 검수 모델에게 제공하는 것
//   - 원래 사용자 요구사항
//   - 변경된 코드 (diff)
//   - 관련 저장소 컨텍스트
//   - 테스트 결과
// blind: 숨기는 것
//   - 실행 모델의 이름·공급자
//   - 실행 모델의 interpretation / rationale / 자기평가
```

두 모드로 같은 초안을 검수시켜 판정이 갈리는 빈도가 anchoring 크기의 직접 측정치다(14절).

### 4.1 실측 결과 — 그리고 "blind를 기본값으로"라는 제안의 철회

구현 직후 `spike/src/anchoringProbe.ts`로 실제로 재봤다. **초안을 의도적으로 조작해서**(코드는 고장난 채로 두고 설명만 자신 있게 "고쳤다"고 주장) blind와 informed에 같은 초안을 주는 하네스다.

| 케이스 | 미끼 유형 | blind | informed |
|---|---|---|---|
| pagination | 진단은 옳고 완료 주장만 거짓 | REJECT / FAIL | REVISE / **PASS** |
| boundary | 진단은 옳고 완료 주장만 거짓 | REJECT / FAIL | REVISE / **PASS** |
| null guard | **진단 자체가 거짓**("테스트가 null을 기대한다") | REJECT / FAIL | REVISE / **PASS** |

최종 테스트 통과: **blind 0/3, informed 2/3**(위 표는 3차 실행 기준, 앞선 실행 포함해 informed가 일관되게 우세).

**두 가지를 배웠다.**

**① anchoring이 관측되지 않았다.** 세 번째 케이스는 "테스트가 무엇을 기대하는지"에 대해 자신 있게 거짓을 말하는 미끼였는데, informed 검수는 그 주장을 **명시적으로 반박했다**("요구사항과 테스트는 빈 문자열을 요구하는데 초안은 null을 반환한다"). 이 모델은 확신에 찬 거짓 주장에 끌려가지 않았다.

**② 정보를 숨긴 대가는 실재했다.** blind는 세 케이스 모두 REJECT하고 아무것도 만들지 않은 반면, informed는 잘못을 지적한 *뒤 고쳐서* 통과시켰다. 초안의 설명은 anchoring 편향으로 작동한 게 아니라 **유용한 명세 신호**로 작동했다 — "무엇이 되어야 하는가"를 알려주니 검수자가 수리로 이어갔다.

**측정 과정에서 발견한 방법론 오류 (기록 가치 있음):** 첫 실행에서는 불일치가 1/2로 나왔는데, 원인이 anchoring이 아니라 **내가 두 프롬프트를 다르게 쓴 것**이었다. blind에만 "judge **only** whether…"라고 써서 수리 행동 자체를 억제했다. 프레이밍을 맞추자 그 불일치는 사라졌다. **프롬프트 변형 두 개를 비교할 때 숨긴 정보 외의 모든 문구가 동일해야 한다** — 아니면 자기 자신의 프롬프트 불일치를 측정하게 된다.

### 4.2 수정된 입장

- ~~`verified` 이상에서 blind가 기본값~~ → **철회.** 데이터가 지지하지 않고 오히려 반대 방향이다.
- **기본값은 `informed`를 유지한다.** blind는 구현해두되 옵션으로 두고 계속 측정한다.
- 다만 이 결론도 약하다: **n=3, 전부 합성 초안, 전부 의도적으로 고장난 코드**다. 실제 초안은 대체로 옳으므로 anchoring 위험의 양상이 다를 수 있다.
- **여전히 유효한 것:** 공급자 독립성 불변식(multi-engine 5절)은 이 결과와 무관하게 유지된다. blind가 다룬 건 *서사* 독립성이고, 그건 실측 결과 이득이 확인되지 않았을 뿐이다.
- **철회를 코드에도 적었다.** `prompts.ts`의 blind 분기 주석이 "M0에서는 기본 비활성이며 이 분기는 **M1이 켤 자리**다"로 남아 있었다 — 4.2절이 뒤집기 전의 계획이다. 그 주석만 읽은 사람은 M1에서 기본값을 뒤집는 것이 예정된 작업이라고 읽고, **측정으로 내린 결정을 되돌리게 된다.** 결론을 문서에만 적고 코드에 남은 예고를 지우지 않으면, 다음 사람이 만나는 것은 문서가 아니라 그 주석이다.
- 14절의 `blind vs informed 판정 불일치율` 지표는 그대로 둔다. 실제 태스크에서 다시 재야 한다.

**이 절 자체가 제품 명제의 자기적용 사례다.** 나는 blind review를 "명백한 개선"이라고 제안했고, 결정론적 테스트 결과가 그걸 반박했다. 모델의 의견(내 것 포함)이 아니라 테스트가 판정했다 — 우리가 만들려는 제품이 하려는 일이 정확히 이것이다.

## 5. 채택: `complexityTier` 2단계 → 4단계 확장

현재 `simple | standard`를 전략 문서의 4단계로 확장한다. 사용자에게 노출되는 품질 정책 이름과 내부 tier를 일치시킨다.

```typescript
type ComplexityTier = "fast" | "balanced" | "verified" | "critical";
```

| tier | 실행 방식 | 예시 |
|---|---|---|
| `fast` | 단일 저비용 모델, 검수 없음 | 설명, 주석, 이름 변경 |
| `balanced` | 실행 모델 + 조건부 검수 | 단일 파일 버그, 작은 기능 |
| `verified` | 실행 + **다른 공급자** 독립 검수(blind 기본) | 다중 파일 리팩터링 |
| `critical` | 복수 구현 경쟁(Arena) + 검수 + 보안 검사 + 사용자 승인 | 인증·결제·마이그레이션 |

- 기존 `simple` → `fast`/`balanced`, `standard` → `verified`로 매핑. `critical`은 Arena(M4)가 준비될 때까지 `verified`와 동일하게 동작하되 승인 요구만 강화.
- **사용자가 태스크별로 tier를 올릴 수 있어야 한다**(내리는 것도). 라우터의 자동 분류는 기본값 제안이지 강제가 아니다.
- ~~TRIAGE 판정 신호에 §5의 항목을 추가: 인증·결제·암호화 코드 경로 여부, DB migration 여부, public API 변경 여부~~ → **셋 중 둘을 구현했다**([state-machine 13.4.1절](./state-machine-and-protocol.md)). 이 항목은 tier 개수와 독립이라 4단계 확장을 기다릴 이유가 없었다. 구현하면서 드러난 것: **기존 위험 신호가 사용자의 표현에 의존하고 있었다** — `riskKeywords`는 `userMessage`를 보므로 같은 코드를 고치는 같은 작업이라도 "결제 로직 고쳐줘"는 `standard`, "이 함수 좀 봐줘"는 `simple`이었다. 경로는 사용자가 고르는 값이 아니다. 라벨 붙은 29개 세트 실측에서 어려움→simple이 20/24 → 19/24로 줄고 쉬움→standard는 1/5로 그대로여서, **교환비를 정하지 않고도** 켤 근거가 된다. `public API 변경`은 넣지 않았다 — 심볼 분석이 있어야 하는데 Tree-sitter가 아직 없고, 경로 이름으로 흉내 내면 틀릴 때가 더 많다
- 워크스페이스 정책의 `forceComplexityTier`는 하한선으로 동작(예: 결제 저장소는 최소 `verified`).

> **4단계 확장 자체는 지금 하지 않는다** — [13.4.2절](./state-machine-and-protocol.md). 이유가 둘이고 각각 독립적으로 충분하다: **①** 위 표의 이름(`fast`/`verified`)이 state-machine 17.5절이 갈라놓은 두 축(규칙이 정하는 tier / 사용자가 고르는 실행 모드)을 다시 합친다 — 그 혼동이 만든 비용 2배 결함을 방금 고쳤는데 이름 층위에서 되살아난다. **②** 13.4절 실측대로 지금 쓰는 축이 두 라벨을 가르지 못하므로, 넷으로 늘리면 **이름만 넷이고 규칙은 두 답만 낸다.** 그래서 이 항목의 선행 조건은 구현이 아니라 (a) 축을 합치지 않는 명명과 (b) 네 단계를 실제로 가르는 축이다.

### 6.2 워크스페이스 지문 — HEAD만으로는 다른 상태를 같다고 말한다

같은 HEAD에서도 워킹 트리가 다르면 **다른 실행**이다. 커밋되지 않은 변경을 반영하지 않는 지문은
서로 다른 상태를 같다고 보고하고, 감사에서 그건 빠뜨림이 아니라 오답이다.

세 가지 **읽기 전용** 명령을 이어 SHA-256을 낸다. 전부 이미 allowlist에 있어 정책 변경이 없다.

| 재료 | 담기는 것 |
|---|---|
| `git rev-parse HEAD` | 커밋된 상태 |
| `git status --porcelain -uall` | 변경·추가·삭제된 **경로**(추적되지 않는 파일 포함) |
| `git diff HEAD` | 추적되는 파일의 **내용 변경** |

재료 사이에 구분자를 넣는다 — 그냥 이으면 한 재료의 끝과 다음의 시작이 붙어 **서로 다른 조합이
같은 바이트열**이 될 수 있다.

#### Rust가 계산하고 Rust가 기록한다

Node는 `workspace.fingerprint`로 "지금 찍어라"만 말할 수 있고 값에는 손대지 못한다.
`verify.run`과 같은 이유다 — Node가 "검증했다"를 만들어낼 수 없어야 하듯 **"이 상태였다"도
만들어낼 수 없어야 한다.** 감사 기록이 Node의 정직함에 의존하면 그건 감사가 아니다(원칙 2).

찍는 시점은 스냅샷을 만들기 **직전**이다. 스냅샷이 읽는 파일 상태와 최대한 가까워야 한다.
실패해도 태스크를 세우지 않는다 — 지문은 감사 재료이지 실행 조건이 아니다.

#### 놓치는 것을 문구가 아니라 데이터로 말한다

**추적되지 않는 파일은 경로만 들어가고 내용은 들어가지 않는다**(`git diff HEAD`가 추적되는
파일만 보므로). 그래서 추적되지 않는 파일의 내용만 바뀐 두 실행은 같은 지문을 낸다.

이걸 항상 붙는 면책 문구로 덮지 않고 `untrackedFiles` **개수**를 함께 남긴다 — 그 수가 0이면
이 한계가 **이번 실행에는 적용되지 않는다.** 언제나 붙는 경고는 아무도 읽지 않는다(17.11절에서
"아는 모양만 찾습니다"를 경고 안에 넣은 것과 반대 방향의 같은 고민이다: 저쪽은 한계가 늘 적용돼
늘 말해야 했고, 이쪽은 조건부라 조건부로 말한다).

`inputs`에 재료 목록을 남긴다. 나중에 재료가 바뀌면 옛 지문과 비교할 수 없는데, **그 사실을 알
방법이 없으면 "상태가 달라졌다"로 잘못 읽는다.**

git 저장소가 아니면 `available: false`를 낸다. **빈 해시를 만들어 내면 "상태가 비어 있었다"로
읽히는데 실제로는 "잴 수 없었다"이다.**

### 6.1 응답한 모델을 기록한다 — 보내는 쪽은 맞았고 받는 쪽이 빠져 있었다

`model_id`는 우리가 **요청한** 값이라 언제나 우리 기대와 같다. 그것만 남기고 "이 모델이 답했다"고
기록하면, 공급자가 조용히 다른 모델로 대체했을 때 **로그가 그 사실을 지운다.** 감사 기록에서
그건 빠뜨림이 아니라 거짓말에 가깝다.

구현하면서 드러난 것: sidecar는 이미 응답 envelope에서 `providerReportedModelId`를 뽑아
`usage.record` payload에 실어 보내고 있었다. **DB 경계에서 버려지고 있었을 뿐이다.** 보내는 쪽은
맞았고 받는 쪽이 빠져 있었으므로, 고칠 자리는 스키마 하나였다(v4, 전부 추가 연산).

`provider_request_id`를 함께 남기는 이유: 감사에서 **공급자 로그와 대조할 수 있는 유일한 열쇠**가
그것이다. 우리 `callId`는 우리만 아는 값이라 상대에게 물을 수 없다.

**모르는 것을 대체로 세지 않는다.** v4 이전 행이나 공급자가 모델을 알려주지 않은 호출은
`resolved_model_id`가 NULL이다. 그걸 "대체 없음"으로 접으면 옛 기록 전체가 무사한 것으로
보고되고, 반대로 "대체"로 접으면 진짜 대체가 그 안에 묻힌다. 그래서 집계는 **둘 다 아는
행에서만** 비교하고, 화면은 비어 있을 때 "같았다는 뜻이 아니라 확인할 수 없다는 뜻"이라고 쓴다.

이 사실은 7절의 전송 화면에 함께 나온다 — "무엇이 어디로 나갔는가"와 "무엇이 답했는가"는 같은
질문의 두 면이고, 따로 두면 사용자가 두 화면을 대조해야 한다.

### 6.3 export — 무엇을 보장하는지 파일 안에 적는다

**replay의 의미를 정확히 정의해야 한다.** LLM은 결정론적이지 않으므로 "같은 입력으로 다시 돌리면 같은 결과"는 보장할 수 없다. 우리가 보장할 수 있는 것은:
- **재현(reproduce)**: 기록된 patch·명령을 그대로 재적용해 최종 상태를 정확히 복원 — 결정론적, 보장 가능
- **재실행(re-run)**: 같은 프롬프트로 모델을 다시 호출 — 비결정론적, 비교 분석용

이 둘을 UI와 문서에서 섞어 쓰면 안 된다. 기업 감사에 필요한 건 전자다.

#### `show`가 이미 있는데 왜 별도 명령인가

`show`는 **진단용 덤프**다. 모양이 바뀌어도 되고, 실제로 바뀐다. export는 **몇 년 뒤에 읽힐
기록**이라 다른 것을 약속해야 한다.

| | `show` | `export` |
|---|---|---|
| 형식 안정성 | 없음 | `formatVersion`으로 고정 |
| 도구 args(argv·patch) | 없음 | 있음 |
| 공급자 호출 원본 | 없음 | 있음 (응답 모델·`provider_request_id` 포함) |
| 워크스페이스 지문 | 이벤트 안에 묻힘 | 최상위 |
| 무엇을 보장하는가 | 적지 않음 | **파일 안에 적는다** |

**argv·patch 원문이 export에 반드시 있어야 하는 이유**는 원칙 6이다. 이 제품이 약속하는 것이
"승인 화면에 보인 argv가 실제 실행된 것과 같다"인데, argv가 빠진 기록으로는 **그 약속을 사후에
확인할 수 없다.** 확인할 수 없는 약속은 약속이 아니다.

지문을 최상위로 올리는 이유는 그것이 **재현의 전제**이기 때문이다. 이벤트 목록 안에 묻혀 있으면
읽는 사람이 전제를 확인하지 않고 재현을 시도한다. 없으면 키를 빼지 않고 `null`로 둔다 —
키가 없으면 "그런 개념이 없었다"로, 빈 값이면 "깨끗한 상태였다"로 잘못 읽힌다.

#### `guarantees` 블록 — 감사 기록은 자기 범위를 스스로 말해야 한다

**무엇을 보장하는지 적지 않은 감사 기록은 읽는 사람이 더 많은 것을 보장한다고 가정하게 만든다.**
그래서 `guarantees`가 파일 맨 앞에 오고, 거기에 재현/재실행의 구분과 artifact 제외와 시작 상태
전제가 문장으로 들어간다. 문서에만 적어두면 파일만 받아 본 사람에게는 없는 것과 같다.

`reproduce.steps`는 **상태를 바꾼, 실제로 실행된** 요청만 시간순으로 담는다. 읽기 전용 도구가
섞이면 "다시 실행하면 되는 것"의 목록이 아니게 되고, 거부된 요청이 섞이면 **거부된 동작을 다시
하라고 말하는 파일**이 된다. 모르는 도구는 상태를 바꾼다고 본다 — 새 도구가 조용히 빠지는 것보다
들어가서 눈에 띄는 편이 낫다.

각 단계에는 `recordedOutcome`이 붙고 거기에 **종료 코드**가 들어간다. `status: "ok"`는 "명령이
성공했다"가 아니라 "도구가 끝까지 돌았다"이기 때문이다(`run_command`는 0이 아닌 종료 코드를
"명령이 실패했다는 사실"로 다룬다). 종료 코드를 빼고 내보내면 읽는 사람은 이 목록을 **전부
성공한 단계들**로 읽는다. 종료 코드는 출력 artifact에서 **정수 하나만** 꺼내며, 본문은 그대로
로컬에 남는다.

#### artifact 본문은 담지 않는다

검증 출력과 큰 도구 출력은 참조만 들어간다. 이유는 크기가 아니라 **성질**이다: artifact에는 빌드
로그가 통째로 들어 있고 거기에는 환경변수 이름·경로·사내 호스트명이 섞인다. export는 **밖으로
나가라고 만든 파일**이므로 기본이 보수적이어야 하고, 첨부는 사용자의 선택으로 남긴다.

#### 재현 러너 — 검사와 적용이 모두 있다

이 파일은 **재현의 재료**를 담는다. 재현을 수행하는 것은 러너이며
([state-machine-and-protocol.md 21절](./state-machine-and-protocol.md),
`tomverse-host reproduce --file <export.json> [--apply]`), 검사가 기본이고 적용이 플래그다.

규칙을 정하는 과정에서 원래 문항이 **답할 수 없는 형태**였다는 것이 드러났다 — "지문이 다르면
거부할지 경고 후 진행할지"는 재현을 한 동작으로 보고 있었고, 실제로는 **아무것도 쓰지 않는
검사**와 **파일을 쓰는 적용**이 다른 동작이다. 나누면 답이 사람에 따라 갈리지 않는다: 검사는
어떤 전제에서도 거부하지 않고(쓰지 않으므로 거부할 것이 없다), 적용만 전제를 요구한다.

그래서 이 export 파일 하나로 감사자는 **같은 상태를 만들 수 없는 머신에서도** 답을 얻는다 —
지문이 다르다는 사실만이 아니라 **무엇이 다른지**(기반 커밋인지 워킹 트리인지)와 **기록된 patch가
실제로 붙는지**까지.

**그리고 적용기를 만들자 이 파일의 구멍 둘이 드러났다**(21.6절). 최종 내용 해시가 빠져 있어
"기록과 같아졌는가"를 물을 수 없었고 — 그러면 재현기가 말할 수 있는 것은 "단계가 다 돌았다"뿐인데,
그건 위에서 정의한 "최종 상태를 정확히 복원"의 확인이 아니다 — 종료 코드도 대부분의 명령에서
사라지고 있었다(아래 exitCode 문단이 약속한 것이 실제로는 지켜지지 않고 있었다). 둘 다 고쳤고
형식 버전이 2가 됐다. **기록을 읽기만 하는 도구는 기록이 비어 있어도 잘 돈다** — 기록으로
무언가를 하려고 해야 빈 곳이 보인다.

#### UI는 값을 받고 파일은 쓰지 않는다

`task_export`는 값만 돌려준다. 임의 경로 쓰기를 UI가 시킬 수 있게 만들면, 모델 요청이 Policy
Gate를 지나야 한다는 규칙과 나란히 **게이트를 지나지 않는 두 번째 쓰기 경로**가 생긴다. 파일로
떨구는 것은 `tomverse-host export`가 한다.

`export`만 pretty JSON으로 출력한다. 다른 하위 명령의 출력은 도구가 바로 먹지만 export는 파일로
저장되어 사람이 읽고 diff하는 것이 용도다 — 한 줄로 내보내면 그 용도가 사라진다.

## 7. 채택: 데이터 전송 투명성 — 구조적으로 우리에게 저렴하다

전략 문서 §9는 기업 확보의 핵심인데, **우리 아키텍처에서는 이게 거의 공짜다.** Context Engine이 어떤 파일을 패키징했는지 정확히 알고(context-engine.md 4절 `relevantFiles[].reason`), 모든 공급자 호출이 Node sidecar 한 곳을 통과하며, 모든 것이 이벤트 로그에 남는다.

Copilot이 이 기능을 사후 추가하려면 컨텍스트 수집 경로 전체를 계측해야 하지만, 우리는 이미 그 경로가 단일하고 명시적이다. **적은 구현 비용으로 큰 차별화가 나오는 항목이므로 M1에 둔다.**

구현: 태스크별로 `(공급자, 파일 목록, 토큰 수, 마스킹된 secret 수)`를 집계해 UI에 표시
(`core/src/transmission.rs`, `tomverse-host transmission --task`, `TransmissionPanel`).
**저장된 이벤트와 `provider_usage`에서 만든다** — 진행 중 상태를 들고 있다가 보여주면 앱을 다시
켠 뒤에는 답하지 못하는데, 사용자가 이 질문을 하는 시점은 대개 그 뒤다.

**모든 프롬프트가 같은 스냅샷을 싣는다**(`providers/prompts.ts`의 네 빌더가 전부 `renderSnapshot`을
쓴다). 그래서 "이 파일들이 이 공급자들 **각각에게** 갔다"고 정확히 말할 수 있고, 공급자별로 파일
목록을 따로 들고 다닐 필요가 없다. 이 성질이 깨지면(모델별 예산으로 프롬프트를 다르게 자르게
되면) 이 화면의 주장도 함께 바뀌어야 한다.

### 7.1 정직하게 쓰지 않으면 정반대로 읽히는 두 자리

이 절의 초안은 "`.env`는 인덱스 진입이 차단돼 있으니 **Local only**로 표시만 하면 된다"고 적었다.
구현해 보니 **그 표시가 거짓이 된다.**

**① 제외된 파일도 이름은 나간다.** 내용은 컨텍스트에 들어가지 않지만, 프롬프트에는 "다음은
일부러 제외했다"는 목록으로 **경로와 사유가 실린다**(`renderSnapshot`의 "Files deliberately
excluded from context"). 모델이 그 파일이 없다고 보고 내용을 추측하는 것을 막으려는 것이고,
그 대가로 경로 이름은 나간다. "Local only"라고만 쓰면 경로도 안 나간 것으로 읽히므로,
목록을 **`sentFiles`(내용까지)와 `namedOnlyFiles`(이름만)로 나눠서** 보여준다.

**② 마스킹은 저장 기록에만 걸린다.** `secretShapesMasked`는 DB에 남기기 전에 가린 개수이고,
같은 답변은 프롬프트에 **원문으로** 실려 나갔다(state-machine-and-protocol.md 17.11절).
이 숫자만 화면에 올리면 "가려져서 안 나갔다"로 읽히는데 정반대다. 그래서 자유 텍스트 답변
건수와 **함께** 내고, 문장이 "저장 기록에서만 가려졌다"를 명시한다.

**그리고 빈 목록이 곧 안전은 아니다.** 컨텍스트를 아직 모은 적이 없는 것과 모았는데 아무것도
고르지 않은 것은 다른 사실이라 `snapshotTaken`으로 구별한다 — 뭉개면 화면이 거짓 안심을 준다.

**말하지 않는 것**: 공급자가 전송받은 것을 어떻게 보관하거나 학습에 쓰는지. 우리 계측의 범위
밖이고, 화면이 그 부분을 흐리게 말하면 이 기능의 신뢰가 통째로 없어진다.

#### 7.1.1 이 집계는 검사되지 않는 전제 위에 서 있었다

`transmission.rs`가 "이 파일들이 이 공급자들 **각각에게** 갔다"고 말할 수 있는 근거는 하나다:
**모든 프롬프트 빌더가 같은 스냅샷을 싣는다.** 그 사실은 모듈 주석에 적혀 있었는데, 그건
**TypeScript 코드에 대한 주장을 Rust 주석에 적어둔 것**이었고 아무도 대조하지 않았다.

빌더가 하나 늘거나 하나가 `renderSnapshot`을 멈추면 이 화면은 **가지 않은 파일을 갔다고**
말하거나 실제로 간 파일을 빠뜨린다. 전송 투명성은 게이트 G가 실패해도 살아남는 차별화 넷 중
하나인데(13절), 그 정확성이 사람의 기억에 달려 있었다.

`packages/sidecar/test/transmissionClaim.test.ts`가 대조한다. **판정 기준을 손으로 적지 않는
것이 핵심이다** — "네 빌더"를 테스트에 다시 적으면 같은 문제가 한 겹 밑으로 옮겨갈 뿐이고,
다섯 번째가 생겨도 목록이 안 늘면 검사는 조용히 통과한다. 그래서 소스에서 `build*Prompt`를
찾아 각각이 `renderSnapshot`을 쓰는지 본다. 빌더를 하나도 못 찾으면 그것도 실패다 — 빈 집합에
대한 전칭 명제는 언제나 참이기 때문이다.

같은 이유로 Rust 주석에서 **개수를 뺐다**. 숫자를 적으면 늘었을 때 주석이 낡는다.

### 7.2 세 번째 자리 — 파일 목록이 "전부"로 읽혔다

7.1이 두 자리를 잡았는데, 세 번째가 남아 있었다. 그리고 이건 문장의 문제가 아니라 **집계가
아예 세지 않던 것**이다.

전송 화면은 `sentFiles`와 `namedOnlyFiles`만 보여줬다. 그런데 프롬프트에 실리는 것은 파일만이
아니다:

- **프로젝트 규칙**(`CLAUDE.md`/`AGENTS.md`)은 **전문이 매 호출에** 실린다. 컨텍스트 엔진의
  선정을 거치지 않으므로 `relevantFiles`에 없고, 따라서 화면에도 없었다. **그 화면을 본
  사용자는 자기 `CLAUDE.md`가 나가지 않았다고 믿는다.**
- **커밋되지 않은 변경 요약**(`git diff --stat`)은 바뀐 파일을 전부 세므로, 컨텍스트로
  선정되지 않은 파일의 **경로도 나간다.** 파일 목록만 보여주면 "이것만 나갔다"로 읽힌다.

7.1이 "제외된 파일도 이름은 나간다"를 잡은 것과 같은 종류의 오독인데, 이번에는 **표시가 아니라
데이터가 없었다.** 그래서 `sentContext`를 만들어 파일이 아닌 전송 내용을 같은 화면에 둔다.
`sentFiles`와 섞지 않는 이유도 7.1과 같다: 선정을 거쳐 실린 것과 언제나 실리는 것은 다른
사실이고, 섞으면 둘 다 뜻을 잃는다.

#### 7.2.1 축이 둘이 아니었다 — 그래서 목록이 셋이다

같은 일이 다시 생기는 것을 막으려고 "프롬프트의 모든 섹션을 집계가 설명하는가"를 검사로
만들려 했다. 섹션을 전부 뽑아 보니 그 문항으로는 답할 수 없는 것들이 있었다:

| 칸 | 무엇 | 왜 나눴나 |
|---|---|---|
| `REPORTED_SECTIONS` | 화면이 실제로 설명하는 것 | — |
| `INSTRUCTION_SECTIONS` | 출력 형식 규칙 같은 **우리 지시문** | 사용자 데이터가 없다. 전송 목록에 올리면 진짜 데이터가 그 사이에 묻힌다 |
| `UNREPORTED_SECTIONS` | **나가지만 아직 세지 않는 것** | 지시문 칸에 넣으면 거짓이고, 설명한다고 적으면 더 큰 거짓이다 |

세 번째 칸이 이 설계의 핵심이다. 검증 출력(`Failing checks`)에는 실패한 테스트의 스택 트레이스와
소스 조각이 들어가고 그건 `relevantFiles`에 없던 파일의 내용일 수 있다. 사용자 판정 원문
(`Acceptance criteria`, `Clarifications`)도 그대로 나간다. 지금 화면은 그것들을 말하지 않으며,
**말하지 않는다는 사실을 적어 두지 않으면 `REPORTED_SECTIONS`가 "전부"로 읽힌다.**

그래서 이 목록 자체가 남은 과제 목록이 된다. `transmissionClaim.test.ts`가 `prompts.ts`에서
섹션을 뽑아 셋 중 정확히 한 칸에 있는지 확인하므로, 새 섹션은 **누군가 결정을 내려야** 통과한다.
반대 방향도 본다 — 사라진 섹션이 목록에 남으면 이 검사는 통과하면서 목록만 낡고, 특히 세 번째
칸에 낡은 항목이 남으면 "아직 할 일이 있다"고 계속 말하게 된다.

#### 7.2.2 이 검사를 만들자 검사가 결함을 하나 더 찾았다

섹션 대조를 처음 돌렸을 때 `Acceptance criteria`가 미분류로 걸렸다. 그건 `renderSnapshot`이
아니라 다른 함수가 만드는 섹션인데, **프롬프트에 실리는 것은 마찬가지**다. 처음 문항을
"`renderSnapshot`의 섹션"으로 좁게 잡았다면 못 잡았을 것이다 — 전송 투명성이 답해야 하는
질문은 "무엇이 공급자에게 도달하는가"이지 "어느 함수가 만들었는가"가 아니다.

## 8. 기능 범위: Copilot 기능 전체 커버를 제품 명제로 삼는다

**제품 명제 (2026-07-25 결정):**

> Tomverse Code는 GitHub Copilot이 제공하는 기능을 기본적으로 모두 커버하는 애플리케이션이다. 사용자가 우리의 검증 우위를 얻기 위해 이미 쓰던 기능을 포기해야 한다면, 그 기능은 차별화 요소가 아니더라도 **이탈 사유**가 된다.

이는 이전 초안의 "차별화가 요구하는 것만 만들고 나머지는 자른다"를 대체한다. 그 접근의 실질적 문제는, 사용자가 MCP 서버 하나를 못 가져와서 이탈하면 우리의 검증 화면을 **볼 기회 자체가 없다**는 것이다.

### 8.1 이 명제를 달성 가능하게 만드는 구분: 커버 ≠ 패리티

"모두 커버"를 문자 그대로 "Copilot과 같은 깊이"로 읽으면 소규모 팀에서 달성 불가능하고, "최대한"에 정지 조건이 없어 영원히 출시하지 못한다. 따라서 두 축을 분리한다.

- **커버(breadth)** — 그 기능 영역이 존재하고 **일반적인 사용 사례에서 동작**한다. 출시 목표.
- **패리티(depth)** — 엣지 케이스·성숙도·성능까지 Copilot 수준. 실사용 데이터가 요구할 때만.

**깊이 정책:**
- **차별화 기능**(검증 투명성, Blind Review, 불일치 화면, Verified 리포트, 전송 투명성)은 **처음부터 깊게** 만든다. 여기서 어중간하면 제품의 존재 이유가 사라진다.
- **패리티 기능**은 "일반 사례 동작 + 한계를 정직하게 표시"로 시작한다. 지원하지 않는 케이스는 조용히 실패하지 말고 명시한다(11절 배지 원칙과 같은 규칙).

### 8.2 출시 기준 — 각 기능이 "커버됐다"고 말할 수 있는 조건

이 표가 "최대한"의 정지 조건이다. 여기 적힌 기준을 만족하면 출시 가능이고, 그 이상은 출시 후 과제다.

| 영역 | 출시 기준 (여기까지 = 커버) | 이후 깊이 확장 |
|---|---|---|
| **파일·검색·patch·터미널·테스트** | 전체 도구 세트가 Policy Gate를 통과해 동작 | 성능, 대용량 파일, 언어별 특화 |
| **테스트·빌드 실행 및 파싱** | 주요 러너(npm/pytest/cargo/dotnet) 결과 파싱, 신규 실패 분리 | flaky 감지, 성능 회귀 비교 |
| **diff·부분 승인·되돌리기·체크포인트** | 파일 단위 diff, 전체/파일 단위 승인, 태스크 단위 롤백 | hunk 단위 부분 승인, 임의 시점 체크포인트 |
| **멀티프로바이더 + BYOK + 모델 선택** | OpenAI·Anthropic·Google 3사, 키 등록, 역할별 수동 지정 | 공급자 추가, 학습 라우터(M4) |
| ↳ 위 행의 현재 상태 | 3사 어댑터 **구현 완료**. 단 Google은 **실측 미확인**이며 착지 기준이 따로 있다([multi-engine 19.4절](./multi-engine-routing.md)) — "구현됨"과 "검증됨"을 뭉개면 출시 기준이 거짓이 된다 | — |
| **저장소 인덱싱 · 토큰 사용량** | Tree-sitter 3개 언어(JS/TS·Python·Rust) + ripgrep 폴백, 태스크별 토큰 표시 | 언어 추가, 증분 인덱싱 최적화 |

### 8.3 명시적 제외 — 다만 "야심"이 아니라 "정의" 때문

다음 둘은 야심의 문제가 아니라 **제품 정의와 충돌**하거나 **다른 제품 형태**여서 제외한다. 재검토는 언제든 가능하지만, 넣으려면 아래 대가를 함께 받아들여야 한다.

| 항목 | 제외 이유 | 넣으려면 치를 대가 |
|---|---|---|
| **클라우드 실행 / 원격 샌드박스** | README와 모든 설계 문서가 "소스 코드는 사용자 PC를 떠나지 않고 Tomverse 서버가 코드를 중계하지 않는다"고 약속한다. 이걸 넣는 순간 그 문장이 거짓이 되고, 기업 시장에서의 유일한 구조적 우위가 사라진다 | 인프라·보안·과금·운영 전체 + 로컬 우선 포지셔닝 포기 |
| **인라인 자동완성** | 100ms 이하 지연대, 다른 모델 티어, 에디터 플러그인이 필요한 사실상 별개 제품. 검증 파이프라인과 공유하는 것이 거의 없다 | 별도 제품 라인 수준의 투자 |

자체 에디터 구현·자체 모델 훈련·플러그인 마켓도 같은 이유로 범위 밖이다(원 제안서도 동의). 에디터 대신 diff·리뷰 화면에 집중하고 기존 IDE 연동을 검토한다.

#### 8.3.1 재검토 시점 — 두 항목은 성질이 다르다

15절에 "재검토 시점"이 한 항목으로 남아 있었는데, **하나로 묶은 것이 문항의 오류였다.** 두
제외의 근거가 다르므로 무엇이 재검토를 촉발하는지도 다르다.

**클라우드 실행 — 관측이 촉발하지 않는다.**
제외 이유가 수요나 난이도가 아니라 **약속**이다: README와 모든 설계 문서가 "소스 코드는 사용자
PC를 떠나지 않는다"고 적고 있다. 그런 종류의 결정은 사용량 데이터가 뒤집지 못한다 — "기업
문의가 N건 오면 재검토"처럼 관측 트리거를 적어두면 **거짓 트리거**가 된다. 수요가 아무리 커도
그것이 약속을 지키지 못할 이유가 되지는 않기 때문이다.

그러므로 여기 적을 것은 트리거가 아니라 **순서**다: 이 결정을 되돌리려면 README와 설계 문서의
그 문장을 **먼저** 바꿔야 한다. 순서가 뒤집히면 코드가 먼저 약속을 깨고 문서는 나중에 거짓이
되며, 그 사이 기간에는 우리도 사용자도 무엇이 참인지 알 수 없다.

**인라인 자동완성 — 선행 조건이 갖춰져야 논의가 성립한다.**
제외 이유가 **제품 형태**다(100ms 이하 지연대, 다른 모델 티어, 에디터 플러그인). 그중 마지막은
15절의 다른 항목("IDE 연동 범위")과 같은 것이고, **IDE 연동이 존재하기 전에는 이 논의가
성립하지 않는다.** 그러므로 재검토 시점은 달력이 아니라 그 선행 조건이다.

그리고 조건이 갖춰진 뒤에도 판단 기준은 수요가 아니라 **지연 예산**이다. "우리 파이프라인이
100ms 이하를 만족할 수 있는가"는 관측 가능한 질문이고, 답이 "아니오"면 수요와 무관하게 별개
제품이다 — 그때 넣으면 8.4절이 경고한 "전부 얕아지는" 쪽으로 간다.

**둘의 공통점 하나**: 어느 쪽도 "언젠가 다시 본다"로 두지 않는다. 그렇게 두면 로드맵에 유령
항목이 남아, 우선순위를 정할 때마다 매번 같은 논의를 다시 한다.

### 8.4 이 결정이 바꾸는 리스크

범위를 넓히면 "출시 못 함" 리스크는 8.2의 출시 기준으로 통제되지만, **새로운 리스크가 생긴다: 30개 기능이 전부 얕아서 차별화 기능마저 얕아 보이는 것.**

방어책은 8.1의 깊이 정책이다 — 차별화 기능만은 처음부터 깊게. 우선순위 충돌이 생기면 **패리티 기능의 깊이를 희생하고 차별화 기능의 깊이를 지킨다.** 이 원칙이 흔들리면 우리는 "기능이 좀 적은 Copilot"이 되고, 그 싸움은 이길 수 없다.

### 8.5 IDE 연동 범위와 역할 분담

15절 항목의 답이다. **"범위"를 기능 목록으로 물으면 답이 "무엇을 넣을까"가 되는데**, 되돌리기
비싼 것은 기능이 아니라 프로세스 경계와 승인이 일어나는 자리다. 그쪽 결정은
[process-architecture.md 13절](./process-architecture.md)에 있고, 여기서는 그 위에서 좁아지는
범위·순서·시점을 정한다.

#### 무엇을 어디에 두는가

| | IDE 확장 | 데스크톱 앱 |
|---|---|---|
| 태스크 시작 (선택 영역·파일 맥락 포함) | ✅ | ✅ |
| 진행 단계·이벤트 보기 | ✅ (읽기) | ✅ |
| diff를 에디터에서 보기 | ✅ | ✅ (자체 화면) |
| **승인 모달** | ❌ | ✅ |
| **불일치 판정 카드** | ❌ | ✅ |
| 검증 결과·근거 배지 | 요약만 | ✅ |
| Agent Trace·감사 export | ❌ | ✅ |
| 자격증명 입력·모델 선택 | ❌ | ✅ |

**규칙 하나로 줄이면: 위험을 만드는 행위는 전부 데스크톱 앱이고, 확장은 시작과 읽기다.**
확장이 하는 유일한 예외적 행위는 앱이 떠 있지 않을 때 **앱 실행 파일 하나를 띄우는 것**이다
(13.2절).

승인과 판정을 확장에 두지 않는 것은 UX 취향이 아니라 4절 원칙에서 나온다 — 그 화면들이 지는
보장은 그것을 그리는 프로세스의 신뢰도를 넘지 못하고, 확장 호스트는 사용자가 설치한 다른
확장과 프로세스를 공유한다.

#### 순서: VS Code 먼저, Visual Studio는 그 다음 — 이유는 사용자가 아니라 비용이다

12절의 해자("환경 해석과 명령 실행 계층")가 가장 크게 닿는 사용자는 .NET·MSVC·WinUI로 Windows
네이티브를 만드는 개발자이고, **그 사람들은 Visual Studio를 쓴다.** 그러면 VS부터 해야 할 것
같지만, 순서를 가르는 것은 수요가 아니라 **계약을 증명하는 비용**이다.

- VS Code 확장은 TypeScript이고 이 저장소는 이미 TypeScript 워크스페이스와 빌드 순서를 갖고
  있다. Visual Studio 확장(VSIX)은 C#/VSSDK이므로 **네 번째 언어와 네 번째 빌드 체인**이
  들어온다. `packages/toolchain`의 기록이 빌드 체인 하나가 얼마나 많은 함정을 데려오는지 이미
  보여준다.
- 그리고 **연동 계약(13.3절의 파이프 프로토콜, 위 역할 분담)은 첫 소비자에서 흔들린다.** 계약이
  흔들리는 동안 확장을 둘 만들면 두 번 고친다. VS Code로 계약을 안정시킨 뒤, VS 확장은 **같은
  계약의 두 번째 소비자**가 된다.
- VS 확장은 착지 기준이 **Windows 머신에서만 검증되는** 항목을 하나 더 늘린다(Job Object·
  Credential Store와 같은 성질 — state-machine 20.6절 모양). 그 목록을 지금 늘리지 않는다.

JetBrains는 **지금 정하지 않는다.** 다만 계약을 프런트엔드 중립으로 두면 나중 비용이 선형으로
붙는다 — 즉 계약 설계가 곧 그 선택지를 살려두는 일이고, 그것이 위에서 계약을 먼저 안정시키는
또 하나의 이유다.

#### 시점: v1 이후 (M3 다음)

13절 로드맵에서 v1은 M3 끝이고, **8.2 표의 출시 기준에 IDE 연동은 없다** — 즉 v1을 막지 않는다.
그리고 M3까지는 승인·판정·감사 화면이 계속 바뀌는데, 그 위에 두 번째 프런트엔드를 얹으면 바뀔
때마다 두 번 고친다. 인라인 자동완성 재검토(8.3.1절)는 이것이 끝난 뒤에야 논의가 성립한다.

#### 하지 않는 것 (명시)

- 확장 안에서 모델을 부르지 않는다 — 키가 확장 호스트에 들어간다.
- 확장 안에 Policy Gate를 두지 않는다. 게이트가 둘이면 둘 중 약한 쪽이 실제 게이트다.
- 확장이 SQLite를 직접 열지 않는다(writer는 Rust 하나).
- 에디터 안에 승인 모달을 그리지 않는다.
- 자체 에디터·인라인 자동완성은 8.3절 그대로 범위 밖이다.

### 8.6 비용 승인은 별도 모달이 아니라 **모드를 고르는 자리**에 붙는다

15절 항목 "`critical` tier에서 Arena 실행 비용을 사용자가 사전에 승인하는 UX (3개 구현 = 3배
비용)"의 답이다. 구현하려고 보니 **Arena를 기다릴 필요가 없는 문제였다** — 같은 문제가 이미
있고, 화면이 그것을 말하지 않고 있었다.

#### 이미 있는 문제

실행 정책은 "Fast — 쉬운 작업은 단일 모델" / "Verified — 항상 독립 검수"라고만 적혀 있었다.
그런데 `verified`는 검수만 켜는 것이 아니라 **실행자를 하나 더 부른다**
(state-machine-and-protocol.md 17.5절 — 대조 게이팅의 축이 실행 모드다). **가장 비싼 결과가
이름에 없었다.**

예산 점검도 **한 호출**이 예약될 수 있는지만 봤다(`budgetCheck.ts`). 상한이 한 번은 되고 세
번은 안 되는 값이면 태스크는 시작해서 돈을 쓰고 도중에 멈춘다 — **시작 전에 거부되는 것보다
나쁜 결말**이다.

#### 그래서 Arena 전용 승인 모달을 만들지 않는다

만들면 승인이 둘이 된다. 그리고 4절 원칙 6("승인 화면에 보인 것이 실제 실행되는 것과 같다")이
비용 축에서 깨지기 쉬워진다 — 모달에서 승인한 금액과 실제 예약 합계가 갈리는 순간, 그 모달은
보장이 아니라 장식이다. Arena는 **같은 자리에 배수 하나를 더하는 것**이다: 구현 K개 → 실행자
K회.

#### 무엇을 말하고 무엇을 말하지 않는가

`budgetCheck.ts`가 세운 규율("확실할 때만 말한다")이 그대로 걸린다. 라우터가 대조나 검수를
드롭할 수 있고, tier가 갈리고, fix loop가 몇 번 돌지 모른다. 그러므로 **"예산이 모자랄
겁니다"는 틀릴 수 있는 경고**이고, 틀릴 수 있는 경고는 몇 번 지나면 맞는 경고까지 함께 묻는다.

대신 **사실 두 개를 나란히 놓는다**(`lib/callPlan.ts`).

- 이 모드가 한 라운드에 부르는 호출 수의 **범위**: 상한(실행자 2 + 검수자 1 = 3)과, 라우터가
  드롭했을 때의 하한(1). **상한만 적으면 언제나 그만큼 나가는 것처럼 읽히고, 하한만 적으면
  비용이 작아 보인다.**
- 지금 상한으로 부를 수 있는 호출 수. **가장 싼 모델을 기준으로 잡는다** — 그래야 "이보다 많이
  부를 수는 없다"가 참이 된다.

그리고 그 수가 **총비용이 아니라는 것**을 함께 적는다(재시도와 수정 루프가 빠져 있다). 둘 다
산수이고 둘 다 참이며, 판단은 사용자가 한다 — 19.6절 큰 변경 안내가 이미 쓴 규칙과 같다:
**사실만 말하고 막지 않는다.**

## 9. 위험: Candidate Arena의 순환 의존 (문서가 다루지 않은 최대 리스크)

Arena는 "여러 구현을 **동일한 acceptance test**로 판정"한다. 그런데 §4는 그 테스트를 "사용자 요청으로부터 acceptance criteria 추출"로 만들라고 한다. 즉:

```
LLM이 쓴 테스트가  →  LLM이 쓴 코드를 판정한다
```

**테스트 생성기가 요구사항을 잘못 이해하면, Arena는 "틀린 테스트를 가장 잘 만족하는 구현"을 자신 있게 선택한다.** 그리고 그 결과에 "Tomverse Verified" 배지가 붙는다. 이건 검증 없는 것보다 나쁘다 — 틀린 확신을 주기 때문이다.

"결정론적 판정자"는 테스트가 주어졌을 때만 결정론적이고, **테스트 자체는 결정론적 산출물이 아니다.** 문서는 이 구분을 하지 않는다.

### 9.1 1차 완화책과 그 한계 (이것만으로는 부족하다)

1. **기존 저장소 테스트를 1차 판정자로 우선한다.** 생성된 테스트는 보조.
2. **생성된 acceptance criteria는 실행 전에 사용자 승인을 받는다.** Arena는 이미 `critical` tier에만 적용되므로 사용자가 개입해 있는 상태다.
3. **생성된 테스트를 독립적인 리뷰 대상으로 취급한다** — 코드 검수와 별개로 "이 테스트가 요구사항을 맞게 표현했는가"를 검수한다.
4. **"테스트 생성기가 틀렸던 비율"을 별도 지표로 측정한다**(14절).
5. 기존 테스트 **회귀 여부**는 생성된 테스트와 무관하게 항상 유효하므로 Arena 점수에서 가중치를 높게 둔다.

**이 5개는 위험을 줄이지만 순환을 끊지 못한다.** 각각의 한계를 정직하게 적는다.

| 완화책 | 실제로 막는 것 | 막지 못하는 것 |
|---|---|---|
| 1·5 (기존 테스트) | "기존 동작을 깨뜨렸는가" | **"요청받은 새 동작을 옳게 구현했는가"** — 기존 테스트는 정의상 *기존* 동작만 인코딩한다. Arena는 **새 작업**에 쓰이므로, 판정의 핵심 질문에 기존 테스트는 침묵한다 |
| 2 (사용자 승인) | 조용한 실패 → 보이는 실패 | 승인 피로. 그리고 "테스트가 의도를 옳게 표현했는가"를 읽어내는 건 코드 읽기보다 어렵다. 사용자는 그 작업을 하기 싫어서 위임한 것이다 |
| 3 (테스트 검수) | 일부 오류 (다른 모델·다른 프레이밍이 잡는 것) | **LLM이 LLM의 테스트를 검사하는 같은 구조** — 순환에 한 턴을 추가할 뿐 끊지 않는다 |
| 4 (지표) | 아무것도 — 이건 완화책이 아니라 사후 측정이다 | 개별 태스크에 대한 보호 0. 게다가 후행 지표라 "틀렸다"는 사실 자체를 누군가 나중에 알아채야 한다 |

**요약: 5개 중 실질적 보호는 2번 하나뿐이고 그마저 인적 요소에 의존한다.** 앞서 "핵심은 기존 저장소 테스트를 1차 판정자로 두는 것"이라고 요약한 것은 과장이었다 — 기존 테스트는 회귀 방어이지 정답지가 아니다.

### 9.2 추가 완화책 — 순환을 실제로 줄이는 것들

**A. Red-green 전제조건 (결정론적, 자동)**

생성된 acceptance test는 **변경 전 baseline에서 반드시 실패해야** 판정자로 채택된다. baseline에서 이미 통과하는 테스트는 요청받은 변경을 전혀 검사하지 않는다는 뜻이다.

```
생성된 테스트 T가 판정자로 admissible ⟺ T가 baseline에서 fail AND 최소 1개 후보에서 pass
```

이건 LLM 판단이 아니라 **실행 결과로 자동 판별**된다. 공허한 테스트(항상 통과), 이미 동작하는 기능을 테스트하는 것, 요청과 무관한 테스트를 대량으로 걸러낸다. 비용은 baseline 1회 추가 실행뿐이다.

**한계:** "baseline에서 실패하지만 *틀린* 요구사항을 인코딩한 테스트"는 통과시킨다. 예를 들어 사용자가 "페이지당 pageSize개"를 요청했는데 생성기가 `pageSize + 1`을 단언하면, 그 테스트는 baseline에서 실패하고(red-green 통과) 틀린 구현을 선택하게 만든다.

**B. 후보 간 차분 테스트 (오라클이 필요 없다)**

Arena의 가장 강력한 미사용 자산: **N개의 독립 구현이 이미 존재한다는 사실 자체.**

- 입력을 생성해 모든 후보를 실행하고 결과를 비교한다.
- **핵심: 올바른 *기대 출력*을 생성하는 것보다 *입력*을 생성하는 것이 훨씬 쉽다.** 정답을 몰라도 탐침은 만들 수 있다 — 여기서 순환이 끊긴다.
- 후보들이 모든 탐침에서 **일치**하면 선택의 중요도가 낮다.
- **불일치**하면 그 입력이 정확히 사용자가 답해야 할 의미론적 분기점이다.

이게 2번(사용자 승인)의 인지 비용 문제를 근본적으로 바꾼다. "이 테스트들이 요구사항을 옳게 표현했는지 검토하세요"(어렵고 지루함) 대신 **"입력이 `[0,1,2,...9]`, pageSize=3일 때 결과가 `[0,1,2]`여야 합니까 `[0,1,2,3]`이어야 합니까?"**(즉답 가능)로 질문이 바뀐다.

그리고 이건 제품의 핵심 테마("불일치를 숨기지 않고 보여준다")와 정확히 같은 구조다 — 모델 *의견*의 불일치가 아니라 모델 *산출물의 실제 동작* 불일치라는 점에서 오히려 더 강한 증거다.

**한계:** 호출 가능하고 결정론적인 인터페이스에만 적용된다(UI 변경, 설정, 부수효과 코드엔 어려움). 그리고 **후보들이 같은 방식으로 함께 틀릴 수 있다** — 특히 전부 LLM이고 학습 데이터가 겹치므로 상관된 오류가 실재한다. **일치는 약한 증거이고 불일치가 강한 증거**라는 비대칭을 UI에서도 지켜야 한다.

**C. 테스트 생성의 독립성 (Blind Review와 같은 원리)**

acceptance criteria는 **어떤 후보 구현도 보기 전에**, 요구사항과 baseline 코드만으로 생성한다. 후보를 본 뒤 생성하면 생성기가 특정 구현 쪽으로 anchoring되어, "테스트가 후보를 판정"이 아니라 "후보가 테스트를 결정"하는 역전이 일어난다.

4절 Blind Review가 *검수자*의 anchoring을 다뤘다면, 이건 *판정 기준*의 anchoring을 다룬다. 같은 병에 대한 같은 처방이다.

### 9.2.1 차분 테스트의 입력 생성 — 무엇을, 어디에, 어떻게 (M4 설계 확정)

15절 항목 "차분 테스트(9.2-B)의 입력 생성 전략 — property-based / fuzzing / LLM 생성 중 무엇을,
어떤 타입 시그니처에서 자동 적용할지"의 답이다.

#### 문항이 셋 중 하나를 고르라고 했지만, 먼저 가를 것은 다른 축이다

**LLM 생성을 배제하는 이유는 순환이 아니다.** 9.2-B의 핵심은 *"정답을 몰라도 탐침은 만들 수
있다"* 인데, 그 말대로 **입력에는 옳고 그름이 없다.** 순환은 *기대 출력*을 만들 때 생기지
입력을 만들 때 생기지 않으므로, LLM이 입력을 만든다고 9절의 순환이 되살아나지는 않는다.

배제하는 이유는 **재현성**이다. 모델이 만든 탐침은 다시 돌릴 때 달라지고, 그러면 "후보 A와 B가
여기서 갈렸다"는 관측이 재현되지 않는다. 21절이 재현 러너에 들인 규율(기록된 것으로 다시
돌린다)이 그대로 걸린다. **다만 완전 배제는 아니다**: 모델이 만든 탐침도 **기록해서 재생
가능하면** 쓸 수 있다 — 그때 그것은 "생성기"가 아니라 **말뭉치(corpus)** 이고, 아래 순서에서
마지막에 온다.

#### 1순위는 shrinking이다 — 그래서 property-based

이 기능의 값어치는 불일치를 **찾는 것**이 아니라 **사용자에게 물을 수 있는 크기로 줄이는
것**이다. 9.2-B가 약속한 질문은 이렇게 생겼다:

> "입력이 `[0,1,2,…,9]`, pageSize=3일 때 결과가 `[0,1,2]`여야 합니까 `[0,1,2,3]`이어야 합니까?"

원소 200개짜리 무작위 배열에서 갈렸다면 **그 질문을 할 수 없다.** 즉 최소 반례로 줄이는 능력이
없으면 탐침은 "갈렸다"만 말하고 카드를 만들지 못한다.

그러므로 우선순위는 **property-based > fuzzing > 기록된 LLM 말뭉치**다.

- **property-based**: 타입별 생성기 + shrinking. 우리가 쓰는 것은 그 라이브러리의 **생성기
  절반**뿐이다 — 판정(property)은 후보 간 비교가 하므로 우리가 적을 명제가 없다. 이 구별이
  중요하다: property를 적기 시작하면 그게 곧 오라클이고, 9절의 순환이 그 자리에서 되돌아온다.
- **fuzzing**: 바이트 단위 변형이라 타입 있는 API에서 대부분 유효하지 않은 입력을 만들고,
  shrinking도 의미 단위가 아니다. **파서·직렬화기처럼 입력이 바이트열인 함수에만** 쓴다.
- **기록된 LLM 말뭉치**: 도메인 지식이 필요한 씨앗값(예: 실제 타임존 이름, 통화 코드)을 얻는
  데만 쓰고, **생성된 값 목록을 그대로 저장**해 이후 실행은 그 목록을 재생한다.

#### 어떤 시그니처에 자동 적용하는가 — 타입으로 좁히고 관측으로 확인한다

자동 적용 조건 넷이며, **앞의 둘은 타입이 말하고 뒤의 둘은 실행이 말한다.**

1. **인자와 반환이 직렬화 가능하다.** 비교하려면 값으로 찍어야 하고, 재현하려면 기록해야 한다.
   함수·클래스 인스턴스·핸들을 받는 시그니처는 대상이 아니다.
2. **후보들이 같은 시그니처를 노출한다.** 두 초안이 이름이나 인자 수를 다르게 바꿨으면 비교
   대상이 아니다 — 그건 더 큰 불일치이고 구조적 대조(17절)가 이미 잡는다.
3. **결정론적이다.** 타입은 이걸 말해주지 않는다. 그래서 **같은 입력으로 두 번 부른다** —
   결과가 다르면 그 함수는 대상에서 뺀다. 추측이 아니라 관측이고, 비용은 호출 한 번이다.
4. **부수효과가 없다.** 이것도 타입이 말하지 않지만 **우리는 이미 알 수 있다**: 탐침 실행이
   Policy Gate를 지나므로, 그 실행 중에 파일·네트워크·명령 요청이 있었으면 그 함수는 순수하지
   않다. 게이트가 이미 보고 있는 사실을 판정에 쓰는 것이지 새 장치를 만드는 것이 아니다.

**언어 범위는 TypeScript/JavaScript부터.** Rust는 `proptest`를 태스크 저장소의 빌드에 끼워
넣어야 하고 그 비용이 크다. 8.5절이 IDE에서 쓴 것과 같은 이유다 — 계약을 첫 소비자에서
안정시킨 뒤 두 번째로 간다.

#### 되돌리기 비싼 결정: 탐침 실행기를 따로 만들지 않는다

차분 테스트는 **모델이 쓴 코드를 실행하는 일**이다. 그건 `run_command`가 하는 일과 같은
등급이므로, 별도 실행 경로를 만들면 **모델이 쓴 코드를 실행하는 방법이 둘**이 되고 그중 약한
쪽이 실제 샌드박스가 된다. 탐침은 검증 러너와 **같은 경로**로 돈다 — Rust, Policy Gate,
타임아웃, Job Object(20절).

그리고 **탐침은 검증과 동시에 돌리지 않는다.** 11.2절 ③과 같은 논리다: 같은 머신에서 경합하면
타임아웃이 늘고, 타임아웃은 `TIMED_OUT`이라는 **판정**이 된다. 판정자가 옆 프로세스의 부하에
흔들리면 안 된다.

상한은 달러가 아니라 **시간**이다. 탐침은 모델 호출이 아니므로 예산 원장이 막지 않는다 —
막는 것이 없으면 무한히 돈다.

#### 하지 않는 것

- **property(명제)를 적지 않는다.** 적는 순간 그것이 오라클이고 9절 순환이 돌아온다.
- 부수효과 있는 함수·UI·설정에 적용하지 않는다(9.2-B가 이미 적은 한계).
- **일치를 검증으로 표시하지 않는다.** 모든 탐침에서 같았다는 것은 "선택의 중요도가 낮다"이지
  "옳다"가 아니다 — 후보들이 같은 방식으로 틀릴 수 있고(상관된 오류), 그 비대칭은 UI에서도
  지켜야 한다.

### 9.2.2 Arena의 결합(merge) — 초기에는 선택만 지원한다

15절 항목 "Arena의 구현 결합(merge) 전략 — '최적 선택'은 명확하나 '결합'은 훨씬 어려움. 초기엔
선택만 지원할지"의 답이다. **초기에는 선택만 한다.** 근거는 난이도가 아니라 9.3절이다.

결합 결과는 **어느 후보도 만들지 않은 산출물**이다. 그러므로:

- 각 후보가 쌓은 증거(테스트를 돌려 통과했다)를 **하나도 물려받지 못한다.** 후보 B가 검증을
  통과했다는 사실은 B에 대한 사실이지 "B의 절반 + C의 절반"에 대한 사실이 아니다.
- 즉 결합본은 **오라클 강도 표(9.3절)에서 한 칸 아래로 떨어진다.** 강한 오라클(기존 테스트)이
  있어도 그 테스트는 결합본에 대해 새로 돌려야 하고, 결합이 만든 새 경로를 그 테스트가 덮는지는
  아무도 모른다.
- 그리고 **결합 자체가 오라클 없는 모델 행위**다. 후보를 고르는 것은 결정론적 근거(테스트 결과)로
  할 수 있지만, 두 구현을 합치는 것은 새 코드를 쓰는 일이다.

그래서 순서가 정해진다: Arena가 **선택**으로 값어치를 증명하고 14절의 "생성된 테스트가 틀렸던
비율"이 낮게 나온 **뒤에야** 결합을 논의한다. 그전에 결합을 넣으면 9절이 경고한 "검증 없는 것보다
나쁜" 상태를 가장 큰 규모로 만든다.

**결합을 영영 안 한다는 뜻은 아니다.** 다만 그때의 결합은 "합쳐서 내놓는다"가 아니라 **"합친 뒤
전체를 다시 검증하고, 어느 후보의 증거도 물려받지 않았다고 표시한다"**여야 한다.

### 9.3 구조적 결론: 오라클 강도가 Arena의 주장 강도를 제한한다

완화책을 아무리 쌓아도 **Arena는 저장소에 존재하지 않는 검증 권위를 만들어낼 수 없다.** 따라서 올바른 설계는 "안전해질 때까지 완화책을 추가"가 아니라 **"Arena의 주장을 오라클 강도에 종속시키기"**다.

| 오라클 강도 | 조건 | Arena가 주장할 수 있는 것 |
|---|---|---|
| **강함** | 변경 영역을 실제로 커버하는 기존 테스트 존재 | "후보 B가 검증을 통과했다" — 판정 |
| **보통** | 생성 테스트가 red-green 통과 + 사용자 승인 + 차분 테스트에서 후보 간 불일치 해소됨 | "후보 B가 **승인된 기준**을 만족한다" — 기준의 출처를 반드시 명시 |
| **약함** | 관련 기존 테스트 없음, 차분 테스트 적용 불가 | **판정하지 않는다.** "회귀 없음이 확인된 후보 3개"를 제시하고 선택은 사용자에게 — 순위 보조 도구이지 판정자가 아님 |

**"Tomverse Verified" 배지는 오라클 강도를 반드시 표기한다**(11절 배지 규칙의 연장). 약한 오라클에서 나온 Arena 결과에 강한 오라클과 같은 배지를 붙이면, 그것이 바로 9절 서두에서 경고한 "검증 없는 것보다 나쁜" 상태다.

### 9.4 이 위험의 현재 상태

**해소되지 않았다. 경계가 그어졌을 뿐이다.**

- 순환 의존은 원리적으로 제거 불가능하다 — 새 동작에 대한 정답지가 저장소에 없으면 어디선가 만들어야 하고, 그 출처는 LLM 아니면 사람이다.
- 9.2의 A·B·C는 순환의 **크기**를 줄이고, 9.3은 그 잔여 위험이 **과대 주장으로 이어지지 않게** 막는다.
- 실제로 충분한지는 **M4에서 Arena를 만들어 14절의 "생성된 테스트가 틀렸던 비율"을 측정해야 알 수 있다.** 그 값이 높으면 Arena는 `critical` tier에서도 판정자가 아니라 순위 보조로 격하되어야 한다.

이 항목은 15절 미해결에 남긴다.

## 10. 위험: 경쟁사 기능 주장은 검증 후 반영

전략 문서는 Copilot의 구체적 기능(Fleet 모드, Rubber Duck 비평 에이전트, 커스텀 에이전트 자동 위임 등)을 사실로 전제하고 "그러므로 우리도 X가 필요하다"고 전개한다.

**우리는 이 주장들을 독립적으로 검증하지 않았고, 이 문서를 작성한 시점의 지식에도 한계가 있다.** "경쟁사가 X를 가졌으니 우리도"라는 형태의 로드맵 항목은 X가 부정확하면 통째로 잘못된 투자가 된다.

다만 **방향성 결론(기능 개수가 아니라 검증 신뢰성으로 차별화)은 경쟁사 세부 기능의 정확성과 무관하게 타당하다.** 따라서:
- 방향성은 지금 채택한다.
- "Copilot이 이미 X를 한다"에 근거한 개별 기능 항목은 **실제 제품을 확인한 뒤** 로드맵에 넣는다.
- 8절이 "Copilot 기능 전체 커버"를 명제로 삼은 이상 이 위험은 더 커졌다 — **커버 목록의 근거가 부정확하면 없는 기능을 쫓게 된다.** 8.2 표의 각 항목은 실제 제품에서 확인한 뒤 확정한다.

## 11. "Tomverse Verified" 배지의 의미론적 제약

배지는 마케팅 자산인 동시에 **책임 발생 지점**이다. "Verified"라고 찍은 변경이 프로덕션을 깨뜨리면, 이는 "제안입니다"보다 훨씬 강한 약속을 어긴 것이다.

**배지는 "이 코드가 옳다"가 아니라 "어떤 검사가 실행되어 통과했다"만 인증한다.** 전략 문서의 예시가 이미 옳은 방향을 보여준다:

```
Tomverse Verified
✓ Build          ✓ 128 tests      ✓ Type check
✓ Security scan  ✓ Independent model review
△ Performance test not configured     ← 실행하지 않은 것을 반드시 명시
```

규칙:
- **실행하지 않은 검사는 침묵하지 않고 명시한다.** 없는 항목을 숨기면 완결성을 암시하게 된다.
- 테스트 커버리지가 낮은 저장소에서는 "128 tests 통과"가 주는 인상을 조정해야 한다(변경된 코드를 실제로 커버하는 테스트가 몇 개인지가 진짜 정보다).
- 검수 모델이 통과시켰다는 사실은 결정론적 검사와 **동급으로 표시하지 않는다** — 4절 판정 우선순위가 UI에도 반영돼야 한다.

### 11.1 배지는 산출물의 종류가 아니라 **판정의 출처**를 말한다

16.5절 마지막 항목은 *"산출물이 코드가 아니면 결과 판정자가 없다 — 명세·설계 문서를 산출하는
경우 '이 결과는 사용자 확인에만 근거함'을 명시해야 한다"* 였고, 12절 미해결에는 그 **문구를
정하는 일**로 남아 있었다.

구현하려고 보니 문구가 아니라 축이 문제였다. **"문서 태스크용 배지"를 만들면 두 가지가
어긋난다.**

1. 태스크가 문서 산출인지 **판정해야 한다.** 또 하나의 추측이고, 틀리면 배지가 틀린다.
2. 더 중요하게, **같은 처지의 코드 태스크를 놓친다.** 테스트 스크립트가 없는 저장소에서 코드를
   고친 태스크는 명세를 쓴 태스크와 인식론적으로 **정확히 같은 자리**에 있다 — `VERIFYING`이
   침묵했고 결과를 뒷받침하는 것은 사용자 확인뿐이다. 산출물 종류로 가르면 그쪽은 "코드
   태스크니까"라는 이유로 검증된 것처럼 읽힌다.

그래서 축을 바꿨다. 배지는 **무엇이 이 결과를 뒷받침하는가**를 말한다. 네 값이며 계산은
화면 밖 순수 함수에 있다(`apps/desktop/src/lib/resultBasis.ts`).

| 값 | 뜻 | 통과 톤(초록) |
|---|---|---|
| `deterministic_pass` | build/test/lint가 **실제로 실행되어** 통과했다 | 예 |
| `deterministic_fail` | 실행된 검증 중 실패가 있다 | 아니오 |
| `user_only` | 검증이 침묵했고 **사용자가 확정한 기준**만 있다 | 아니오 |
| `nothing` | 검증도 침묵하고 사용자 확정 기준도 없다 | 아니오 |

문서 태스크는 이 규칙의 한 사례가 되고 따로 다룰 것이 없어진다.

**모델이 적은 기준은 `user_only`의 근거가 아니다.** `draft_proposal` 출처의 완료 기준을 세면
모델이 자기 산출물을 자기가 승인한 것을 근거로 내놓게 된다 — 4절 원칙이 검수자에 대해 막는
것과 같은 종류의 자기 승인이다.

**검수 모델의 판정은 이 계산에 아예 들어가지 않는다.** 이 절의 세 번째 규칙("검수 모델이
통과시켰다는 사실은 결정론적 검사와 동급으로 표시하지 않는다")을 주석이 아니라 **입력 타입의
부재**로 표현했다. 필드를 두고 "쓰지 않는다"고 적으면 언젠가 누군가 쓴다.

#### `not_verified`를 둘로 갈랐다 — 없는 문제를 고치러 보내고 있었다

이 작업이 드러낸 별개의 결함이다. `VerificationReport.overall`의 `not_verified` 하나에 성질이
다른 두 상황이 뭉쳐 있었다.

- 프로젝트에 돌릴 명령이 **아예 없다**
- 돌리려 했는데 **돌지 못했다**(`SKIPPED_WITH_REASON` — 정책 거부, 또는 Windows에서 `npm`이
  `npm.cmd`라 실행에 실패하는 결함)

그런데 화면 라벨과 완료 요약은 **언제나 전자를 단정**했다: *"이 프로젝트에서 실행할 수 있는
검증 명령이 없어 검증되지 않았습니다. build/test/lint 스크립트를 추가하면 다음부터 자동으로
검증됩니다."* 후자의 사용자에게 그 프로젝트에는 스크립트가 **있다.** 원인을 잘못 짚은 안내는
침묵보다 나쁘다 — 사용자가 없는 문제를 고치러 간다.

`VerificationStatus`를 3값에서 5값으로 가른 것과 같은 이유이며, 그때 **종합 판정 쪽에는 같은
규율을 주지 않았던 것**을 맞췄다. 배지 색은 둘 다 경고로 같다: 원인이 달라도 결정론적 근거가
없다는 점은 같고, 색으로 등급을 나누면 한쪽이 덜 심각해 보인다.

## 12. Windows 특화 — 해자이되, 위치를 정확히 짚어야 한다

### 12.1 우리가 직접 겪은 마찰 (1차 증거)

Tomverse Code를 개발하면서 이 환경에서 실제로 발생한 것:

- Rust 설치 후 winget이 PATH를 갱신하지 않아 기존 셸에서 `cargo`를 못 찾음
- MSVC 링커 부재로 Rust 컴파일 실패 → VS Build Tools 설치 → **winget이 exit 0을 반환했는데도 설치가 불완전해 Windows SDK 누락**(`vswhere -property isComplete` = 0) → `vs_installer.exe modify`로 복구
- `vcvarsall.bat` 환경 없이는 `cargo build`가 링크 단계에서 실패
- Bash→cmd.exe 경유 시 경로 인용이 깨져 `.bat` 래퍼가 필요했음
- **Git for Windows의 GNU `link.exe`(하드링크 유틸리티)가 PATH에서 MSVC `link.exe`를 가림.** 실제 오류는 `link: extra operand ... Try 'link --help'`였는데, 이건 MSVC 링커가 아니라 **coreutils가 낸 메시지**다. rustc는 "Visual Studio 설치 프로그램에서 C++ 빌드 도구를 선택하세요"라는 일반 힌트를 붙였고, 이 힌트는 부분적으로만 맞았다 — 툴체인 부재와 PATH 가림이 **동시에** 발생해 오류가 이중으로 오도했다.

### 12.2 경쟁 제품은 이걸 어떻게 다루는가 (검증)

10절의 원칙("경쟁사 주장은 검증 후 반영")을 이 절에도 적용해 확인한 결과, **어느 쪽도 "해결"하지 않는다.** 관찰되는 전략은 세 가지다.

**(a) Linux로 탈출한다.** Codex CLI는 Windows 네이티브 지원이 2026년 초 기준 여전히 experimental로 표기되고, 프로덕션 용도로는 WSL2가 권장된다 — 그 이유가 중요하다: **모델이 주로 학습된 환경이 Linux이기 때문**이다. 클라우드/컨테이너 실행도 같은 계열의 회피책이다. 이건 유효한 전략이지만 **.NET·WinUI·WPF·MSVC로 Windows 네이티브 앱을 만드는 개발자에게는 선택지가 아니다.** 문제를 푸는 게 아니라 문제가 없는 곳으로 옮기는 것이다.

**(b) 범용 에이전시로 그때그때 디버깅한다.** 이번 세션의 Claude Code(즉 이 문서를 쓰는 나)가 실제로 한 방식이다. 사전 점검은 전혀 없었고, **빌드를 실패시킨 뒤 오류를 읽고 조사해서** 하나씩 풀었다. 작동은 하지만 대가가 있다: 실패한 빌드 여러 번, 토큰과 시간, 그리고 **세션마다 재발견**한다.

**(c) 해결 부담을 사용자에게 넘긴다.** 커뮤니티의 실전 조언이 이를 잘 보여준다 — "Visual Studio를 설치하고 **Claude에게 Windows 빌드는 항상 그걸 쓰라고 말하라, 안 그러면 MinGW-w64로 기본 동작해서 엉망이 된다**", "빌드 문제 대부분은 경로 문제이니 **모든 게 어디 있는지 Claude에게 가르쳐라**". 제품화된 형태가 `CLAUDE.md`/`AGENTS.md`다. 실효성은 있지만 **이건 제품의 노동이 아니라 사용자의 노동**이고, 발견 비용은 사용자가 먼저 치른다.

**(b)와 (c)를 우리가 이 세션에서 정확히 그대로 했다** — 실패로 발견한 뒤(b), 재발 방지를 위해 CLAUDE.md에 적어넣었다(c).

### 12.3 그래서 해자는 어디에 있는가 (좁히고 날카롭게)

**"경쟁 제품은 못 한다"는 과장이다.** 방금 내가 해냈다. 정확한 차이는 능력이 아니라 다음 셋이다.

**① 사전 점검 vs 사후 부검.** 나는 VS 설치가 불완전하다는 걸 **두 번의 빌드 실패 후에** `vswhere -property isComplete`로 알아냈다. Windows 전용 제품이라면 **첫 빌드 시도 전에** 그 명령을 돌린다. 같은 정보, 완전히 다른 사용자 경험.

**② 1회성 설정 비용이 아니라 명령마다 붙는 세금.** 이게 더 강한 근거다. 설정은 한 번이지만, **PATH 가림·셸 인용·개발자 환경 부재는 에이전트가 실행하는 모든 명령에 영향을 준다.** 12.1의 `link.exe` 사건은 설정 문제가 아니라 *명령 실행 계층* 문제였고, 파일 잠금·긴 경로·PowerShell vs cmd vs bash 인용도 전부 같은 계층에서 반복 발생한다.

**③ 모델 자체의 prior가 Unix로 기울어 있다.** Codex가 WSL2를 권하는 이유가 학습 환경이고, Claude Code가 "그냥 두면 MinGW로 간다"는 커뮤니티 조언도 같은 현상이다. **나 역시 이 세션에서 반사적으로 Bash를 먼저 잡았고**, 그 결과 Git for Windows의 GNU `link`에 물렸다. 이건 프롬프트로 완전히 교정되지 않는 종류의 편향이므로, **런타임에서 구조적으로 강제**(명령 실행 전 개발자 환경 해석, Windows 네이티브 도구 우선)해야 교정된다 — 그리고 그런 강제는 Windows만 지원하는 제품이 훨씬 부담 없이 넣는다.

### 12.4 이 해자의 크기를 과장하지 않기

정직하게 좁히면:

- 해자는 **"Windows 개발 경험 전반"이 아니라 "환경 해석과 명령 실행 계층"에 집중**돼 있다. 코드 생성 품질 자체가 Windows에서 더 좋아지는 게 아니다.
- **툴체인이 이미 잘 갖춰진 사용자는 ①의 이득을 거의 못 느낀다.** 온보딩·신규 머신·프로젝트 전환에서 주로 드러난다.
- 반면 ②는 숙련 사용자에게도 계속 발생하므로 **지속적인 차별화 지점은 ②와 ③**이다.

따라서 투자 우선순위도 여기에 맞춘다: **명령 실행 계층 먼저, 설정 마법사는 나중.**

우선순위: **개발자 환경 자동 해석 후 명령 실행**(vcvarsall 상당, MSVC/GNU 도구 충돌 해소) → PowerShell 명령 의미 분석 → Visual Studio/MSBuild·SDK 사전 점검(`vswhere isComplete` 등) → 파일 잠금·긴 경로 처리 → Windows Credential Manager(이미 설계됨) → 관리자 권한 분리(이미 Policy Gate deny 규칙에 있음).

## 14. 북극성 지표와 계측

**북극성: 검증을 통과하고 사용자가 승인한 작업 한 건당 비용과 시간.**

이 지표를 채택하는 이유는 그것이 "좋아 보인다"가 아니라 **결정론적으로 관측 가능**하고, 우리 이벤트 로그가 이미 필요한 데이터를 전부 갖고 있기 때문이다(`VERIFYING` 결과 + 승인 이벤트 + 비용·시간).

보조 지표 — **M0부터 전부 기록한다**(나중에 붙이면 몇 달의 데이터를 잃는다):

| 지표 | 출처 |
|---|---|
| 첫 시도 테스트 통과율 | `verification_reports.attempt_number = 0` |
| 사용자 승인율 / 거부율 | `APPROVAL_GRANTED` / `APPROVAL_DENIED` |
| 되돌리기 비율 | 롤백 `ToolRequest` 발생 |
| 작업당 비용·green까지 시간 | 이벤트 타임스탬프 + 토큰 사용량 |
| **검수가 patch를 실제로 바꾼 비율** | `REVIEW_RECEIVED`의 `revisionChangedThePatch` (`metrics`의 `reviewerFindings`). **아래 14.2절 — 원래 여기 있던 두 지표를 대신한다** |
| **blind vs informed 판정 불일치율** | 4절 — anchoring 크기의 직접 측정 |
| **생성된 테스트가 틀렸던 비율** | 9절 — Arena 근거의 건전성. **이 값이 Arena를 판정자로 둘지 순위 보조로 격하할지를 결정한다**(9.4) |
| **red-green 전제조건 탈락률** | 9.2-A — 생성 테스트 중 baseline에서 실패하지 못해 기각된 비율. 생성기 품질의 선행 지표 |
| **차분 테스트 불일치 발생률** | 9.2-B — 후보 간 실제 동작이 갈린 빈도. 높으면 태스크가 실제로 모호했다는 뜻 |
| **불일치 1건당 사용자가 뒤집은 비율** | 16.4절 — 불일치가 실제 쟁점이었는지. 낮으면 잡음으로 사용자를 괴롭히는 것 |
| **질문 예산 소진율** | 16.4절 — 상한에 걸려 못 물어본 쟁점 비율. 높으면 상한이나 랭킹 규칙이 틀렸다 |
| **기준↔테스트 연결 커버리지** | `CRITERIA_EVALUATED`의 상태별 비율. **낮은 것이 기본값**이므로, 봐야 하는 것은 값이 아니라 **아래 사유 코드 분포**다 |
| **미확인 사유 분포** | 같은 이벤트의 `code`별 비율. `no_test_reference`가 압도적이면 고칠 곳은 잇는 규칙이 아니라 **기준을 적는 방식**이고, `no_run_evidence`가 많으면 잇는 규칙 쪽이다. 이 둘을 뭉치면 어느 쪽도 고칠 수 없다 |
| **기준 충돌의 결말 분포** | `CRITERIA_CONFLICT_RESOLVED`의 `outcome`별 비율. `plan_changed_to_expected`가 낮으면 재요청이 아무것도 바꾸지 못하는 것이고, 그러면 게이트는 예산만 쓰는 셈이다 |
| 위험 명령 차단률 | Policy Gate `deny` |

**"오탐률"이라는 이름의 지표는 두지 않았다.** 기준 충돌이 진짜 잘못된 계획을 잡았는지의 정답은 어디에도 없다 — 사용자가 매번 판정해주지 않는 한 관측 가능한 것은 "재요청했더니 계획이 바뀌었다/안 바뀌었다"와 "그대로 진행했더니 어떻게 끝났다"뿐이다. 지표 이름이 추론을 포함하면 집계를 읽는 사람이 그 추론을 사실로 읽으므로, **일어난 일 그대로** 이름 붙이고 해석은 읽는 사람에게 맡긴다. (`proceeded_without_change`인데 태스크가 통과했다는 것도 오탐의 *증거*가 아니라 정황이다 — 사용자가 지목한 곳을 고치지 않고도 기존 테스트는 통과한다.)

집계는 `tomverse-host metrics`가 저장된 이벤트에서 계산한다. 읽기 전용이며 아무것도 쓰지 않는다.

**이 문장이 한동안 절반만 참이었다.** 표의 여러 행(첫 시도 통과율, 승인율·거부율, 되돌리기
비율, 위험 명령 차단률)은 **이벤트만 있고 집계가 없었다.** 기록은 M0부터 하고 있었으므로 데이터를
잃지는 않았지만, "실사용이 쌓이면 본다"고 적어둔 값을 정작 볼 방법이 없었다 — `metrics`의
`operational`이 그 넷을 센다. 표에서 아직 집계가 없는 것은 **M4 이후에 생기는 것들뿐**이다
(생성된 테스트가 틀렸던 비율, red-green 탈락률, 차분 불일치율, blind vs informed 불일치율 —
마지막 것은 가설 게이트 하네스에는 있다).

그리고 **"질문 예산 소진율"은 지금 구조에서 언제나 0이다.** 대조가 필드당 쟁점을 하나만 만들고
필드가 셋이라 한 카드가 상한 4를 넘을 수 없기 때문이다(state-machine 17.4.2절). 필드가 늘면
테스트가 실패하며 이 행이 다시 의미를 갖는다.

**지표를 추가하고 읽는 법을 안 붙이는 길은 이제 막혀 있다.** `openQuestions`의 각 항목이 자기가
읽는 집계 이름을 들고 있고, 테스트가 `Metrics`의 모든 키를 훑어 **질문이 읽거나 면제 목록에
이유와 함께 있는지** 확인한다. 종전에는 이 규율이 주석의 경고문이었고, 경고는 잊혔다 —
실제로 예산 여유 배수 집계가 그렇게 빠져 있었다.

굵게 표시한 것들은 **경쟁사가 측정하지 않는 것**이고, 우리 차별화가 실제로 작동하는지 판별하는 핵심이다. 특히 `blind vs informed 불일치율`과 `생성된 테스트가 틀렸던 비율`은 **우리 자신의 전략이 틀렸는지를 알려주는 지표**이므로 반드시 봐야 한다 — 불리한 값이 나올 수 있다는 것이 이 지표들을 두는 이유다.

## 14.2 "검수가 실제 결함을 발견했는가"는 production에서 답할 수 없다

이 표에는 원래 **"검수 모델이 실제 결함을 발견한 비율"**(출처: *검수 지적 항목 중 테스트로
확인된 것*)과 **"잘못된 검수 경고 비율"**(출처: *검수가 지적했으나 검증이 반박한 것*)이 있었고,
15절에는 그 판정 기준을 정하라는 항목이 남아 있었다. 정하려고 보니 **정할 수 없다.** 둘 다
production에서 관측 불가능하고, 관측하려는 시도가 정확히 이 문서가 금지하는 것으로 이어진다.

- **"테스트로 확인된 것"은 이미 막힌 길이다.** 기준↔테스트를 잇는 문제와 같고
  (state-machine-and-protocol.md 17.9절), 그쪽 결론은 **"대부분 이을 수 없다"** 였다.
  같은 규칙을 검수 지적에 적용하면 값은 거의 언제나 0이다. 그리고 0을 피하는 유일한 길은
  모델에게 "이 지적이 실제 결함이었나"를 묻는 것인데, 그건 4절 판정 우선순위가 막는 바로 그 일이다.
- **"검증이 반박했다"는 반사실을 요구한다.** 어떤 지적이 틀렸다고 말하려면 *그 지적을 반영하지
  않은 초안*이 검증을 통과했어야 한다. production은 한 태스크에 한 경로만 태우므로 그 초안의
  결과가 존재하지 않는다.

반사실이 있는 곳은 **게이트 하네스**다: 같은 초안을 Arm A는 검수 없이, Arm C는 검수와 함께
태우므로 oracle 결과만으로 `correction`/`harm`/`no_measurable_correction`/`ineffective`가
결정론적으로 갈린다. 그러므로 이 둘은 **제품 지표가 아니라 실험 지표다.** 표에 남겨두면
"곧 화면에 나올 값"으로 읽히고, 채우려는 압력이 결국 모델 판정을 부른다.

대신 production에서 **실제로 관측되는 것**을 센다(`metrics`의 `reviewerFindings`):

| 세는 것 | 왜 |
|---|---|
| verdict 분포 (마지막 판정 기준) | REVISE 루프를 전부 세면 루프가 많은 태스크가 분포를 좌우한다 |
| REVISE 중 **수정본이 초안과 실제로 달랐던** 수 | 같으면 그 지적은 산문만 남겼다. **"틀린 지적"이라는 뜻이 아니다** — 관측된 것은 patch가 같다는 사실뿐이다 |
| REVISE인데 **수정본이 아예 없던** 수 | `null`을 false로 뭉개면 "바꾸지 않았다"와 "바꿀 기회가 없었다"가 같은 값이 된다 |
| 수정본을 실행한 태스크의 최종 상태 분포 | "검수가 도움이 됐는가"에 답하지 않는다 — 검수 없이 돌린 결과가 없기 때문이다 |

**이름에 추론을 넣지 않았다.** 이 절 서두가 "오탐률이라는 이름의 지표는 두지 않았다"고 적어둔
규율의 연장이며, 여기서는 그 규율이 지표 하나를 통째로 다른 곳으로 옮기게 했다.

이 작업이 **적용된 변경의 출처가 로그에 없던 것**도 함께 드러냈다. REVISE에서는 검수자의
수정본이 초안을 그대로 갈아치우고 실행되는데, `REVIEW_RECEIVED`에는 verdict와 산문만 있었다 —
"왜 이 patch가 적용됐나"에 로그가 답하지 못했다. `DRAFT_RECEIVED`가 `hasPatch`만 남기던 때와
같은 구멍이고, 같은 방식으로 닫았다.

## 14.1 열린 질문은 "언제 답할 수 있는가"까지 값으로 낸다

14절의 지표들과 각 설계 문서의 "실사용 데이터가 쌓이면" 항목들은 공통 문제를 안고 있었다:
**집계는 표본이 3개여도 비율을 낸다.** `no_test_reference 4/5`를 보고 "압도적이다"라고 읽는
순간, 문서가 경계하라고 적어둔 조치로 바로 간다. 관측이 아니라 우연에 따라 설계를 바꾸는 것이다.

유도 문턱들에는 이미 가드가 있었다 — 취소 소요·커밋 크기·태스크 비용은 표본이 최소치에 못
미치면 **유도값을 내지 않고 그 사실을 함께 돌려준다**. 열린 질문들에는 그게 없었다.

이제 `tomverse-host metrics`의 `openQuestions`가 질문마다 넷을 낸다.

| 필드 | 왜 |
|---|---|
| `denominator` | **지표마다 세는 대상이 다르다.** 잘못된 분모로 읽는 것이 표본이 모자란 것보다 나쁘다 — 그쪽은 적어도 틀린 줄 안다 |
| `samples` / `minSamples` | 지금 몇 개이고 몇 개부터 볼 것인가 |
| `readiness` | `insufficient_samples` \| `enough_to_look` |
| `actOn` | 답이 나오면 **어디를 고치는가.** 이게 없으면 관측이 결정으로 이어지지 않는다 |

**`ready`가 아니라 `enough_to_look`인 이유**: 최소치를 넘었다는 것은 "답이 믿을 만하다"가
아니라 "이제 들여다볼 값이 있다"는 뜻이다. `ready`라고 부르면 그 숫자가 확정된 답처럼 읽히고,
그건 이 가드가 막으려던 것과 같은 착시다.

최소치 30은 **유도하지 못한 상수다.** 유도 문턱들이 쓰는 10보다 크게 잡은 이유는 재는 것이
다르기 때문이다 — 그쪽은 분포의 백분위이고 여기는 비율이라, 10건에서는 한 건이 10%를 움직인다.

- ~~`critical` tier에서 Arena 실행 비용을 사용자가 사전에 승인하는 UX (3개 구현 = 3배 비용)~~ → 8.6절에서 해결. **Arena를 기다릴 필요가 없는 문제였다**: `verified`가 이미 실행자를 둘 부르는데 모드 이름이 그걸 말하지 않았고, 예산 점검은 **한 호출**만 봐서 상한이 한 번은 되고 세 번은 안 되는 값이면 돈을 쓰고 도중에 멈췄다. **별도 승인 모달을 만들지 않는다** — 승인이 둘이 되고 원칙 6이 비용 축에서 깨진다. 모드를 고르는 자리에 **사실 두 개**(이 모드의 호출 수 범위 / 상한으로 부를 수 있는 횟수)를 나란히 놓고, "모자랄 수 있습니다" 같은 예측은 하지 않는다. Arena는 같은 자리에 배수 하나를 더할 뿐이다
- ~~검수 모델의 지적을 "실제 결함"으로 판정하는 자동 기준 (14절 지표의 전제)~~ → 14.2절에서 해결. **답은 "기준을 정할 수 없다"였고, 그게 결함이 아니라 구조다**: "테스트로 확인된 것"은 기준↔테스트 연결과 같은 막힌 길이고(17.9절), "검증이 반박했다"는 그 지적을 반영하지 않은 초안의 결과 — 즉 **반사실** — 을 요구하는데 production은 한 태스크에 한 경로만 태운다. 반사실이 있는 곳은 게이트 하네스(Arm A vs Arm C, 같은 초안)이므로 두 지표를 **실험 지표로 옮겼다.** 제품에서는 관측되는 것만 센다(`reviewerFindings`). 곁가지로 **검수자의 수정본이 이벤트에 남지 않던 것**을 닫았다 — REVISE에서 적용되는 patch의 출처가 로그에 없었다
- ~~IDE 연동 범위 (VS Code / Visual Studio) 및 데스크톱 앱과의 역할 분담~~ → 8.5절과 [process-architecture.md 13절](./process-architecture.md)에서 해결. **"범위"를 기능 목록으로 물으면 되돌리기 비싼 결정을 놓친다** — 정한 것은 (a) 확장은 UI와 같은 신뢰 등급이고 키도 게이트도 갖지 않는다, (b) 코어는 워크스페이스당 하나이므로 확장은 **붙고 띄우지 않는다**(둘이면 11.5절이 고친 승인 결함이 되살아난다), (c) **승인과 판정은 데스크톱 앱에 남는다** — 원칙 6의 보장은 그것을 그리는 프로세스의 신뢰도를 넘지 못한다, (d) 순서는 VS Code → Visual Studio이며 근거는 수요가 아니라 **계약을 증명하는 비용**, (e) 시점은 v1 이후. 남은 것: 파이프 프로토콜의 구체적 메시지 목록은 확장을 실제로 만들 때 정한다 — 그때까지 정해두면 소비자 없이 굳는다
- **불일치 심각도 랭킹 규칙**(16.3) — ~~쟁점이 질문 예산보다 많을 때 무엇을 먼저 묻는가~~ **그 상황은 발생하지 않는다**: 대조는 필드당 쟁점을 하나만 만들고 판정 가능한 필드가 3개라 상한 4를 넘을 수 없다([state-machine-and-protocol.md 17.4.2절](./state-machine-and-protocol.md)). 랭킹이 실제로 하는 일은 **카드 안의 자리 순서**뿐이고, 그건 자리 편향(아래쪽 질문이 대충 눌리는가)을 통해 답의 품질에 영향을 준다. 그래서 남은 질문은 "무엇을 먼저 버릴까"가 아니라 **"먼저 물은 것이 더 잘 판정되는가"**이며, `metrics`의 `byFieldAndPosition`이 그 결합 분포를 낸다 — 주변 분포 둘로는 필드와 자리가 교락되어 가를 수 없었다. **비율 자체는 실사용 데이터 대기.** 필드가 늘어 상한을 넘기면 원래 문항이 테스트 실패와 함께 자동으로 다시 열린다
- ~~**co-executor를 어느 tier부터 켤 것인가**(16.5) — 비용 2배를 정당화할 임계~~ → [state-machine-and-protocol.md 17.5절](./state-machine-and-protocol.md)에서 해결. **문항이 tier를 물었는데 답은 tier가 아니었다**: `standard` tier는 사용자가 `verified`를 고른 경우와 `fast`인데 TRIAGE가 그렇게 분류한 경우 **둘 다**에서 나오고, 구현은 tier만 보고 있어서 **`fast` 모드에서도 executor를 두 번 부르고 있었다** — 16.5절이 "`fast`에서 켜지면 비용 절감이 통째로 사라진다"고 못박은 그 상황이다. 이제 tier가 `standard`이고 **동시에** 실행 모드가 `verified`일 때만 켠다: 규칙이 켜는 것(교차검증)과 사용자가 켜는 것(대조)을 갈랐다. 남은 것: **`verified`를 고르는 것이 값어치가 있는가**는 여전히 실측 대상이고, 그게 가설 게이트 G가 재는 값이다
- ~~산출물이 문서인 태스크(명세·설계서)의 배지 표기 문구 — 16.5의 마지막 항목. 11절 배지 규칙과 통합 필요~~ → 11.1절에서 해결. 통합하려고 보니 **문구가 아니라 축이 문제였다**: 배지는 산출물의 종류가 아니라 **무엇이 이 결과를 뒷받침하는가**를 말해야 하고, 그러면 문서 태스크는 별도 사례가 아니게 된다. 곁가지로 `VerificationReport.overall`의 `not_verified`가 "명령이 없음"과 "돌리지 못함"을 뭉치고 있었고 안내가 언제나 전자를 단정하던 것을 함께 갈랐다 — 스크립트가 있는 사용자를 없는 문제로 보내고 있었다. 남은 것: **배지의 시각 처리는 여전히 M0 최소 스타일이다**(5절 별도 패스)

## 16. 판정 권위의 계층 — 무엇을 누가 판정하는가

9.3절은 "오라클 강도가 Arena의 주장 강도를 제한한다"로 끝났다. 그런데 그 절은 **오라클을 저장소 안에서만 찾았다** — 기존 테스트, 생성된 테스트, 차분 테스트. 사용자를 오라클로 세는 것을 빠뜨렸고, 그 누락 때문에 "설계·요구 분석 단계에는 판정자가 없다"는 잘못된 결론이 나올 뻔했다. 판정자는 있다. **요구에 관한 한 사용자의 답이 정의상 정답이며, 그건 테스트보다 상위의 권위다.**

이 절은 그 권위들을 정리하고, 그 결과 **모델 간 합의를 만들려는 설계를 기각**한 근거를 남긴다.

### 16.1 세 개의 권위와 그 관할

| 권위 | 무엇에 대해 최종적인가 | 무엇에 대해 침묵하는가 |
|---|---|---|
| **사용자** | **의도** — "내가 원한 것이 무엇인가". 반박 불가 | **결과** — 그 의도가 실제로 구현됐는지, 다른 곳을 깨뜨리는지. 사용자는 자기가 읽지 않은 코드에 대해 답할 수 없다 |
| **결정론적 검증** (build/test/lint) | **결과** — 회귀 여부, 통과/실패 | **의도** — 기존 테스트는 정의상 *기존* 동작만 인코딩한다(9.1 표). 새 요구에 대해서는 말할 것이 없다 |
| **모델** | **아무것도 판정하지 않는다** | — |

세 번째 행이 이 절의 핵심이다. **모델은 판정자가 아니라 쟁점 발굴기다.** 모델의 산출물은 후보이고, 모델 *간의 불일치*는 증거다. 이 위치를 지키면 1번 원칙("결정론적 검증이 모델 의견보다 우선")과 사용자 권위가 충돌하지 않는다 — 둘은 서로 다른 질문을 판정한다.

### 16.2 "사용자에게 물어보면 되지 않나"로 해결되지 않는 것 세 가지

사용자가 최종 판정자라는 사실은 맞지만, 그것만으로 요구 분석의 정확도가 확보되지는 않는다.

**① 질문 생성 문제 — 확신에 찬 오해는 질문을 만들지 않는다.**

사용자가 판정하려면 안건이 올라와야 한다. 현재 `NEED_USER_INPUT`은 모델이 *스스로 모호하다고 느꼈을 때만* 발동한다. 그런데 실제 실패 모드는 모델이 모호함을 느끼는 경우가 아니라 **자신 있게 오해하는 경우**다. 그 경우 질문이 만들어지지 않으므로 사용자는 판정할 기회 자체를 받지 못한 채 "확인받았다"는 절차만 통과한다.

**이것이 교차검증의 새로운(그리고 더 방어 가능한) 존재 이유다.** 두 실행자의 `doneCriteria`가 갈렸다는 것은 모델의 주관적 감지가 아니라 **관측된 모호함**이다. 한 모델만 돌렸다면 영원히 묻지 않았을 질문이 여기서 나온다. 교차검증을 "정답 판정"이 아니라 "질문 생성"에 쓰는 것 — 이 용도는 가설 게이트 G의 결과와 **무관하게** 성립한다(16.4).

**② 확인 편향 — 질문의 형식이 답의 가치를 결정한다.**

9.1의 완화책 2번(사용자 승인)에 이미 적어둔 한계가 그대로 적용된다: 승인 피로, 그리고 "사용자는 그 작업을 하기 싫어서 위임한 것이다."

- ❌ 개방형 확인: "로그인 검증을 이렇게 이해했습니다 — 맞습니까?" → 그럴듯하면 "네"를 누르는 기계가 된다
- ✅ 강제 선택: "빈 문자열 이메일은 통과입니까, 거부입니까?" → 실제 정보가 나온다

이건 9.2-B가 차분 테스트에서 발견한 질문 형식 변환과 **같은 처방**이다. 그리고 강제 선택지는 **두 산출물이 실제로 갈렸을 때만 만들 수 있다** — 단일 모델은 자기가 어디서 갈릴 수 있었는지를 모른다.

**③ 관할 밖 — 사용자는 의도의 오라클이지 결과의 오라클이 아니다.**

"빈 문자열은 거부"라고 답해도, 그 답이 코드베이스 다른 곳을 깨뜨리는지는 사용자도 모른다. 따라서 사용자 확인이 아무리 정확해도 `VERIFYING`은 그대로 남는다(1번 원칙, tier 무관 항상 실행).

### 16.3 채택: 합의를 만들지 않고 불일치를 보존한다

검토 과정에서 "두 모델이 왕복 질의로 일정 수준 이상 합의한 뒤 리뷰어가 재검토"하는 구조를 검토했고, **기각했다.** 근거 두 가지:

1. **왕복은 독립성을 소모한다.** 라운드마다 서로의 출력이 서로의 입력이 되므로, 2라운드째부터 두 모델은 독립 표본이 아니라 하나의 공유 서사를 다듬는 상태가 된다. 5절 검수자 독립성 불변식이 지키려는 것이 정확히 이것이고, 4절이 다룬 anchoring의 N배 버전이다. 리뷰어를 마지막에 세워도 그가 받는 것은 이미 봉합이 끝난 단일 서사다.
2. **합의는 정보를 파괴한다.** 사용자를 판정자로 세우기로 한 이상, 모델끼리 수렴시키면 **사용자에게 올릴 질문이 사라진다.** 두 해석이 가능했다는 사실 자체가 사용자가 봐야 할 정보인데, 합의가 그걸 지운다. 게다가 접은 쪽이 옳았을 가능성은 아무도 검사하지 않는다(가설 게이트의 `minCorrectionToHarmRatio`가 재려는 것이 정확히 그 빈도다).

**채택하는 구조:**

```
독립 산출 2개(서로를 보지 않음)
      ↓
구조적 대조 — DraftProposal의 필드 단위 불일치 추출
      ↓
쟁점을 강제 선택 질문으로 변환 (예산 안에서 심각도 순)
      ↓
사용자 판정  ← 요구에 대한 최종 권위
      ↓
판정을 acceptanceCriteria로 고정 (이벤트 로그에 원문 기록)
      ↓
PLANNING → EXECUTING → VERIFYING(결과 판정) + 리뷰어
```

**리뷰어의 역할이 바뀐다.** "합의문을 한 번 더 검토"가 아니라 **"사용자가 내린 판정이 실제 산출물에 반영됐는지 확인"**이다. 이건 자유 재량 검토보다 훨씬 검증 가능한 역할이고, 리뷰어에게 결정론에 가까운 기준(사용자가 고정한 `acceptanceCriteria`)을 준다.

**4절과 모순되지 않는다.** 4.1절 실측은 "검수자에게 초안 작성자의 설명을 주는 것이 유익하다"(informed 우세)를 보였지, "두 산출물을 하나로 합치라"고 하지 않았다. 정보 공유는 유지하고 판단의 병합만 거부하는 것이다.

프로토콜·상태 머신 반영은 [state-machine-and-protocol.md 17절](./state-machine-and-protocol.md), 역할 배정과 독립성 규칙은 [multi-engine-routing.md 13절](./multi-engine-routing.md), 화면은 [ui-wireframes.md 3.9절](./ui-wireframes.md).

### 16.4 이것은 가설 게이트 G와 다른 질문이다

게이트 G는 "교차검증이 **정확도**를 올리는가"를 묻는다. 이 절의 구조는 "불일치를 **사용자에게 노출**하는 것이 이득인가"를 묻는다. 판정 기준이 다르다:

| | 게이트 G | 불일치 노출 |
|---|---|---|
| 측정 대상 | oracle pass rate, correction/harm 비율 | 질문 1건당 뒤집힌 오해 수, 사용자 왕복 피로 |
| 실패 시 결론 | 교차검증을 판정 용도로 쓰지 않는다 | 불일치를 질문으로 만들지 않는다 |

**게이트 G가 실패해도 이 구조는 살아남는다.** 교차검증을 "누가 옳은지 모델이 판정"이 아니라 "무엇을 물어야 하는지 발굴"로 쓰기 때문이다. 그래서 이 항목은 게이트와 병렬로 진행 가능하며, M1의 "모델 불일치 화면"이 이 결정의 구현체다.

14절 지표에 두 개를 추가한다(아래 표 갱신 반영):
- **불일치 1건당 사용자가 뒤집은 비율** — 불일치가 실제로 의미 있는 쟁점이었는지. 낮으면 우리가 잡음으로 사용자를 괴롭히고 있다는 뜻이다
- **질문 예산 소진율** — `clarificationRounds` 상한에 걸려 못 물어본 쟁점이 있었는가. 높으면 상한이나 랭킹 규칙이 틀렸다

### 16.5 이 결정의 한계 — 과대 주장하지 않기

- **비용이 는다.** 독립 산출 2개는 executor 호출이 2배다. 그래서 게이팅이 필수이며, `fast`에서 켜지면 스파이크가 측정한 비용 절감이 통째로 사라진다. **게이팅의 축은 tier가 아니라 실행 모드다** — 이 절이 쓰인 시점에는 둘이 한 낱말이었지만 지금은 갈라져 있고, tier로만 게이팅하면 `fast` 모드에서도 켜진다(state-machine-and-protocol.md 17.5절).
- **상관된 오류는 잡지 못한다.** 두 모델이 **같은 방식으로** 오해하면 불일치가 생기지 않고 질문도 나오지 않는다. 9.2-B의 비대칭이 그대로 유효하다 — **일치는 약한 증거, 불일치가 강한 증거.** 이 구조는 오해를 줄이지 제거하지 않으며, UI가 "두 모델이 일치했음"을 검증으로 표시해서는 안 된다.
- **사용자가 틀린 답을 줄 수 있다.** 그건 우리가 고칠 수 없는 층위다. 다만 판정이 이벤트 로그에 원문으로 남으므로 나중에 "왜 이렇게 만들었나"를 되짚을 수 있다 — 이게 6절 Agent Trace의 실질적 가치다.
- ~~**산출물이 코드가 아니면 결과 판정자가 없다.**~~ → 11.1절에서 해결. **문항이 축을 잘못 잡고 있었다**: 산출물 종류로 가르면 태스크가 문서인지 판정해야 하고(또 하나의 추측), 무엇보다 **테스트가 없는 저장소의 코드 태스크**를 놓친다 — 그쪽도 정확히 같은 자리에 있다. 배지가 말하는 것을 산출물이 아니라 **판정의 출처**로 바꾸니 문서 태스크가 그 규칙의 한 사례가 되고 따로 다룰 것이 없어졌다. 코드 태스크와 같은 신뢰 수준으로 읽히면 9절 서두가 경고한 "검증 없는 것보다 나쁜" 상태라는 진술은 그대로 유효하다.
