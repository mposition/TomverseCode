# UI 와이어프레임

status: draft
관련: [state-machine-and-protocol.md](./state-machine-and-protocol.md) (TaskPhase, ExecutionPlan, VerificationReport), [context-engine.md](./context-engine.md)

## 1. 설계 목표

- 원 아키텍처 제안서의 UI 요구사항을 화면 단위로 구체화한다: 채팅/스트리밍, 프로젝트·브랜치·세션 선택, 단계 표시(분석→검수→승인→실행→검증), diff 미리보기, 명령 실행 승인, 비용/토큰/소요시간 표시, 실패 시 재시도·롤백.
- **UI 프로세스는 API 키도 셸 실행 권한도 갖지 않는다**(원 제안서 원칙) — 여기서 그리는 모든 화면은 Local Orchestrator가 typed IPC로 밀어주는 상태를 그대로 렌더링할 뿐이며, "승인" 버튼을 눌러도 UI가 직접 뭘 실행하지 않고 승인 이벤트만 오케스트레이터에 전달한다.
- `TaskPhase`(14개, state-machine-and-protocol.md 2절)를 사용자에게 그대로 노출하지 않는다 — 원 제안서가 요구한 5단계(분석→검수→승인→실행→검증)로 압축해서 보여주고, 내부 상세는 개발자 모드/로그에서만 노출한다(2절 매핑 표).
- 와이어프레임은 저해상도(그레이박스, 실제 색상/폰트 없음)로 유지한다 — 레이아웃과 상태 전이를 확정하는 단계이지 비주얼 디자인 단계가 아니다.

## 2. `TaskPhase` → 사용자 노출 5단계 매핑

| 사용자에게 보이는 단계 | 내부 `TaskPhase` | 진행 표시 |
|---|---|---|
| 준비 중 | `CREATED`, `SNAPSHOTTING`, `TRIAGE` | 스피너, 보통 1초 미만이라 깜빡임 방지용 최소 표시시간만 둠 |
| 분석 | `DRAFTING`, `SINGLE_MODEL_FIX` | "OpenAI가 초안 작성 중" 또는 (simple tier면) "Claude가 검토 중" — tier에 따라 라벨이 달라짐 |
| 검수 | `REVIEWING` | "Claude가 독립 검토 중" (SINGLE_MODEL_FIX tier에서는 이 단계가 생략되고 바로 승인으로 감 — 3.1절) |
| 확인 필요 | `AWAITING_USER_INPUT` | 별도 강조 상태(파란 배지) — 진행바에서 이탈해 사용자 입력 대기 카드로 전환. 진입 사유가 둘이며 카드가 다르다: 모델이 모호함을 신고한 경우(3.4절)와 **두 초안이 갈린 경우**(3.9절) |
| 승인 대기 | `PLANNING`, `AWAITING_APPROVAL` | ExecutionPlan 요약 + 승인 필요 항목 개수 |
| 실행 | `EXECUTING` | 현재 진행 중인 `ToolRequest` 설명 (n/총 개수) |
| 검증 | `VERIFYING`, `FIX_LOOP` | build/test/lint 각 체크의 진행 상태. FIX_LOOP면 "검증 실패, 재시도 중 (N/max)" |
| 취소 중 | `CANCELLING` | 진행바에서 이탈해 "실행 중인 명령을 종료하는 중" 표시. **완료로 접지 않는다** — 아직 자식 프로세스가 살아 있을 수 있다 |
| 완료/실패 | `COMPLETED`/`FAILED`/`CANCELLED`/`REJECTED`/`INTERRUPTED` | 터미널 배지 + 요약 |

개발자 모드(설정에서 토글)에서는 실제 `TaskPhase` 값과 `complexityTier`, 카운터(`reviseRounds` 등)를 진행 표시 아래 작은 텍스트로 노출한다 — 디버깅/신뢰 구축용.

### 3.1 메인 작업 화면 (레이아웃)

```
┌─────────────────────────────────────────────────────────────────────────┐
│ [≡] Tomverse Code        워크스페이스: my-app ▾   브랜치: main ▾    [⚙] │
├───────────────┬─────────────────────────────────────┬───────────────────┤
│ 세션 목록      │  채팅 타임라인                        │  Diff / 검증 패널  │
│               │                                       │                   │
│ ● 세션 A (진행)│  User: 로그인 버튼이 안 눌려요          │  변경된 파일 (2)   │
│   세션 B      │                                       │  ├ src/Login.tsx  │
│   세션 C      │  ● 분석 ✓ ─ 검수 ✓ ─ 확인필요 ─         │  │  +12 −3        │
│               │    승인 ─ 실행 ─ 검증                  │  └ src/api.ts     │
│               │                                       │     +4 −0         │
│ [+ 새 세션]    │  Claude: 버튼 클릭 시 어떤 폼 필드를    │                   │
│               │  검증해야 하는지 명확하지 않습니다.      │  [파일 클릭 시     │
│               │  이메일만 확인하면 될까요, 비밀번호도    │   전체 diff 표시]  │
│               │  포함해야 할까요?                       │                   │
│               │                                       ├───────────────────┤
│               │  [답변 입력______________] [전송]       │ 비용 $0.02 · 8.4s │
│               │                                       │ 토큰 1.2k/0.6k    │
└───────────────┴─────────────────────────────────────┴───────────────────┘
```

- 단계 표시기(2절 매핑)는 채팅 타임라인 상단에 가로 스텝퍼로 고정되며, 현재 단계가 강조된다.
- Diff 패널은 `ExecutionPlan`이 확정되기 전(`PLANNING` 이전)에는 비어있고 "아직 변경 계획이 없습니다"를 표시 — `DraftProposal.patch`/`ReviewDecision.revisedPatch`가 나온 시점부터 미리보기용으로 먼저 채워질 수 있다(승인 전 미리보기, 아직 적용은 안 됨을 명확히 구분하는 라벨 필요).
- 비용/토큰 위젯(3.5)은 우측 패널 하단에 상시 고정.

### 3.2 워크스페이스/세션/브랜치 스위처

- 상단 바의 드롭다운. 워크스페이스 전환 시 [context-engine.md](./context-engine.md) 2절의 `WorkspaceIndex` 전환/로딩이 발생하므로, 인덱스가 아직 없는 워크스페이스는 "처음 여는 프로젝트라 인덱싱 중..." 로딩 상태를 보여준다(첫 오픈만 느림, 3절 근거).
- 브랜치 전환은 `git checkout`을 UI가 직접 실행하지 않고 `run_command` `ToolRequest`로 오케스트레이터에 요청 → Policy Gate가 `git checkout`을 allowlist 정책(state-machine-and-protocol.md 5절)에 따라 자동/승인 처리.

### 3.3 승인 모달

```
┌───────────────────────────────────────────┐
│  승인이 필요합니다                          │
│                                             │
│  ⚠ run_command                             │
│    git commit -m "fix login validation"    │
│    실행 위치: my-app/                       │
│                                             │
│  ⚠ delete_file                             │
│    src/LoginOld.tsx                        │
│                                             │
│         [거부]              [모두 승인]      │
└───────────────────────────────────────────┘
```

- `ExecutionPlan.toolRequests` 중 `riskTier != "auto"`인 항목만 나열(state-machine-and-protocol.md 4절). `auto`는 조용히 실행되어 모달에 나타나지 않는다 — 원 제안서의 "승인 피로도" 우려를 반영.
- 항목별 개별 승인/거부는 v1 범위에서 제외하고 "모두 승인" / "거부"(전체 취소, `CANCELLED`)만 지원 — 부분 승인은 ExecutionPlan의 순서 의존성 문제를 일으킬 수 있어 이후 검토(6절 미해결).
- `run_command`는 실제 실행될 argv를 그대로 노출한다(5절 allowlist가 shell string을 받지 않으므로 이 표시가 곧 실제 실행 내용과 100% 일치 — 셸 인젝션으로 표시와 실행이 달라질 수 없음).

### 3.4 확인 필요 카드

`AWAITING_USER_INPUT` 진입 시 채팅 타임라인 안에 인라인으로 나타난다(별도 모달 아님 — 대화의 자연스러운 일부로 취급). `ReviewDecision.questionsForUser` 또는 `SingleModelFixResult.questionsForUser`(state-machine-and-protocol.md 3/4b절)를 그대로 렌더링. 답변 전송 시 `DRAFTING`으로 재진입(14.1절 tier 승격 규칙에 따라 이후 항상 standard 경로).

### 3.5 비용/토큰/소요시간 위젯

```
┌─────────────────────────┐
│ 이번 태스크               │
│  비용     $0.0068        │
│  토큰     1.2k in/0.6k out│
│  경과     4.2s            │
│  예상 남은 시간  ~3s (평균 기반) │
└─────────────────────────┘
```

- "예상 남은 시간"은 현재 phase의 과거 평균 소요시간(같은 워크스페이스의 최근 태스크 이력에서 계산, `task_events` 조회)을 기반으로 한 근사치이며 확정값이 아님을 라벨로 명시.
- tier가 `simple`이면(TRIAGE 13.2절) 비용 위젯에 "단일 모델 처리 중 — 교차검증 생략"을 작게 표시해, 왜 이번 태스크가 더 빠른지 사용자가 이해할 수 있게 한다.

**검증 통과 후 커밋 토글** (state-machine-and-protocol.md 18절):

- 실행 정책(Fast/Verified) **옆의 별도 스위치**다. 기본은 꺼짐이고, 라벨에 "매번 승인을 묻습니다"를 함께 적는다 — 켜는 것이 "이제 묻지 않는다"로 읽히면 안 된다.
- 커밋은 되돌리기가 **파일만 복원하고 커밋은 남기는** 유일한 단계다. 그래서 실행 정책과 한 묶음으로 두지 않고 스위치를 나눴다.
- 켜져 있어도 승인 모달은 실제 argv(`git add -- <경로들>`, `git commit -m <메시지>`)를 그대로 보여준다. 사용자가 승인하는 것과 실행되는 것이 같다는 보장이 여기서도 유지된다.
- **UI 토글이 승인 등급을 낮추지 않는다.** Rust `TaskPolicy`는 워크스페이스를 열 때 고정되므로 토글이 켜져도 Policy Gate는 `git commit`을 High 승인으로 다룬다 — UI에서 켠 스위치가 신뢰 경계의 위험 등급을 낮출 수 있으면 그건 게이트가 아니다.

**취소 중 표시와 탈출구** (state-machine-and-protocol.md 16.3절):

- "취소 중"에는 **경과 시간을 함께 보여준다.** 정상 취소는 1초 안에 끝나므로, 숫자가 커지는 것 자체가 사용자에게 "이건 평소와 다르다"를 알리는 유일한 신호다.
- 5초를 넘기면 **강제 포기** 버튼을 연다. 그 전에는 보여주지 않는다 — 정상 취소 중에 탈출구가 뜨면 "뭔가 잘못됐나"라는 불안만 만든다.
- 버튼 옆 문구는 반드시 **"기다리기를 그만두는 것이지 프로세스를 죽이는 것이 아니다"**를 말한다. 이걸 "강제 종료"로 읽게 두면, 사용자는 정리가 끝났다고 믿고 남은 프로세스를 확인하지 않는다. 죽일 수 있었으면 애초에 이 버튼이 필요하지 않았다는 것이 이 문구의 근거다.

### 3.6 실패/취소 후 롤백 화면

state-machine-and-protocol.md 10절 롤백 UX의 화면 구현:

```
┌─────────────────────────────────────────────┐
│  ✗ 작업 실패 (검증 3회 재시도 후 중단)         │
│                                               │
│  이 작업이 변경한 파일 (2개)                   │
│   ☑ src/Login.tsx                            │
│   ☑ src/api.ts                               │
│                                               │
│  [변경사항 보기]     [되돌리기]   [그대로 두기] │
└─────────────────────────────────────────────┘
```

- `FAILED`는 "되돌리기"가 사전 체크된 기본값, `CANCELLED`는 체크 해제 상태로 시작(10절 원칙 그대로).

**커밋이 있으면 선택지가 둘이다** (state-machine-and-protocol.md 19절):

- 버튼이 **둘로 갈린다**: "파일만 되돌리기"와 "커밋 되돌리기(revert)". 알아서 고르는 한 버튼을 만들지 않는다 — 저장소에 남기는 결과가 다른 두 동작을 하나로 합치면, 사용자는 자기가 무엇을 눌렀는지 모른 채 이력이 바뀌는 것을 본다.
- 각각이 **무엇을 남기는지** 그 자리에 적는다: 파일만 되돌리면 커밋이 남아 워킹 트리가 HEAD와 달라지고, revert는 취소 커밋을 하나 더 만들어 이력에 둘 다 남는다.
- **`git reset`은 버튼으로 만들지 않는다.** 대신 "이 앱이 하지 않는다"와 그 이유(되돌릴 수 없고, 그 커밋을 이미 다른 사람이 받았는지 알 수 없다)를 적고 사용자에게 넘긴다. 우리가 하지 않는 일을 화면에서 감추면 사용자는 그 선택지가 없다고 오해한다.
- 커밋 sha를 확인하지 못했으면 revert 버튼을 **열지 않고** 그 사실을 말한다. 추측으로 이력을 건드리지 않는다.
- "변경사항 보기"는 3.1의 diff 패널로 스크롤/포커스 이동.

### 3.7 검증 결과 패널

`VerificationReport.checks[]`(state-machine-and-protocol.md 3절)를 체크리스트로:

```
검증 결과
 ✓ build     (2.1s)
 ✓ typecheck (0.8s)
 ✗ test      (3.4s) — 2개 실패
 – lint      (skipped)

[실패한 테스트 로그 보기]
```

`FIX_LOOP` 진입 시 이 패널이 "재시도 중 (2/3)"으로 바뀌고, 재시도가 끝나면 다시 최신 결과로 갱신된다.

## 4. 상호작용 규칙 (요약)

- **스트리밍:** `DraftProposal`/`ReviewDecision`/`SingleModelFixResult`의 텍스트 필드(`interpretation`, `rationale` 등)는 Provider가 스트리밍 지원 시 토큰 단위로 채팅 타임라인에 흘려보낸다. `finalFile`/`patch`처럼 구조화 출력의 나머지 필드는 스트리밍 완료 후 한 번에 반영(부분 JSON을 파싱 시도하지 않음 — 깨진 중간 상태를 렌더링하지 않기 위함).
- **취소:** 진행 표시기 옆 "취소" 버튼은 모든 비-터미널 phase에서 노출되며 `CANCELLING`을 거쳐 `CANCELLED`로 전이(2절 상태 다이어그램의 `--> CANCELLING` 전이들과 1:1 대응). 누른 뒤에는 버튼이 "취소 중..."으로 바뀌고 비활성화된다 — 요청 자체는 멱등이지만 연타는 사용자에게 혼란스럽다. **버튼 상태를 타이머로 풀지 않는다.** 프로세스가 실제로 죽었다는 사실은 호스트만 알고, 그 사실이 terminal 이벤트로 도착할 때 푼다.
- **취소 중 안내:** 이미 디스크에 쓰인 변경은 취소해도 되돌아가지 않는다. 이걸 숨기지 않고 "이미 변경된 파일은 자동으로 되돌아가지 않습니다 — 결과에서 되돌리기를 선택할 수 있습니다"로 명시한다(state-machine-and-protocol.md 16.3절).
- **재시도 표시:** `reviseRounds`/`fixLoopRounds`가 0보다 크면 단계 표시기에 작은 재시도 카운터 배지(예: "검수 (2/2)")를 추가 — 사용자가 "왜 오래 걸리지"를 이해하게 함.

### 3.8 최근 작업 목록 (M0.1)

```
┌─ 최근 작업 (12건)                                    [새로고침] ┐
│ ⚠ 앱이 비정상 종료되어 중단된 작업이 1건 있습니다.               │
│   파일이 변경된 상태로 남아 있을 수 있으니 되돌리기 여부를 확인하세요. │
├─────────────────────────────────────────────────────────────┤
│ 중단됨  login.ts 이메일 검증이 빈 문자열을 통과…              │
│         2026-07-27 14:02 · 변경 2개 · verified   [되돌리기][다시 실행] │
│ 완료    paginate.js 페이지 계산이 한 칸 밀려…                 │
│         2026-07-27 13:40 · 변경 1개 · fast       [되돌리기][다시 실행] │
│ 취소됨  전체 테스트 스위트를 리팩터링…                        │
│         2026-07-27 13:11 · fast                  [다시 실행]  │
└─────────────────────────────────────────────────────────────┘
```

- **워크스페이스를 열기 전에도 보인다.** 앱이 비정상 종료된 직후 사용자가 가장 먼저 알아야 하는 것이
  "중단된 작업이 있다"이기 때문이다. 그래서 저장 계층이 워크스페이스와 독립적으로 초기화된다.
- 행을 클릭하면 저장된 이벤트 타임라인이 **실시간 로그와 별도 패널에** 열린다 — 같은 목록에 섞으면
  같은 이벤트가 두 번 보인다.
- "다시 실행"은 **새 `task_id`로 같은 요청 문구를 처음부터** 돌린다. 중단 지점 이어가기가 아니다.
  이유는 state-machine-and-protocol.md 16.1절.
- "되돌리기"는 변경된 파일이 있을 때만 노출된다. 완료된 작업도 되돌릴 수 있다.

### 3.9 불일치 판정 카드 (M1) — 구현됨

근거는 [product-strategy.md 16절](./product-strategy.md), 데이터 구조는 [state-machine-and-protocol.md 17.2절](./state-machine-and-protocol.md).

두 실행자가 독립적으로 낸 초안이 갈렸을 때 나타난다. **3.4절 "확인 필요 카드"의 확장이 아니라 다른 카드다** — 확인 필요 카드는 모델이 "모르겠다"고 말한 경우이고, 이건 모델이 **둘 다 안다고 믿는데 답이 다른** 경우다. 사용자에게 이 둘은 전혀 다른 상황이므로 시각적으로 구별한다.

```
┌─ 확인이 필요합니다 — 두 모델의 해석이 갈렸습니다 (2건)          ┐
│                                                                │
│ ① 완료 기준                                          [필수]    │
│   빈 문자열 이메일을 어떻게 처리해야 합니까?                    │
│   ( ) 거부한다 — 검증 오류 메시지 표시                          │
│   ( ) 통과시킨다 — 서버 측에서 판정                             │
│   ( ) 직접 입력 ______________________________                 │
│                                                                │
│ ② 수정 위치                                          [필수]    │
│   두 초안이 서로 다른 파일을 고치려 합니다.                     │
│   ( ) src/validate.ts — 입력 검증 계층                          │
│   ( ) src/api/login.ts — 요청 처리 계층                         │
│   ( ) 직접 입력 ______________________________                 │
│                                                                │
│ ▸ 두 초안의 전체 차이 보기                                      │
│                                                     [확인]     │
└────────────────────────────────────────────────────────────────┘
```

**설계 규칙:**

- **강제 선택이 기본이고, 개방형 확인("이렇게 이해했는데 맞습니까?")을 만들지 않는다.** 16.2절 ② — 그럴듯한 요약에 "네"를 누르는 기계가 되면 사용자 판정이 형식만 남는다. 자유 입력은 항상 열어두되 세 번째 선택지로 둔다.
- **선택지에 모델 이름을 표시하지 않는다.** "GPT는 A라고, Claude는 B라고 했습니다"로 보여주면 사용자가 요구가 아니라 **모델 선호로 판단**하게 된다. 판정 대상은 "무엇이 맞는 요구인가"이지 "어느 모델이 나은가"가 아니다. 개발자 모드에서만 출처를 노출한다.
- **blocking 불일치는 한 화면에 묶어서 한 번에 묻는다.** 라운드 상한은 왕복 횟수이지 질문 개수가 아니다(17.4절). 세 번 깨우는 것이 최악이다.
- **비-blocking 불일치는 카드에 넣지 않고** 접힌 영역("두 초안의 전체 차이 보기")에만 둔다. 필수 항목과 참고 항목을 같은 목록에 섞으면 전부 참고 항목처럼 읽힌다.
- **일치한 필드를 초록 체크로 그리지 않는다.** 두 모델이 같은 방식으로 틀릴 수 있으므로 일치는 약한 증거다(16.5절). "두 모델이 동의함"을 검증 배지처럼 표시하는 것은 금지다 — 이 카드에서 초록색은 사용자가 **직접 판정한 항목**에만 쓴다.
- 답변 후 카드는 사라지지 않고 **판정 기록으로 타임라인에 남는다.** 나중에 "왜 이렇게 만들었나"의 정본이 되기 때문이다(`USER_DECISION_RECORDED`).

**구현에서 정해진 것** (`DisagreementCard.tsx`):

- **3.4절 확인 필요 카드와 동시에 뜨지 않는다.** 둘 다 `APPROVAL_REQUESTED_NOTE`로 오고 `disagreements`의 유무로 갈린다. 이벤트를 나누지 않은 이유: UI가 둘 중 하나를 놓치면 화면이 멈춘 것처럼 보이기 때문이다. 같이 그리면 사용자가 같은 질문에 두 번 답한다.
- **필수 항목에 전부 답해야 보낼 수 있다.** 부분 제출을 허용하면 남은 항목이 "묻지 못한 쟁점"으로 기록되는데, 실제로는 물었고 사용자가 건너뛴 것이라 로그가 거짓말을 한다.
- **자유 입력을 고르면 선택 라디오와 텍스트 입력이 함께 남는다.** `optionId` 없이 텍스트만 보내며, 감사 로그에 `freeform: true`로 기록된다 — 두 초안이 모두 틀렸다는 신호이고 그게 가장 값진 정보다(17.8절 ④).
- **테두리 색을 3.4절 카드와 다르게 쓴다.** 모델이 "모르겠다"고 한 것과 두 모델이 다른 답을 낸 것은 사용자에게 전혀 다른 상황이고, 같아 보이면 그 구별이 사라진다.
- **`blockingReason`과 초안 출처(`fromProposalId`)는 개발자 모드에서만 보인다.** 평소에 출처가 보이면 사용자가 요구가 아니라 모델 선호로 판단한다.

### 3.10 최종 보고의 기준 체크리스트 (M1) — 구현됨

3.7절 검증 결과 패널 위에 **사용자가 정한 기준**이 먼저 온다. 이전에는 build/test/lint 결과만 보고해서 사용자가 무엇을 결정했는지가 최종 화면에서 사라졌다(17.3절). `AcceptanceCriteriaPanel`이 `VerificationPanel` 위에 온다.

```
사용자가 정한 기준 (3)
 ✓ 빈 문자열 이메일을 거부한다          — validate.test.ts:41 로 확인됨
 ✓ 기존 로그인 흐름을 깨뜨리지 않는다    — 회귀 테스트 통과
 ? 오류 메시지를 한국어로 표시한다       — 대응하는 테스트 없음 (미확인)

검증 결과
 ✓ build     (2.1s)
 ✓ typecheck (0.8s)
 ...
```

- **`?`(미확인)를 `✓`로 만들지 않는다.** 기준 충족 여부를 모델에게 판정시키면 순환 의존이 그대로 재현된다(product-strategy 9절). 자동으로 이을 수 있는 것만 잇고 나머지는 미확인으로 남긴다 — "확인하지 못했다"와 "충족했다"는 다른 사실이다.
- **`✓`가 뜨는 조건은 좁다**(17.9절). 기준 문장이 **실재하는 테스트 파일을 지목**했고, 그 파일이 검증 출력에 실제로 나타났고, Rust의 `test` 체크가 통과한 경우에만 `✓`다. 그 밖에는 `?`이며 실제로 대부분이 여기다 — 기준과 테스트를 잇는 일반적인 방법이 아직 없기 때문이다. 위 그림은 연결이 넓어졌을 때의 목표 상태다.
- **표식은 넷이다.** `✓`(지목한 테스트가 실행됐고 통과) / `✗`(지목한 테스트를 포함한 검증이 실패) / `⚠`(이 기준이 지목한 파일을 변경이 건드리지 않음) / `?`(미확인). `?`만 있는 것보다 넷으로 나눈 이유는 3.7절이 `NOT_CONFIGURED`를 `✓`로 그리지 않는 것과 같다 — 실패와 미확인을 뭉개면 실패가 침묵으로 보인다.
- **판정 근거 문장을 항상 함께 보여준다.** 근거 없는 표식은 사용자가 검증할 수 없는 주장이고, 특히 `?`는 이유가 없으면 결함처럼 보인다.
- **`✓`는 결정론적 검증이 통과한 것에만 쓴다.** 미확인은 경고색 `?`로 두어 통과색과 섞이지 않게 한다 — 3.7절이 `NOT_CONFIGURED`를 `✓`로 그리지 않는 것과 같은 이유다.
- **블록 제목은 "확정된 기준"이고, 위 그림의 "사용자가 정한 기준"이 아니다.** 목록에는 사용자 판정(`user_decision`)과 모델 제안(`draft_proposal`)이 함께 들어가므로, 전부를 "사용자가 정한"이라고 부르면 화면이 거짓말을 한다. 대신 항목마다 출처 배지를 붙이고 부제로 개수를 나눠 적는다("사용자 판정 1개 · 모델 제안 2개"). 사용자 판정 항목만 굵게 두어 권위 차이를 시각적으로도 남긴다.
- **기준이 하나도 없으면 이 블록 자체를 그리지 않는다.** 빈 체크리스트는 "기준이 다 실패했다"로 읽힌다.
- **못 물어본 blocking 쟁점이 있으면 이 블록 아래에 표시한다**(`unresolvedDisagreements`). 질문 예산이 모자랐다는 사실을 숨기지 않는다.
