# UI 와이어프레임

status: draft
관련: [state-machine-and-protocol.md](./state-machine-and-protocol.md) (TaskPhase, ExecutionPlan, VerificationReport), [context-engine.md](./context-engine.md)

## 1. 설계 목표

- 원 아키텍처 제안서의 UI 요구사항을 화면 단위로 구체화한다: 채팅/스트리밍, 프로젝트·브랜치·세션 선택, 단계 표시(분석→검수→승인→실행→검증), diff 미리보기, 명령 실행 승인, 비용/토큰/소요시간 표시, 실패 시 재시도·롤백.
- **UI 프로세스는 API 키도 셸 실행 권한도 갖지 않는다**(원 제안서 원칙) — 여기서 그리는 모든 화면은 Local Orchestrator가 typed IPC로 밀어주는 상태를 그대로 렌더링할 뿐이며, "승인" 버튼을 눌러도 UI가 직접 뭘 실행하지 않고 승인 이벤트만 오케스트레이터에 전달한다.
- `TaskPhase`(14개, state-machine-and-protocol.md 2절)를 사용자에게 그대로 노출하지 않는다 — 원 제안서가 요구한 5단계(분석→검수→승인→실행→검증)로 압축해서 보여주고, 내부 상세는 개발자 모드/로그에서만 노출한다(2절 매핑 표).
- 와이어프레임은 저해상도(그레이박스, 실제 색상/폰트 없음)로 유지한다 — 레이아웃과 상태 전이를 확정하는 단계이지 비주얼 디자인 단계가 아니다.

## 2. `TaskPhase` → 사용자 노출 5단계 매핑

| 사용자에게 보이는 단계 | 내부 `TaskPhase` | 진행 표시 |
|---|---|---|
| 준비 중 | `CREATED`, `SNAPSHOTTING`, `TRIAGE` | 스피너, 보통 1초 미만이라 깜빡임 방지용 최소 표시시간만 둠 |
| 분석 | `DRAFTING`, `SINGLE_MODEL_FIX` | "OpenAI가 초안 작성 중" 또는 (simple tier면) "Claude가 검토 중" — tier에 따라 라벨이 달라짐 |
| 검수 | `REVIEWING` | "Claude가 독립 검토 중" (SINGLE_MODEL_FIX tier에서는 이 단계가 생략되고 바로 승인으로 감 — 3.1절) |
| 확인 필요 | `AWAITING_USER_INPUT` | 별도 강조 상태(파란 배지) — 진행바에서 이탈해 사용자 입력 대기 카드로 전환. 진입 사유가 둘이며 카드가 다르다: 모델이 모호함을 신고한 경우(3.4절)와 **두 초안이 갈린 경우**(3.9절) |
| 승인 대기 | `PLANNING`, `AWAITING_APPROVAL` | ExecutionPlan 요약 + 승인 필요 항목 개수 |
| 실행 | `EXECUTING` | 현재 진행 중인 `ToolRequest` 설명 (n/총 개수) |
| 검증 | `VERIFYING`, `FIX_LOOP` | build/test/lint 각 체크의 진행 상태. FIX_LOOP면 "검증 실패, 재시도 중 (N/max)" |
| 취소 중 | `CANCELLING` | 진행바에서 이탈해 "실행 중인 명령을 종료하는 중" 표시. **완료로 접지 않는다** — 아직 자식 프로세스가 살아 있을 수 있다 |
| 완료/실패 | `COMPLETED`/`FAILED`/`CANCELLED`/`REJECTED`/`INTERRUPTED` | 터미널 배지 + 요약 |

개발자 모드(설정에서 토글)에서는 실제 `TaskPhase` 값과 `complexityTier`, 카운터(`reviseRounds` 등)를 진행 표시 아래 작은 텍스트로 노출한다 — 디버깅/신뢰 구축용.

### 3.1 메인 작업 화면 (레이아웃)

```
┌─────────────────────────────────────────────────────────────────────────┐
│ [≡] Tomverse Code        워크스페이스: my-app ▾   브랜치: main ▾    [⚙] │
├───────────────┬─────────────────────────────────────┬───────────────────┤
│ 세션 목록      │  채팅 타임라인                        │  Diff / 검증 패널  │
│               │                                       │                   │
│ ● 세션 A (진행)│  User: 로그인 버튼이 안 눌려요          │  변경된 파일 (2)   │
│   세션 B      │                                       │  ├ src/Login.tsx  │
│   세션 C      │  ● 분석 ✓ ─ 검수 ✓ ─ 확인필요 ─         │  │  +12 −3        │
│               │    승인 ─ 실행 ─ 검증                  │  └ src/api.ts     │
│               │                                       │     +4 −0         │
│ [+ 새 세션]    │  Claude: 버튼 클릭 시 어떤 폼 필드를    │                   │
│               │  검증해야 하는지 명확하지 않습니다.      │  [파일 클릭 시     │
│               │  이메일만 확인하면 될까요, 비밀번호도    │   전체 diff 표시]  │
│               │  포함해야 할까요?                       │                   │
│               │                                       ├───────────────────┤
│               │  [답변 입력______________] [전송]       │ 비용 $0.02 · 8.4s │
│               │                                       │ 토큰 1.2k/0.6k    │
└───────────────┴─────────────────────────────────────┴───────────────────┘
```

- 단계 표시기(2절 매핑)는 채팅 타임라인 상단에 가로 스텝퍼로 고정되며, 현재 단계가 강조된다.
- Diff 패널은 `ExecutionPlan`이 확정되기 전(`PLANNING` 이전)에는 비어있고 "아직 변경 계획이 없습니다"를 표시 — `DraftProposal.patch`/`ReviewDecision.revisedPatch`가 나온 시점부터 미리보기용으로 먼저 채워질 수 있다(승인 전 미리보기, 아직 적용은 안 됨을 명확히 구분하는 라벨 필요).
- 비용/토큰 위젯(3.5)은 우측 패널 하단에 상시 고정.

### 3.2 워크스페이스/세션/브랜치 스위처

- 상단 바의 드롭다운. 워크스페이스 전환 시 [context-engine.md](./context-engine.md) 2절의 `WorkspaceIndex` 전환/로딩이 발생하므로, 인덱스가 아직 없는 워크스페이스는 "처음 여는 프로젝트라 인덱싱 중..." 로딩 상태를 보여준다(첫 오픈만 느림, 3절 근거).
- 브랜치 전환은 `git checkout`을 UI가 직접 실행하지 않고 `run_command` `ToolRequest`로 오케스트레이터에 요청 → Policy Gate가 `git checkout`을 allowlist 정책(state-machine-and-protocol.md 5절)에 따라 자동/승인 처리.

### 3.3 승인 모달

```
┌───────────────────────────────────────────┐
│  승인이 필요합니다                          │
│                                             │
│  ⚠ run_command                             │
│    git commit -m "fix login validation"    │
│    실행 위치: my-app/                       │
│                                             │
│  ⚠ delete_file                             │
│    src/LoginOld.tsx                        │
│                                             │
│         [거부]              [모두 승인]      │
└───────────────────────────────────────────┘
```

- `ExecutionPlan.toolRequests` 중 `riskTier != "auto"`인 항목만 나열(state-machine-and-protocol.md 4절). `auto`는 조용히 실행되어 모달에 나타나지 않는다 — 원 제안서의 "승인 피로도" 우려를 반영.
- 항목별 개별 승인/거부는 v1 범위에서 제외하고 "모두 승인" / "거부"(전체 취소, `CANCELLED`)만 지원 — 부분 승인은 ExecutionPlan의 순서 의존성 문제를 일으킬 수 있어 이후 검토(6절 미해결).
- `run_command`는 실제 실행될 argv를 그대로 노출한다(5절 allowlist가 shell string을 받지 않으므로 이 표시가 곧 실제 실행 내용과 100% 일치 — 셸 인젝션으로 표시와 실행이 달라질 수 없음).

### 3.4 확인 필요 카드

`AWAITING_USER_INPUT` 진입 시 채팅 타임라인 안에 인라인으로 나타난다(별도 모달 아님 — 대화의 자연스러운 일부로 취급). `ReviewDecision.questionsForUser` 또는 `SingleModelFixResult.questionsForUser`(state-machine-and-protocol.md 3/4b절)를 그대로 렌더링. 답변 전송 시 `DRAFTING`으로 재진입(14.1절 tier 승격 규칙에 따라 이후 항상 standard 경로).

### 3.5 비용/토큰/소요시간 위젯

```
┌─────────────────────────┐
│ 이번 태스크               │
│  비용     $0.0068        │
│  토큰     1.2k in/0.6k out│
│  경과     4.2s            │
│  예상 남은 시간  ~3s (평균 기반) │
└─────────────────────────┘
```

- "예상 남은 시간"은 현재 phase의 과거 평균 소요시간(같은 워크스페이스의 최근 태스크 이력에서 계산, `task_events` 조회)을 기반으로 한 근사치이며 확정값이 아님을 라벨로 명시.
- tier가 `simple`이면(TRIAGE 13.2절) 비용 위젯에 "단일 모델 처리 중 — 교차검증 생략"을 작게 표시해, 왜 이번 태스크가 더 빠른지 사용자가 이해할 수 있게 한다.

**검증 통과 후 커밋 토글** (state-machine-and-protocol.md 18절):

- 실행 정책(Fast/Verified) **옆의 별도 스위치**다. 기본은 꺼짐이고, 라벨에 "매번 승인을 묻습니다"를 함께 적는다 — 켜는 것이 "이제 묻지 않는다"로 읽히면 안 된다.
- 커밋은 되돌리기가 **파일만 복원하고 커밋은 남기는** 유일한 단계다. 그래서 실행 정책과 한 묶음으로 두지 않고 스위치를 나눴다.
- 켜져 있어도 승인 모달은 실제 argv(`git add -- <경로들>`, `git commit -m <메시지>`)를 그대로 보여준다. 사용자가 승인하는 것과 실행되는 것이 같다는 보장이 여기서도 유지된다.
- **UI 토글이 승인 등급을 낮추지 않는다.** Rust `TaskPolicy`는 워크스페이스를 열 때 고정되므로 토글이 켜져도 Policy Gate는 `git commit`을 High 승인으로 다룬다 — UI에서 켠 스위치가 신뢰 경계의 위험 등급을 낮출 수 있으면 그건 게이트가 아니다.

**취소 중 표시와 탈출구** (state-machine-and-protocol.md 16.3절):

- "취소 중"에는 **경과 시간을 함께 보여준다.** 정상 취소는 1초 안에 끝나므로, 숫자가 커지는 것 자체가 사용자에게 "이건 평소와 다르다"를 알리는 유일한 신호다.
- **관측된 취소 소요를 넘기면** 강제 포기 버튼을 연다. 그 전에는 보여주지 않는다 — 정상 취소 중에 탈출구가 뜨면 "뭔가 잘못됐나"라는 불안만 만든다. 시점은 이 워크스페이스에서 실제로 끝난 취소들의 분포에서 오고(16.3절), 표본이 부족하면 기본값 5초다.
- **임계값은 워크스페이스를 열 때 한 번만 읽는다.** 취소마다 다시 계산하면 탈출구가 뜨는 시점이 매번 달라지는데, 그 흔들림 자체가 불안이다. 읽기에 실패해도 작업을 막지 않는다 — 기본값으로 돌아가면 된다.
- 임계값이 측정에서 왔는지 기본값인지는 **개발 모드에서만** 보여준다. 일반 사용자에게 "이 숫자가 어디서 왔는가"는 필요 없는 정보지만, 임계값이 이상하게 느껴질 때 확인할 곳은 있어야 한다.
- 버튼 옆 문구는 반드시 **"기다리기를 그만두는 것이지 프로세스를 죽이는 것이 아니다"**를 말한다. 이걸 "강제 종료"로 읽게 두면, 사용자는 정리가 끝났다고 믿고 남은 프로세스를 확인하지 않는다. 죽일 수 있었으면 애초에 이 버튼이 필요하지 않았다는 것이 이 문구의 근거다.

### 3.6 실패/취소 후 롤백 화면

state-machine-and-protocol.md 10절 롤백 UX의 화면 구현:

```
┌─────────────────────────────────────────────┐
│  ✗ 작업 실패 (검증 3회 재시도 후 중단)         │
│                                               │
│  이 작업이 변경한 파일 (2개)                   │
│   ☑ src/Login.tsx                            │
│   ☑ src/api.ts                               │
│                                               │
│  [변경사항 보기]     [되돌리기]   [그대로 두기] │
└─────────────────────────────────────────────┘
```

- `FAILED`는 "되돌리기"가 사전 체크된 기본값, `CANCELLED`는 체크 해제 상태로 시작(10절 원칙 그대로).

**커밋이 있으면 선택지가 둘이다** (state-machine-and-protocol.md 19절):

- 버튼이 **둘로 갈린다**: "파일만 되돌리기"와 "커밋 되돌리기(revert)". 알아서 고르는 한 버튼을 만들지 않는다 — 저장소에 남기는 결과가 다른 두 동작을 하나로 합치면, 사용자는 자기가 무엇을 눌렀는지 모른 채 이력이 바뀌는 것을 본다.
- 각각이 **무엇을 남기는지** 그 자리에 적는다: 파일만 되돌리면 커밋이 남아 워킹 트리가 HEAD와 달라지고, revert는 취소 커밋을 하나 더 만들어 이력에 둘 다 남는다.
- **`git reset`은 버튼으로 만들지 않는다.** 대신 "이 앱이 하지 않는다"와 그 이유(되돌릴 수 없고, 그 커밋을 이미 다른 사람이 받았는지 알 수 없다)를 적고 사용자에게 넘긴다. 우리가 하지 않는 일을 화면에서 감추면 사용자는 그 선택지가 없다고 오해한다.
- 커밋 sha를 확인하지 못했으면 revert 버튼을 **열지 않고** 그 사실을 말한다. 추측으로 이력을 건드리지 않는다.
- **revert가 충돌했을 때의 문장이 결말마다 달라야 한다** (19.3절). 충돌해서 원상복구된 경우는 "저장소를 원래대로 돌려놓았습니다 — 바뀐 것은 없습니다"이고 사용자가 할 일이 없다. 원상복구까지 실패한 경우는 저장소가 **revert 진행 중**으로 남았다는 뜻이므로 같은 톤으로 말하면 안 된다 — 지금 손대야 하는 유일한 상태이고, 무엇을 해야 하는지(`git revert --abort`)까지 적는다.
- 충돌한 파일 목록을 함께 보여준다. `git revert --abort` 뒤에는 그 목록을 다시 알아낼 방법이 없으므로 앱이 지우기 전에 읽어 둔 것이고, 사용자가 직접 되돌리기로 결심했을 때의 출발점이다.
- "변경사항 보기"는 3.1의 diff 패널로 스크롤/포커스 이동.

### 3.7 검증 결과 패널

`VerificationReport.checks[]`(state-machine-and-protocol.md 3절)를 체크리스트로:

```
검증 결과
 ✓ build     (2.1s)
 ✓ typecheck (0.8s)
 ✗ test      (3.4s) — 2개 실패
 – lint      (skipped)

[실패한 테스트 로그 보기]
```

`FIX_LOOP` 진입 시 이 패널이 "재시도 중 (2/3)"으로 바뀌고, 재시도가 끝나면 다시 최신 결과로 갱신된다.

**종합 판정 배지는 네 값이다** — `통과` / `실패` / `검증되지 않음 (실행할 검증 명령이 없음)` /
`검증되지 않음 (명령을 실행하지 못함)`. 마지막 둘은 원인이 달라 **사용자가 할 일이 다르므로**
문구를 나눈다. 종전에는 하나로 뭉쳐 언제나 앞엣것을 단정했고, 스크립트가 있는데 실행에 실패한
사용자에게 "명령이 없습니다"라고 말했다(product-strategy.md 11.1절). 색은 둘 다 경고로 같다:
원인이 달라도 결정론적 근거가 없다는 점은 같고, 색으로 등급을 나누면 한쪽이 덜 심각해 보인다.

#### 결과 패널의 근거 배지

완료/실패 표시 **바로 아래**에 "무엇이 이 결과를 뒷받침하는가"를 한 줄로 낸다
(product-strategy.md 11.1절). 여기 없으면 검증이 침묵한 작업이 통과한 작업과 같은 신뢰
수준으로 읽힌다 — 그게 9절 서두가 "검증 없는 것보다 나쁘다"고 부른 상태다.

- 초록(통과) 톤은 **결정론적 근거가 실제로 있을 때만** 쓴다.
- 검증이 침묵했고 사용자 확정 기준만 있으면 `사용자 확인에만 근거함`이라고 **명시한다.**
- 둘 다 없으면 침묵하지 않고 `뒷받침하는 근거 없음`이라고 말한다.
- 계산은 화면 밖 순수 함수에 있다(`src/lib/resultBasis.ts`) — 화면 안에 있으면 검증할 방법이 없다.

## 4. 상호작용 규칙 (요약)

- **스트리밍:** `DraftProposal`/`ReviewDecision`/`SingleModelFixResult`의 텍스트 필드(`interpretation`, `rationale` 등)는 Provider가 스트리밍 지원 시 토큰 단위로 채팅 타임라인에 흘려보낸다. `finalFile`/`patch`처럼 구조화 출력의 나머지 필드는 스트리밍 완료 후 한 번에 반영(부분 JSON을 파싱 시도하지 않음 — 깨진 중간 상태를 렌더링하지 않기 위함).
- **취소:** 진행 표시기 옆 "취소" 버튼은 모든 비-터미널 phase에서 노출되며 `CANCELLING`을 거쳐 `CANCELLED`로 전이(2절 상태 다이어그램의 `--> CANCELLING` 전이들과 1:1 대응). 누른 뒤에는 버튼이 "취소 중..."으로 바뀌고 비활성화된다 — 요청 자체는 멱등이지만 연타는 사용자에게 혼란스럽다. **버튼 상태를 타이머로 풀지 않는다.** 프로세스가 실제로 죽었다는 사실은 호스트만 알고, 그 사실이 terminal 이벤트로 도착할 때 푼다.
- **큰 변경 안내:** 계획이 이 워크스페이스 기준으로 많은 파일을 건드리고 커밋이 켜져 있으면, **계획 시점에** 파일 수와 "커밋 하나로 남는다 / 되돌리기가 전부 아니면 전무다"를 말한다(state-machine-and-protocol.md 19.6절). 커밋을 보고 말하면 이미 늦다 — 그때는 쪼갤 수 있는 것이 없다.
- **막지 않는다.** 파일 30개짜리 이름 바꾸기는 정당하게 한 작업이고, 무엇이 한 작업인지는 앱이 판정할 수 없다. 사실만 말하고 판단은 넘긴다. 모달로 막으면 정당한 큰 작업마다 걸려 안내가 읽히지 않게 된다.
- 커밋이 꺼져 있으면 띄우지 않는다 — 그때는 "커밋 하나로 남는다"가 틀린 말이라 안내의 근거가 성립하지 않는다.
- 문턱이 관측에서 왔는지 기본값인지는 **개발자 모드에서만** 보여준다(강제 포기 시점과 같은 규칙).
- **보내기 전 자격증명 경고:** 요청문·답변·직접 입력에 자격증명처럼 보이는 값이 있으면 그 자리에 알린다(state-machine-and-protocol.md 17.11절). **막지 않는다** — 그 모양이 진짜 요구일 수 있고 요구의 최종 권위는 사용자다. 대신 버튼 문구가 "그대로 실행"/"그대로 전송"/"그대로 확인"으로 바뀌어 무엇을 하고 있는지가 눈에 남는다. 모달로 막으면 거짓 경보마다 막히고, 그러면 사용자가 경고를 읽지 않게 된다.
- **경고 문구는 자기 한계를 함께 말한다:** "아는 모양만 찾습니다. 여기 걸리지 않았다고 자격증명이 없는 것은 아닙니다." 이 문장이 없으면 **경고가 없는 것이 안전으로 읽힌다.**
- 검사 결과에는 **값이 담기지 않는다**(이름과 개수만). 그리고 검사는 아무것도 저장하지 않는다 — 편집 중인 입력을 기록하면 이 기능이 막으려는 것을 이 기능이 하게 된다.
- **취소 중 안내:** 이미 디스크에 쓰인 변경은 취소해도 되돌아가지 않는다. 이걸 숨기지 않고 "이미 변경된 파일은 자동으로 되돌아가지 않습니다 — 결과에서 되돌리기를 선택할 수 있습니다"로 명시한다(state-machine-and-protocol.md 16.3절).
- **재시도 표시:** `reviseRounds`/`fixLoopRounds`가 0보다 크면 단계 표시기에 작은 재시도 카운터 배지(예: "검수 (2/2)")를 추가 — 사용자가 "왜 오래 걸리지"를 이해하게 함.

### 3.7.5 무엇이 나갔는가 — 데이터 전송 투명성 (M1)

product-strategy.md 7절. 결과 패널 **아래**에 둔다 — 사용자가 먼저 묻는 것은 "됐는가"이고
"무엇이 나갔는가"는 그 다음이다. 위에 두면 결과를 읽기 전에 스크롤하게 된다.

- **공급자별로** 호출 수·역할·모델·토큰을 보여준다. 모든 호출이 같은 컨텍스트를 싣기 때문에 파일 목록은 공급자마다 반복하지 않고 한 번만 보여주되, **"각 공급자 모두에게 갔다"를 문장으로 명시한다.**
- **내용까지 나간 파일**과 **이름만 나간 파일**을 다른 목록으로 나눈다. `.env` 같은 파일은 내용이 빠져도 **경로와 제외 사유가 프롬프트에 실린다** — "Local only"로 뭉뚱그리면 경로도 안 나간 것으로 읽힌다(7.1절 ①).
- **마스킹된 secret 수를 단독으로 보여주지 않는다.** 그건 저장 기록에서 가린 수이고 전송된 것은 원문이다. 자유 텍스트 답변 건수와 함께, "저장 기록에서만 가려졌다"를 명시해서 낸다(7.1절 ②).
- **빈 목록과 "아직 모은 적이 없음"을 구별한다.** 후자는 별도 문구로 말한다 — 뭉개면 빈 화면이 거짓 안심을 준다.
- 마지막 줄은 **우리가 답할 수 없는 것**을 적는다: 공급자가 그것을 어떻게 보관·학습하는지는 각 공급자 정책의 영역이다. 이걸 흐리게 말하면 이 화면의 신뢰가 통째로 없어진다.

### 3.7.6 감사 기록 내보내기 (M1)

product-strategy.md 6.3절. 전송 패널 **아래**에 둔다 — "무엇이 나갔는가"는 이 작업을 보는
사람의 질문이고, "감사에 낼 기록을 다오"는 다른 시점의 질문이다.

- **버튼을 눌러야 만든다.** 작업이 끝날 때마다 자동으로 만들어 들고 있을 이유가 없다.
- **화면이 파일을 쓰지 않는다.** 내용을 보여주고 복사만 한다. UI가 임의 경로에 쓸 수 있게
  만들면 **Policy Gate를 지나지 않는 두 번째 쓰기 경로**가 생긴다. 파일로 떨구는 것은
  `tomverse-host export`가 한다.
- **복사 실패를 성공한 척하지 않는다.** 클립보드가 막힌 환경이 있고, 감사 기록을 옮기는
  중이라고 믿는 사람에게 조용한 실패가 가장 나쁘다.
- **artifact 본문이 빠졌다는 사실을 화면도 말한다.** 파일 안에도 `guarantees`가 있지만
  파일을 열지 않고 이 화면만 보는 사람이 있고, 그 사실은 export를 어디에 쓸 수 있는지를 바꾼다.
- **재현과 재실행을 화면 문구에서도 섞지 않는다.** 기록된 patch·명령의 재적용은 결정론적이고,
  같은 프롬프트로 모델을 다시 부르는 것은 아니다. 6.3절이 못박은 구분이 여기서 깨지면 문서에만
  적어둔 구분은 아무 일도 하지 않은 것이다.

### 3.8 최근 작업 목록 (M0.1)

```
┌─ 최근 작업 (50건 이상)                               [새로고침] ┐
│ ⚠ 앱이 비정상 종료되어 중단된 작업이 1건 있습니다.               │
│   파일이 변경된 상태로 남아 있을 수 있으니 되돌리기 여부를 확인하세요. │
├─────────────────────────────────────────────────────────────┤
│ 중단됨  login.ts 이메일 검증이 빈 문자열을 통과…              │
│         2026-07-27 14:02 · 변경 2개 · verified   [되돌리기][다시 실행] │
│ 완료    paginate.js 페이지 계산이 한 칸 밀려…                 │
│         2026-07-27 13:40 · 변경 1개 · fast       [되돌리기][다시 실행] │
│ 취소됨  전체 테스트 스위트를 리팩터링…                        │
│         2026-07-27 13:11 · fast                  [다시 실행]  │
├─────────────────────────────────────────────────────────────┤
│ [더 보기]                                                    │
└─────────────────────────────────────────────────────────────┘
```

- **워크스페이스를 열기 전에도 보인다.** 앱이 비정상 종료된 직후 사용자가 가장 먼저 알아야 하는 것이
  "중단된 작업이 있다"이기 때문이다. 그래서 저장 계층이 워크스페이스와 독립적으로 초기화된다.
- 행을 클릭하면 저장된 이벤트 타임라인이 **실시간 로그와 별도 패널에** 열린다 — 같은 목록에 섞으면
  같은 이벤트가 두 번 보인다.
- "다시 실행"은 **새 `task_id`로 같은 요청 문구를 처음부터** 돌린다. 중단 지점 이어가기가 아니다.
  이유는 state-machine-and-protocol.md 16.1절.
- "되돌리기"는 변경된 파일이 있을 때만 노출된다. 완료된 작업도 되돌릴 수 있다.

**페이지네이션(50건씩, "더 보기").** 제목의 건수가 `50건`이 아니라 `50건 이상`인 이유는
**전체 건수를 세지 않기 때문이다** — 세려면 페이지마다 전체 스캔이 붙는데, 그 숫자로 사용자가
하는 일이 없다. 모르는 것을 아는 척하지 않고 모른다고 적는다. 마지막 페이지에서는 "이상"이
빠지고 "모두 불러왔습니다"가 뜬다. 남은 페이지가 없으면 버튼 자체를 그리지 않는다 — 눌러도
아무 일이 없는 버튼은 사용자에게 고장으로 읽힌다.

**커서는 `(created_at, task_id)` 쌍이고 화면에게는 불투명하다.** 이유가 둘이다.

- 시각 하나로 자르면 **같은 시각의 행이 통째로 사라진다.** 마지막 행의 시각으로 `<`를 하면
  그 시각을 공유하는 다른 행도 함께 잘린다. 사용자에게 목록에서 사라진 작업은 없는 작업이다.
- 커서를 화면이 조립하면 정렬 기준이 바뀔 때 **화면과 질의가 조용히 갈라진다.** 실제로
  갈라져 있었다 — 커서는 `created_at`으로 만들면서 질의는 `updated_at`으로 잘랐고, 두 값이
  같은 동안에는 아무 증상이 없다가 작업이 갱신된 뒤부터 페이지 경계에서 행이 빠졌다. 이제
  커서는 `Store::cursor_for`만 만들고, 형식이 틀린 커서는 오류다(처음부터 되읽으면 "더 보기"가
  첫 페이지를 다시 붙여 목록이 늘어난 것처럼 보인다).

새로고침은 **이미 읽은 페이지를 버린다** — 1페이지만 갈아 끼우면 위쪽은 새 상태, 아래쪽은 옛
상태가 되어 어느 시점에도 존재한 적 없는 목록이 된다. 이어 붙이기 규칙은 화면 밖 순수 함수에
있다(`src/lib/taskPaging.ts`) — 중복된 행이나 전진하지 않는 커서는 **화면에서는 정상으로
보이므로** 눈으로 검증할 수 없다.

#### 3.8.1 스냅샷이 필요한 문제가 아니었다 (M1)

종전에 "고치지 않은 것"으로 적어둔 것: *"페이지를 넘기는 사이에 갱신된 작업은 목록 위쪽으로
이동하므로 아직 안 읽은 페이지에서 빠질 수 있다. 커서 하나로는 스냅샷을 흉내 낼 수 없고,
없애려면 조회 전체를 한 트랜잭션으로 묶어야 한다."*

**진단은 맞았고 처방이 틀렸다.** 행이 사라지는 이유는 스냅샷이 없어서가 아니라 **정렬 키가
움직이기 때문이다.** 커서 페이징은 키가 고정일 때만 성립한다 — `updated_at`으로 정렬하면 아직
안 읽은 페이지에 있던 행이 갱신되어 커서 **위로** 올라가고, 그 행은 어떤 페이지에도 나오지
않는다. 사용자에게 목록에서 사라진 작업은 없는 작업이다.

그래서 정렬과 커서를 **`created_at`으로 옮겼다.** 이 값은 생성 시각이라 production 경로 어디서도
UPDATE되지 않는다. 키가 움직이지 않으면 스냅샷 없이도 페이징이 안정하고, 조회를 트랜잭션으로
묶는 대가(사용자가 "더 보기" 앞에서 쉬는 동안 읽기 트랜잭션이 열려 있는 상태)도 치르지 않는다.

**그 전제를 사람의 기억에 맡기지 않는다.** production 경로가 `created_at`을 UPDATE하기 시작하면
페이징은 다시 **조용히** 깨진다(증상은 "가끔 목록에서 작업이 안 보인다"이고, 원인에서 멀다).
`store.rs`의 UPDATE 문 대입부를 소스에서 훑어 정렬 키를 건드리는 문이 생기면 실패하는 검사를
두었다. 검사가 아무것도 보지 않는 방식으로 고장 나지 않도록, 같은 방식으로 `updated_at` 대입이
실제로 잡히는지도 함께 확인한다.

**곁가지로 화면이 맞아떨어졌다.** 목록 행이 찍는 시각은 처음부터 `createdAt`이었다. 정렬이
`updated_at`이던 동안 화면은 **13:40이 14:02 위에 오는 목록**을 그릴 수 있었고, 그건 사용자에게
그냥 정렬이 안 된 목록이다. 정렬 기준을 화면이 보여주는 값으로 옮기면서 함께 사라졌다.

**바뀐 것도 적어 둔다.** 목록은 이제 "최근 활동 순"이 아니라 "최근 시작 순"이다. 태스크는 대개
짧게 끝나 두 값이 거의 같지만, 오래 도는 작업 하나는 시작 시각 자리에 남는다. 그 편이 낫다고
본 이유는 이 목록이 **이력**이기 때문이다 — 이력의 순서가 갱신 때마다 재배열되면 사용자가
방금 본 행이 어디로 갔는지 알 수 없다. 진행 중인 작업은 목록이 아니라 실행 화면에 있다.

**여전히 남는 것**: 페이지를 넘기는 사이에 **새로 생긴** 작업은 이미 읽은 1페이지 위에 놓여야
하므로 이 목록에 나타나지 않는다. 사라지는 것과 달리 이건 새로고침으로 곧 보이고, 무엇보다
사용자가 방금 만든 작업이라 화면 다른 곳에서 이미 보고 있다.

### 3.9 불일치 판정 카드 (M1) — 구현됨

근거는 [product-strategy.md 16절](./product-strategy.md), 데이터 구조는 [state-machine-and-protocol.md 17.2절](./state-machine-and-protocol.md).

두 실행자가 독립적으로 낸 초안이 갈렸을 때 나타난다. **3.4절 "확인 필요 카드"의 확장이 아니라 다른 카드다** — 확인 필요 카드는 모델이 "모르겠다"고 말한 경우이고, 이건 모델이 **둘 다 안다고 믿는데 답이 다른** 경우다. 사용자에게 이 둘은 전혀 다른 상황이므로 시각적으로 구별한다.

```
┌─ 확인이 필요합니다 — 두 모델의 해석이 갈렸습니다 (2건)          ┐
│                                                                │
│ ① 완료 기준                                          [필수]    │
│   빈 문자열 이메일을 어떻게 처리해야 합니까?                    │
│   ( ) 거부한다 — 검증 오류 메시지 표시                          │
│   ( ) 통과시킨다 — 서버 측에서 판정                             │
│   ( ) 직접 입력 ______________________________                 │
│                                                                │
│ ② 수정 위치                                          [필수]    │
│   두 초안이 서로 다른 파일을 고치려 합니다.                     │
│   ( ) src/validate.ts — 입력 검증 계층                          │
│   ( ) src/api/login.ts — 요청 처리 계층                         │
│   ( ) 직접 입력 ______________________________                 │
│                                                                │
│ ▸ 갈렸지만 묻지 않은 쟁점 (1건)                                  │
│ ▸ 두 초안이 각각 어떻게 봤는지                                   │
│                                                     [확인]     │
└────────────────────────────────────────────────────────────────┘
```

**설계 규칙:**

- **강제 선택이 기본이고, 개방형 확인("이렇게 이해했는데 맞습니까?")을 만들지 않는다.** 16.2절 ② — 그럴듯한 요약에 "네"를 누르는 기계가 되면 사용자 판정이 형식만 남는다. 자유 입력은 항상 열어두되 세 번째 선택지로 둔다.
- **선택지에 모델 이름을 표시하지 않는다.** "GPT는 A라고, Claude는 B라고 했습니다"로 보여주면 사용자가 요구가 아니라 **모델 선호로 판단**하게 된다. 판정 대상은 "무엇이 맞는 요구인가"이지 "어느 모델이 나은가"가 아니다. 개발자 모드에서만 출처를 노출한다.
- **blocking 불일치는 한 화면에 묶어서 한 번에 묻는다.** 라운드 상한은 왕복 횟수이지 질문 개수가 아니다(17.4절). 세 번 깨우는 것이 최악이다.
- **비-blocking 불일치는 필수 목록에 넣지 않고** 접힌 영역("갈렸지만 묻지 않은 쟁점")에 둔다. 필수 항목과 참고 항목을 같은 목록에 섞으면 전부 참고 항목처럼 읽힌다.
- **다만 접힌 영역 안에서는 답할 수 있다.** 종전에는 값만 나열했는데, 그러면 사용자가 거기서 잘못된 해석을 보고도 고칠 방법이 없다 — 규칙이 "묻지 않아도 된다"고 판정한 것이지 사용자가 그렇게 판정한 것이 아니다. 답은 **선택**이고 확인 버튼은 필수 항목만으로 열린다. 필수와 선택은 **같은 질문 컴포넌트**를 쓴다 — 따로 그리면 한쪽에만 붙은 개선(공통 항목 분리 같은)이 다른 쪽에 없게 되고, 그 차이는 화면을 나란히 놓고 봐야만 드러난다. 구분은 배지(`필수`/`선택`)와 왼쪽 선 하나다.
- 그리고 이 답이 **blocking 판정 규칙을 검증할 유일한 데이터**다(state-machine-and-protocol.md 17.4.1절). 오케스트레이터가 이 영역을 채우기 시작한 것도 그 때문이며, 종전에는 카드에 실리지도 않아 이 영역이 한 번도 뜨지 않았다.
- **접힌 영역은 둘이다** (state-machine-and-protocol.md 17.12절). "갈렸지만 묻지 않은 쟁점"은 규칙이 판정한 결과이고, "두 초안이 각각 어떻게 봤는지"(자유 서술)는 애초에 판정 대상이 아니다. 하나로 묶으면 판정한 것과 판정하지 않은 것이 같은 목록에 섞여 전체가 "그냥 참고"로 읽힌다.
- **자유 서술 영역은 차이를 주장하지 않는다.** 서술은 거의 언제나 다르므로 "차이가 있습니다"는 참이지만 아무것도 알려주지 않고, 매번 채워지는 목록은 곧 열리지 않는다 — 진짜 볼 것이 들어가는 날에도. 그래서 제목이 "전체 차이 보기"가 아니고, 그 자리에 "비교 결과가 아니라 서술을 그대로 옮긴 것"이라고 적는다.
- **대조 결과는 갈리지 않아도 말한다.** 카드는 갈린 것이 있을 때만 뜨므로, 그것만으로는 "대조했는데 같았다"와 "대조하지 않았다"가 사용자에게 **똑같이 빈 화면**이다 — 17절이 `DISAGREEMENT_DETECTED`를 0건에도 발행하기로 한 이유가 화면에서는 지켜지지 않고 있었다. 그리고 그 침묵이 하필 가장 위험한 쪽으로 읽힌다: 두 모델이 같은 방식으로 틀리면 불일치가 생기지 않으므로(9.2-B), 조용한 것은 **일치의 증거가 아니라 정보의 부재**다. 그래서 라우팅 패널 아래에 한 줄로 결말을 적는다(`lib/contrastSummary.ts`).
- **네 결말을 뭉개지 않는다**: 대조하지 않음(사유 포함) / 비교할 값이 없었음 / 같았음 / 갈렸음. 특히 **"비교할 값이 없었음"을 "같았음"으로 합치지 않는다** — 대조 코드가 양쪽 모두 비어 있는 필드를 `agreedFields`에 넣지 않는 규율("침묵을 동의로 세지 않는다")이 화면에서 무효가 된다.
- **일치한 필드를 초록 체크로 그리지 않는다.** 두 모델이 같은 방식으로 틀릴 수 있으므로 일치는 약한 증거다(16.5절). "두 모델이 동의함"을 검증 배지처럼 표시하는 것은 금지다 — 이 카드에서 초록색은 사용자가 **직접 판정한 항목**에만 쓴다.
- 답변 후 카드는 사라지지 않고 **판정 기록으로 타임라인에 남는다.** 나중에 "왜 이렇게 만들었나"의 정본이 되기 때문이다(`USER_DECISION_RECORDED`).

**구현에서 정해진 것** (`DisagreementCard.tsx`):

- **3.4절 확인 필요 카드와 동시에 뜨지 않는다.** 둘 다 `APPROVAL_REQUESTED_NOTE`로 오고 `disagreements`의 유무로 갈린다. 이벤트를 나누지 않은 이유: UI가 둘 중 하나를 놓치면 화면이 멈춘 것처럼 보이기 때문이다. 같이 그리면 사용자가 같은 질문에 두 번 답한다.
- **필수 항목에 전부 답해야 보낼 수 있다.** 부분 제출을 허용하면 남은 항목이 "묻지 못한 쟁점"으로 기록되는데, 실제로는 물었고 사용자가 건너뛴 것이라 로그가 거짓말을 한다.
- **자유 입력을 고르면 선택 라디오와 텍스트 입력이 함께 남는다.** `optionId` 없이 텍스트만 보내며, 감사 로그에 `freeform: true`로 기록된다 — 두 초안이 모두 틀렸다는 신호이고 그게 가장 값진 정보다(17.8절 ④).
- **테두리 색을 3.4절 카드와 다르게 쓴다.** 모델이 "모르겠다"고 한 것과 두 모델이 다른 답을 낸 것은 사용자에게 전혀 다른 상황이고, 같아 보이면 그 구별이 사라진다.
- **`blockingReason`과 초안 출처(`fromProposalId`)는 개발자 모드에서만 보인다.** 평소에 출처가 보이면 사용자가 요구가 아니라 모델 선호로 판단한다.

#### 3.9.1 선택지의 어려움은 개수가 아니라 길이와 구조였다 (M1)

5절 항목("선택지가 3개 이상일 때의 레이아웃")의 답이다.

**개수 쪽은 만들어질 수 없다.** 선택지는 `positions` 하나당 하나이고 `positions`는 초안 하나당
하나인데, 라우터는 executor를 둘까지만 배정한다(multi-engine-routing 13.1절). 셋을 지금 그리는
것은 **생길 수 없는 상태의 화면을 상상해 그리는 일**이고, 그렇게 그린 화면은 실제로 셋이 생길
때 맞을지 확인할 방법이 없다.

**정작 어려운 것은 한 선택지 안이었다.** 라벨은 `value.join(" / ")`로 만들어지는데
`doneCriteria`·`requiredTests`·`targetPaths`는 전부 목록이고, 특히 완료 기준은 모델이 쓴
문장들이다. 항목이 서넛만 되어도 라디오 버튼 옆에 문단이 붙는다. 더 나쁜 것은 **두 목록이
대부분 같고 한 항목만 다를 때**다 — 그때 사용자가 하는 일은 판정이 아니라 두 문단을 눈으로
diff하는 것이 된다. 판정하라고 만든 카드가 판정을 어렵게 한다.

그래서 공통 항목을 위로 빼고 각 선택지에는 **그 선택지에만 있는 것**만 남긴다.

```
│ ① 완료 기준                                          [필수]    │
│   무엇을 만족해야 이 작업이 끝난 것입니까?                      │
│   │ 양쪽 공통 — 고르는 대상이 아닙니다                          │
│   │  · 빈 문자열 거부                                          │
│   │  · 형식 검증                                               │
│   ( ) 429 응답                                                 │
│   ( ) 401 응답                                                 │
│   ( ) 직접 입력 ______________________________                 │
```

규칙:

- **선택의 의미는 바뀌지 않는다.** 고르는 것은 여전히 그 초안의 **목록 전체**이고 감사 기록에도
  전체가 남는다(`option.label` 그대로). 달라지는 것은 무엇을 보고 고르는가뿐이다. 화면 표시가
  기록을 바꾸기 시작하면 "왜 이렇게 만들었나"의 정본이 화면 사정에 흔들린다.
- **공통 항목은 선택지와 같은 무게로 그리지 않는다.** 같은 무게면 그것도 고를 수 있는 것처럼
  읽힌다.
- **고유 항목이 하나도 없는 선택지는 빈칸으로 두지 않는다.** "공통 항목만 — 더 요구하지 않음"이라고
  적는다. **없다는 것도 답이고**, 빈칸이면 그 선택지가 무슨 뜻인지 알 수 없다.
- **아무것도 정하지 않은 초안도 선택지 자리를 지킨다.** 목록에서 빼면 "이 초안은 아무것도 정하지
  않았다"를 고를 수 없게 된다.
- **겹치는 항목이 없으면 갈라내지 않는다.** 나눌 것이 없는데 나누는 틀만 그리면 세로 공간만 먹는다.
- **자르지 않는다.** 긴 기준을 접어 감추는 것은 사용자가 판정해야 할 것을 감추는 것이다
  (3.10절이 "연결 방법이 생기기 전에 표시만 다듬지 않는다"고 한 것과 같은 규칙).

계산은 `src/lib/optionChoice.ts`에 있다 — **화면 안에 있으면 검증할 방법이 없다.** 그리고
선택지 개수에 상관없이 성립하게 써서 3개짜리로도 테스트한다. 셋 이상에서 흔히 틀리는 방식은
"둘에만 있는 항목을 공통으로 세는 것"인데, 그러면 그 항목이 빠진 세 번째 선택지를 고를 근거가
사라진다. 그래서 공통은 **모든** 선택지에 있는 것으로만 판정한다.

이렇게 해두면 executor가 늘어날 때 다시 물어야 하는 것은 **시각 밀도 하나**로 좁아진다.

**조사 하나가 틀려 있었다.** 값이 빈 선택지의 라벨이 `${필드명}를 정하지 않음`으로 조립되어
"완료 기준를", "필요한 검증를"이 그대로 사용자 화면에 나가고 있었다. 받침으로 고르는 함수를
양쪽(sidecar·화면)에 두고 각각 테스트한다 — 표시 문자열은 표시하는 쪽이 갖는다는 규칙 때문에
`FIELD_LABEL`과 같은 모양으로 중복된다.

### 3.10 최종 보고의 기준 체크리스트 (M1) — 구현됨

3.7절 검증 결과 패널 위에 **사용자가 정한 기준**이 먼저 온다. 이전에는 build/test/lint 결과만 보고해서 사용자가 무엇을 결정했는지가 최종 화면에서 사라졌다(17.3절). `AcceptanceCriteriaPanel`이 `VerificationPanel` 위에 온다.

```
사용자가 정한 기준 (3)
 ✓ 빈 문자열 이메일을 거부한다          — validate.test.ts:41 로 확인됨
 ✓ 기존 로그인 흐름을 깨뜨리지 않는다    — 회귀 테스트 통과
 ? 오류 메시지를 한국어로 표시한다       — 대응하는 테스트 없음 (미확인)

검증 결과
 ✓ build     (2.1s)
 ✓ typecheck (0.8s)
 ...
```

- **`?`(미확인)를 `✓`로 만들지 않는다.** 기준 충족 여부를 모델에게 판정시키면 순환 의존이 그대로 재현된다(product-strategy 9절). 자동으로 이을 수 있는 것만 잇고 나머지는 미확인으로 남긴다 — "확인하지 못했다"와 "충족했다"는 다른 사실이다.
- **`✓`가 뜨는 조건은 좁다**(17.9절). 기준 문장이 **실재하는 테스트 파일을 지목**했고, 그 파일이 검증 출력에 실제로 나타났고, Rust의 `test` 체크가 통과한 경우에만 `✓`다. 그 밖에는 `?`이며 실제로 대부분이 여기다 — 기준과 테스트를 잇는 일반적인 방법이 아직 없기 때문이다. 위 그림은 연결이 넓어졌을 때의 목표 상태다.
- **"실재한다"의 정본은 인덱스이지 스냅샷이 아니다**(17.9.1절). 스냅샷은 토큰 예산이 고른 부분집합이라, 거기 없다는 것은 파일이 없다는 뜻이 아니다. 그리고 우리가 아는 목록에도 없으면 화면은 **"없습니다"가 아니라 "찾지 못했습니다"**라고 말한다 — 인덱스에도 상한이 있으므로 부재를 단언할 수 없다.
- **러너가 실행한 파일은 목록 조회보다 강한 근거다**(17.9.1절). `test` 체크의 argv나 출력에 나타났다면 그 파일은 실재하고 실행됐다. 목록에 없다는 이유로 그 근거를 버리지 않는다.
- **표식은 넷이다.** `✓`(지목한 테스트가 실행됐고 통과) / `✗`(지목한 테스트를 포함한 검증이 실패) / `⚠`(이 기준이 지목한 파일을 변경이 건드리지 않음) / `?`(미확인). `?`만 있는 것보다 넷으로 나눈 이유는 3.7절이 `NOT_CONFIGURED`를 `✓`로 그리지 않는 것과 같다 — 실패와 미확인을 뭉개면 실패가 침묵으로 보인다.
- **판정 근거 문장을 항상 함께 보여준다.** 근거 없는 표식은 사용자가 검증할 수 없는 주장이고, 특히 `?`는 이유가 없으면 결함처럼 보인다.
- **`✓`는 결정론적 검증이 통과한 것에만 쓴다.** 미확인은 경고색 `?`로 두어 통과색과 섞이지 않게 한다 — 3.7절이 `NOT_CONFIGURED`를 `✓`로 그리지 않는 것과 같은 이유다.
- **블록 제목은 "확정된 기준"이고, 위 그림의 "사용자가 정한 기준"이 아니다.** 목록에는 사용자 판정(`user_decision`)과 모델 제안(`draft_proposal`)이 함께 들어가므로, 전부를 "사용자가 정한"이라고 부르면 화면이 거짓말을 한다. 대신 항목마다 출처 배지를 붙이고 부제로 개수를 나눠 적는다("사용자 판정 1개 · 모델 제안 2개"). 사용자 판정 항목만 굵게 두어 권위 차이를 시각적으로도 남긴다.
- **기준이 하나도 없으면 이 블록 자체를 그리지 않는다.** 빈 체크리스트는 "기준이 다 실패했다"로 읽힌다.
- **못 물어본 blocking 쟁점이 있으면 이 블록 아래에 표시한다**(`unresolvedDisagreements`). 질문 예산이 모자랐다는 사실을 숨기지 않는다.

### 3.11 예산 상한 입력과 비용 결말 (M1) — 구현됨

multi-engine-routing.md 10.6절. 실행 정책(Fast/Verified) 아래에 **이 작업의 예산 상한**이 온다.

- **비우면 상한 없음이고, 화면이 그렇게 말한다.** `0`을 "무제한"으로 읽지 않는다 — 입력란을
  비운 것과 0을 적은 것은 다른 행동이고, 0은 "아무것도 못 도는 상한"이다. 잘못된 값을 조용히
  "없음"으로 바꾸지도 않는다: 오타 하나가 상한을 지우면 안 되므로 거부하고 사유를 보여준다.
- **제안값은 승인이 아니다.** 입력란을 채우기만 하고, 강제되는 것은 사용자가 확인한 값이다.
  제안이 어디서 왔는지(관측 N건에서 유도 / 표본 부족으로 기본값)를 함께 적는다 — 숫자만
  넘기면 화면이 추정치를 측정값으로 말하게 된다.
- **"이 작업 하나에만 적용된다"를 입력란 옆에서 말한다.** 다시 실행하면 상한만큼 다시 쓸 수
  있다는 사실은 결말 화면에서 처음 알면 늦다.
- **모드가 몇 번 부르는지를 모드 옆에서 말한다**(product-strategy 8.6절). 실행 정책이 바꾸는 것은 대부분 비용인데 이름은 검수만 말하고 있었다 — `Verified`는 **실행자를 하나 더 부른다**. 사실 두 개를 나란히 놓는다: 이 모드의 호출 수 범위(상한과, 라우터가 드롭했을 때의 하한)와 지금 상한으로 부를 수 있는 횟수. **"모자랄 수 있습니다" 같은 예측은 하지 않는다** — 틀릴 수 있는 경고는 몇 번 지나면 맞는 경고까지 함께 묻는다. 그리고 그 수가 총비용이 아니라는 것(재시도·수정 루프 제외)을 함께 적는다.
- **확실히 거부되는 조합은 시작 전에 말한다**(multi-engine-routing 15.5절). 상한이 한 호출의
  최대 비용보다 작으면 첫 호출부터 거부되는데, 그 사실을 시작한 뒤 오류로 아는 것과 누르기 전에
  아는 것은 사용자에게 전혀 다른 일이다. **확실할 때만 말한다** — "비쌀 수도 있습니다"는 하지
  않는다: 틀릴 수 있는 경고는 몇 번 지나면 읽히지 않고, 그러면 맞는 경고도 함께 묻힌다.
  그리고 **막지는 않는다**: 사실만 말하고 실행 버튼은 그대로 둔다.

결과 화면에서는 **비용 패널이 전송 내역보다 위**에 온다. "무엇이 나갔는가"보다 "얼마가
나갔는가"를 먼저 묻고, 특히 상한 없이 돌았다면 그 사실이 눈에 먼저 들어와야 한다.

- **네 상태를 같은 색으로 그리지 않는다.** `상한 없었음` / `상한 안에서 끝남` / `상한에 도달해
  일부 호출을 안 함` / `원장을 신뢰할 수 없어 막음`. 특히 앞의 둘을 같은 초록으로 그리면
  상한을 끈 사용자에게 거짓 안심을 준다.
- **하한을 정확한 값처럼 쓰지 않는다.** 가격을 모르는 호출이 있으면 금액 앞에 `≥`를 붙이고 그
  호출이 몇 건인지 말한다. 모르는 비용을 0으로 더하면 이 숫자가 "썼는데 안 썼다"고 말한다.
- **미해결 예약은 따로 말한다.** 요청이 나간 뒤 응답을 받지 못한 경우이며, 실제 과금 여부는
  공급자 청구 내역으로만 확인된다 — 우리가 대신 판단하지 않는다.
- **이 앱이 낸 호출만의 합계라는 것을 적는다.** 같은 키를 쓰는 다른 도구의 지출은 여기 없고,
  그 사실을 말하지 않으면 이 숫자가 사용자의 청구서로 읽힌다.

### 3.12 역할별 모델 지정 (M1) — 구현됨

multi-engine-routing.md 15절. 예산 상한 **위**에 온다 — 무엇으로 돌릴지가 얼마까지 쓸지보다
먼저 오는 질문이고, 고른 모델이 비용을 지배한다.

- **목록이 비면 블록 자체를 그리지 않는다.** 빈 select는 "고를 것이 없다"와 "목록을 못 읽었다"를
  구별하지 못하고, 어느 쪽이든 사용자가 할 일은 없다.
- **단가를 옵션에 함께 적는다.** 모델 선택은 대부분 비용에 관한 결정이고, 숫자 없이 고르라고
  하면 사용자는 이름으로 고른다.
- **"대체하지 않는다"를 미리 말한다.** 지정한 모델을 쓸 수 없으면 시작하지 않는다는 사실은
  실패 메시지에서 처음 알면 늦다.
- **검수 드롭 규칙을 미리 말한다.** 지정한 검수자가 실행자와 같은 공급자면 검수를 드롭한다 —
  같은 공급자로 "검증한 척"하지 않는 것이 이 도구가 파는 것이므로, 그 교환을 고르기 **전에**
  보여준다.
- **co-executor를 고를 수 없는 이유를 적는다.** 없는 선택지는 이유가 없으면 결함처럼 보인다.

### 3.13 공급자 제한과 자격증명 확인 (M1) — 구현됨

multi-engine-routing.md 16·17절. 공급자 칩 아래, 작업 입력 **위**에 온다 — 무엇으로 돌릴 수
있는지가 무엇을 시킬지보다 먼저 정해진다.

- **"키가 없다"와 "정책이 막았다"를 갈라 말한다.** 뭉개면 사용자는 없는 키를 찾아 헤매거나,
  자기가 건 제한을 잊고 "왜 안 되지"를 반복한다.
- **허용 목록이 비면 그 사실을 경고로 말한다.** 아무 공급자도 허용하지 않으면 작업을 시작할 수
  없는데, 그 이유가 화면에 없으면 시작 버튼이 이유 없이 실패하는 것처럼 보인다.
- **"다시 열어야 적용된다"를 저장 직후에 말한다.** 강제가 sidecar spawn 시점이므로 즉시 반영이
  아니고, 몰래 재시작하면 진행 중인 작업이 죽는다.
- **확인 버튼 옆에 "무료 조회만 합니다"를 적는다.** 안 적으면 예산 상한을 건 사용자가 누르기를
  망설인다 — 실제로 돈이 나가지 않는데.
- **"조회됨"을 "된다"로 그리지 않는다.** 조직 인증이 필요한 모델은 조회되고 호출에서 죽으므로,
  성공 문구가 그 한계를 함께 말한다. 확인이 보증으로 읽히면 안심시킨 만큼 해롭다.
- **아직 확인하지 않은 것과 "문제없음"을 구별한다.** 결과가 없으면 아무것도 그리지 않는다 —
  빈 초록은 확인한 적 없는 상태를 통과로 보이게 한다.

### 3.14 대용량 변경의 diff 패널 (M1) — 구현됨

```
┌─ 변경된 파일 (12)                                             ┐
│ +148 −37 · 1,204줄                                            │
│ [경로로 거르기        ]  정렬 [적용 순서 ▾]                    │
│ ⚠ 필터로 9개를 숨겼습니다 (+120 −30).                          │
│   되돌리기는 숨긴 파일까지 전부에 적용됩니다.                   │
├───────────────────────────────────────────────────────────────┤
│ ▸  #2  src/auth/login.ts            +18 −4                    │
│ ▸  #5  src/auth/session.ts          +6 −2                     │
│ ▾  #7  src/auth/token.ts            +4 −1                     │
│      @@ -12,3 +12,4 @@                                        │
│      - const ttl = 3600;                                      │
│      + const ttl = 7200;                                      │
└───────────────────────────────────────────────────────────────┘
```


**이 화면의 목적은 읽기가 아니라 판단이다.** 사용자가 여기서 하는 일은 이 변경을 받아들일지
되돌릴지 정하는 것이고, 파일 50개를 평평하게 늘어놓으면 그 판단이 쉬워지는 게 아니라
불가능해진다.

- **먼저 요약을 준다.** 파일 수 · +/− · 총 줄 수. 무엇을 판단해야 하는지가 한 줄로 보여야 한다.
- **"큰 변경"은 워크스페이스 기준으로 판정한다.** 19.6절에서 관측으로 유도한 문턱을 그대로 쓴다
  — 절대 기준을 새로 만들면 같은 말("크다")이 화면마다 다른 뜻을 갖는다. 그리고 **되돌리기가
  전부-아니면-전무**라는 사실을 그 자리에서 말한다.
- **접힌 파일은 그리지 않는다.** `<details>`는 접혀 있어도 내용이 DOM에 있다 — 종전 구현은
  파일 50개짜리 변경에서 수천 개의 노드를 만들었다. 편 것만 그린다.
- **한 파일도 상한까지만 그린다.** 수만 줄짜리 diff 하나로 화면이 멈추지 않게 한다.
- **자른 사실을 반드시 말한다.** "N줄 중 M줄만 표시(K줄 감춤)"와 "전부 보기"를 함께 낸다.
  조용히 자르면 사용자는 그게 전부인 줄 알고 판단하는데, **그건 판단의 근거를 몰래 바꾸는 것이다.**
  잘린 내용은 사라지지 않는다 — 전체 diff는 `task_events`와 감사 export에 그대로 있으므로,
  여기서 자르는 것은 읽기 보조를 줄이는 것이지 기록을 줄이는 것이 아니다.

**계산은 화면 밖에 있다**(`src/lib/diffSummary.ts`). +/− 집계가 틀리면 사용자는 "12줄 바뀜"을
보고 판단하는데 실제로는 120줄일 수 있고, 그 오류는 눈으로 잡히지 않는다. 화면 안에 두면
검증할 방법이 없어서 순수 함수로 뺐고, 그 김에 `apps/desktop`에 테스트 하네스가 생겼다
(종전에는 UI 로직을 검증할 수단이 아예 없었다).

#### 필터와 정렬 — 문항이 둘을 묶고 있었다

남은 항목은 "경로 필터나 '변경이 큰 파일부터' 정렬"을 하나로 묶고, 미룬 이유를 **"정렬은 적용
순서를 감추므로 그 대가를 먼저 정해야 한다"**로 적었다. 그런데 **둘은 대가가 다르다.**

- **필터는 순서를 바꾸지 않는다.** 행을 숨길 뿐 남은 행은 그대로 적용 순서다.
- **정렬만 순서를 대체한다.**

그리고 정렬의 대가("순서를 잃는다")는 **순번을 함께 보여주면 대부분 치르지 않아도 된다.**
각 행에 적용 순번(`#3`)을 붙이면 재배열돼도 원래 위치를 읽을 수 있다. 남는 것은 *인접성*뿐이다
— 같은 파일을 두 번 고친 기록이 정렬 후 떨어질 수 있고 그건 순번으로도 복원되지 않는다.
그래서 **기본은 적용 순서**이고, 정렬 중일 때는 화면이 그 사실을 말한다.

**필터의 대가는 따로 있다: 숨긴 것을 모르게 하는 것.** 되돌리기가 **전부 아니면 전무**이므로,
필터가 걸러낸 파일이 있는데 말하지 않으면 사용자는 일부만 보고 전체를 판단한다. 그래서
숨긴 개수와 그 +/− 합계를 함께 내고, "되돌리기는 숨긴 파일까지 전부에 적용됩니다"를 붙인다.

**요약 숫자는 필터를 따르지 않는다.** 헤더의 파일 수와 +/−가 필터를 따라 줄어들면 되돌리기
범위(전체)와 화면의 숫자가 어긋난다 — **필터는 보기이지 범위가 아니다.**

세부 규칙 셋이 더 있고, 셋 다 화면에서는 정상으로 보이는 실패를 막는다(`src/lib/diffList.ts`).

- **0건이 두 가지 뜻을 갖지 않게 한다.** "변경이 없다"와 "필터가 다 걸러냈다"를 합치면
  사용자는 되돌릴 것이 없다고 읽는데, 실제로는 되돌릴 것이 전부 있다.
- **동점은 적용 순서로 푼다.** 풀지 않으면 같은 변경이 렌더마다 다르게 보이고, 사용자는 그걸
  화면이 바뀐 것으로 읽는다.
- **경로 정렬에 `localeCompare`를 쓰지 않는다.** 결과가 환경의 ICU 데이터에 따라 달라지면
  두 사람이 같은 목록을 보고도 다른 순서를 본다.

필터는 **대소문자를 구별하지 않는 부분 문자열**이다. 글롭을 쓰지 않는 이유: 이 입력란의 용도는
"지금 이 목록에서 찾기"이고, 글롭은 기대와 어긋날 때 왜 안 걸리는지 설명이 필요하다.

## 6. 다국어 — 분리 시점의 조건 (M1)

5절 항목("다국어 문자열 카탈로그 분리 **시점**")의 답이다. 문항이 시점을 물었으므로 답도
시점이어야 하는데, **날짜가 아니라 조건**이다.

### 6.1 지금 분리하면 반쪽 번역이 된다

"UI 문자열을 카탈로그로 뺀다"는 자연스러운 첫 수인데, 이 제품에서는 그게 **커버리지의 착시**를
만든다. 사용자에게 그대로 보이는 문장이 화면 밖에도 있기 때문이다.

| 어디 | 예 |
|---|---|
| React 컴포넌트 | 버튼·제목·라벨 |
| `src/lib/*.ts` 순수 함수 | 배너 문구, 숨김 안내, 건수 표기 |
| **Rust `tomverse-core`** | 승인 응답 오류(`RespondError::message`), 백엔드 상태, 재현 판정 사유, 런처 실패 설명 |

세 번째 줄이 문제다. 이 저장소는 이번 마일스톤에서 **사용자에게 보이는 문장을 일부러 core로
옮겼다** — Tauri 껍데기 크레이트가 개발 환경에서 컴파일되지 않아 거기 남는 로직이 검증되지
않기 때문이다(process-architecture.md 10.3절). 옳은 결정이었지만, 그 결과 **문장이 두 프로세스에
흩어져 있다.** UI만 카탈로그로 빼면 언어를 바꿔도 절반만 바뀌고, **반쪽 번역은 번역이 없는
것보다 나쁘다** — 사용자는 어느 문장이 왜 안 바뀌었는지 알 수 없다.

### 6.2 조건: 문장이 프로세스 경계를 넘지 않게 된 뒤에 분리한다

그래서 카탈로그를 만들기 전에 지켜야 할 규칙을 먼저 세운다.

> **화면에 그대로 뜨는 문장은 프로세스 경계를 넘지 않는다. 판정과 파라미터가 넘고, 문장은
> 화면이 만든다.**

같은 규칙을 이미 한 번 적용했다: "다시 열기" 버튼을 띄울지를 화면이 문장에서 읽어내지 않게
`recovery`를 값으로 줬다(process-architecture.md 5.2절). **문장 자체도 같은 이유로 값이어야
한다** — 넘어온 문장은 영원히 한국어이고, 카탈로그를 만들어도 그 밖에 남는다.

값을 문장에 이어 붙이지 않는 것도 같은 규칙의 일부다. `attempts`·`error` 같은 값은
**파라미터로** 넘긴다 — 이미 이어 붙인 문장은 어순이 다른 언어로 옮길 수 없다.

**진단 출력은 예외다.** stderr 로그와 `describe_failure` 같은 개발자용 설명은 화면에 그대로
뜨지 않으므로 원문 그대로 둔다. 번역 대상은 **화면에 뜨는 것**이고, 그 구별을 흐리면 규칙이
모든 문자열로 번져 지킬 수 없게 된다.

### 6.3 지금 한 것 — 규칙을 한 곳에서 실제로 지킨다

백엔드 상태 배너를 전환했다. Rust는 `code` + `params`를 주고 화면이 문장을 만든다.

- 코드는 서로 달라야 하고 파라미터가 비면 안 된다(비면 이어 붙이기로 되돌아간다) — 테스트가 지킨다.
- **화면이 모르는 코드는 원문으로 떨어진다.** Rust가 `message`(원문)를 함께 주고, 카탈로그가
  그 코드를 모르면 그걸 그린다. 반쪽 번역은 나쁘지만 **반쪽 번역과 빈 화면 중에서는 반쪽
  번역이 낫다** — 빈 배너는 사용자가 앱이 멈춘 이유를 알 방법을 없앤다. 떨어졌다는 사실은
  값으로 남긴다(`untranslated`).
- **Rust가 내는 코드를 카탈로그가 전부 아는지 테스트가 대조한다.** 판정 기준은 사람이 적은
  또 다른 목록이 아니라 **Rust 소스에서 유도한 코드 목록**이다. 모르는 코드는 원문으로
  떨어지므로 앱이 깨지지 않는데, 그래서 조용하다 — 조용한 누락은 영원히 번역되지 않는다.

### 6.4 봉투를 공통으로 두고 나머지 경계를 전환했다

경계마다 자기 모양을 만들면 화면에 렌더러가 여러 개 생기고 카탈로그도 갈라진다. 그러면
**"이 코드가 카탈로그에 있는가"를 한 번에 확인할 수 없다** — 확인할 수 없는 규칙은 지켜지지
않는다. 그래서 Rust 쪽은 `UserFacing` 트레이트 하나가 `{code, params, message}` 봉투를 내고
(`core/src/uimsg.rs`), 화면 쪽은 카탈로그 하나가 받는다(`src/lib/messages.ts`).

전환한 것:

| 경계 | 코드 |
|---|---|
| 백엔드 상태 배너 | `respawnLimit` · `protocolViolation` · `spawnFailed` |
| 승인 응답 오류 | `approvalUnknown` · `approvalWrongWorkspace` · `approvalGone` |

**승인 응답은 실패도 `Ok` 봉투로 돌려준다.** Tauri의 `Err`는 문자열 하나뿐이라 구조가 들어갈
자리가 없고, 문자열에 구조를 실으면 **화면이 문장을 파싱하게 된다** — 6.2절이 없애려는 바로
그것이다. 그래서 "사용자에게 보일 이유가 있는 실패"는 `Err`가 아니라 `Ok(envelope)`로 나간다.

검사는 양방향이다. **Rust가 내는 코드를 카탈로그가 전부 아는가**(모르면 원문으로 떨어져 앱은
멀쩡하고 그 문장만 영원히 번역되지 않는다), 그리고 **카탈로그에 죽은 코드가 없는가**(쌓이면
번역할 분량이 실제보다 커 보인다). 판정 기준은 사람이 적은 목록이 아니라 **core 소스 전체에서
유도한 코드 목록**이다.

#### 재현 판정은 전환 대상이 아니다

6.4절의 앞선 목록에 "재현 판정 사유"를 넣었던 것은 **범위를 잘못 잡은 것이다.**
`tomverse-host reproduce`의 출력은 화면이 아니라 **감사자가 읽는 CLI JSON**이고, 그 JSON은
이미 태그된 enum(`Precondition` · `UnknownReason` · `StopReason`)이라 기계가 읽을 형태를
갖추고 있다. 남은 산문은 Policy Gate가 준 사유 같은 **진단 세부**이며 6.2절의 예외에 해당한다.
번역 대상을 "사용자에게 도움이 되는 모든 문자열"로 넓히면 규칙이 지킬 수 없는 크기가 된다.

### 6.5 저장 계층 — 사용자에게 실제로 보이는 두 곳만 전환했다

저장 계층 실패는 껍데기 크레이트 여러 곳에서 `format!`으로 나가고 있었다. 전부 옮기는 대신
**화면에 실제로 뜨는 경로 둘**만 전환했다.

| 경로 | 어떻게 나가나 | 코드 |
|---|---|---|
| 앱 시작 — artifact 저장소·DB 열기·중단된 작업 확정 | `store-ready` 이벤트 | `storeOpenArtifacts` · `storeOpenDatabase` · `storeRecoverInterrupted` |
| 작업 목록 읽기(첫 페이지·"더 보기") | `list_tasks`의 `Ok(envelope)` | `storeReadTasks` |
| 작업 상세 열기(작업 행 + 변경 목록 + 확정 기준) | `get_task`의 `Ok(envelope)` | `storeReadTask` |
| 작업 타임라인 읽기 | `get_task_events`의 `Ok(envelope)` | `storeReadTaskEvents` |
| 화면 문턱 집계 | `derived_thresholds`의 `Ok(envelope)` | `storeReadThresholds` |
| 전송 내역 패널 | `task_transmission`의 `Ok(envelope)` | `storeReadTransmission` |
| 감사 export | `task_export`의 `Ok(envelope)` | `storeReadExport` |

**작업 상세를 이루는 세 읽기는 코드가 하나다.** 코드는 *사용자가 무엇을 하려다 실패했는가*이고
사용자가 한 일은 "이 작업을 연다" 하나다. 어느 읽기였는지는 `detail`에 남는다.

**판정을 `StoreError`와 나눠 담았다.** `StoreError`는 *무엇이 잘못됐는가*(sqlite 오류, io
오류)이고, 화면이 알아야 하는 것은 *사용자가 무엇을 하려다 실패했는가*다. `"database is
locked"`만 보여주면 사용자는 할 수 있는 일이 없고, `"작업 목록을 읽을 수 없습니다"`만 보여주면
원인이 사라진다. 그래서 `StoreOp`가 코드가 되고 원인은 `detail` **파라미터**로 간다 —
이어 붙인 문장은 어순이 다른 언어로 옮길 수 없다(6.2절).

그리고 이 타입은 **core에 둔다**(`core/src/store.rs`). 껍데기 크레이트는 이 개발 환경에서
컴파일되지 않으므로 거기 남는 문장은 검증되지 않는다 — 백엔드 배너와 승인 응답도 같은 이유로
옮겼다(process-architecture.md 5.2절·11.5절).

#### 전환하면서 드러난 결함 둘

전환은 기계적일 것 같았지만 화면 쪽에서 결함 둘을 꺼냈다. 둘 다 **실패가 실제로 일어나야만
보이는** 종류라 조용히 남아 있었다.

- **`String(error)`가 `Error: `를 앞에 붙이고 있었다.** 봉투로 온 실패를 `throw`로 올린 뒤
  `catch`에서 문장을 만들었는데, `String(new Error(t))`는 `"Error: " + t`다. 사용자 화면에
  `Error: 작업 목록을 읽을 수 없습니다: …`가 그대로 나갔다. **봉투로 온 실패는 예상된
  결과이므로 예외로 다루지 않는다** — 예외는 전송 자체가 실패한 경우에만 남긴다. 둘은 다른
  사실이고, 갈래를 나눠 두면 그 구별이 코드에 남는다.
- **틀이 두 번 씌워지고 있었다.** Rust가 `작업을 읽을 수 없습니다: {e}`를 만들고 화면이 다시
  `작업을 읽을 수 없습니다: ${error}`로 감쌌다. 코드+파라미터로 옮기면서 화면 쪽 틀을 지웠다 —
  **문장을 만드는 곳이 하나여야 두 번 씌워지지 않는다.**

#### 봉투를 만드는 자리는 한 곳이고, 그 자리는 core다

경계마다 직접 조립하면 키 이름이 갈라진다. 실제로 갈라져 있었다: `store-ready`만 `message`
대신 `error`를 써서, 화면에 이 경계 전용 읽기가 하나 더 있었다. 지금은 Rust 쪽이
`envelope()` 하나를 지나고 화면 쪽이 `unwrap()` 하나를 지난다. **성공 쪽도 같은 함수를
지난다** — `ok`를 손으로 얹기 시작하면 곧 한 군데가 빠진다.

`envelope()`는 껍데기가 아니라 `core/src/uimsg.rs`에 있다. 이 함수는 `UiMessage`를 JSON
모양으로 바꿀 뿐 tauri를 모르는데, 껍데기에 두면 **이 개발 환경에서 컴파일되지 않아 검증되지
않는다.** 화면과의 계약을 정하는 코드를 검증할 수 없는 자리에 둘 이유가 없다 — 5.2절·11.5절에서
문장을 core로 옮긴 것과 같은 판단이다.

`unwrap`은 **`ok`가 없는 응답을 성공으로 읽지 않는다.** 그렇게 읽으면 전환을 빠뜨린 명령이
조용히 통과하고, 그 사실은 실패가 실제로 일어나는 날에야 드러난다. 그리고 그 자리에서
`render`에 아무 객체나 넘기면 코드도 원문도 없는 값에서 `text: undefined`가 나와 **빈칸이
그려진다** — 테스트가 그 상태를 실제로 잡았다.

#### 빠뜨림을 타입이 막는다

전환을 세 라운드에 나눠 하면서 매번 같은 위험이 있었다: **새 화면 명령을 만들면서 봉투를
잊으면 아무도 알아채지 못한다** — 실패가 실제로 일어나야만 보이기 때문이다. 규칙을 사람이
지키게 두면 언젠가 빠진다.

그래서 저장 계층 접근 자체가 **이름을 요구한다**:

```rust
pub fn with_store<T>(&self, op: StoreOp, f: impl FnOnce(&mut Store) -> T) -> Result<T, UiMessage>
```

무엇을 하려던 것인지 말하지 않고는 저장 계층에 닿을 수 없다. 종전의 `Result<T, String>`은
호출부마다 산문을 지어 붙이게 했고, 그 산문이 화면 쪽 틀과 겹쳐 문장이 두 번 씌워졌다.

#### 산문으로 되돌리는 자리는 **보여야** 한다

화면에 봉투로 나가지 않는 자리도 있다(허용 목록 저장 같은 쓰기, 실행 경로의 태스크 생성).
그 자리들은 `with_store_prose(what, f)`를 쓴다 — **`op`를 받지 않고 설명 문자열을 받는다.**

코드를 만들어 두고 산문으로 흘리지 않는 이유가 여기 있다. 카탈로그에 있지만 실제로는 도착하지
않는 코드가 생기면 6.4절의 양방향 검사가 **"번역된다"는 뜻을 잃는다** — 초록색은 그대로인데
화면에는 여전히 한국어 산문이 뜬다. 검사가 말하는 것과 사용자가 보는 것이 갈라지면 그 검사는
있으나 마나다.

그리고 함수를 나눠 두면 **고르는 것이 눈에 보인다.** 봉투를 빠뜨리는 것은 보이지 않지만,
`with_store_prose`를 쓰는 것은 diff에 남는다.

#### 컴파일되지 않는 크레이트를 얕게라도 본다

위 보장은 타입이 주지만, **그 코드가 사는 껍데기 크레이트는 이 개발 환경에서 컴파일되지
않는다**(process-architecture.md 10.3절). 여기서 도는 `verify`는 그 보장에 대해 아무것도
말해주지 않는다. 그래서 소스를 훑어 "저장 계층 접근에 전부 `StoreOp`가 붙어 있는가"를 한 겹
얕게 확인한다(`test/storeAccess.test.ts`). 타입 검사의 대체물이 아니라, Windows에서
컴파일할 때까지 회귀를 늦게 발견하지 않기 위한 그물이다.

### 6.6 남은 것

- ~~나머지 저장 계층 명령의 `Ok(envelope)` 전환~~ → 6.5절에서 끝냈다. **화면이 읽는 저장
  계층 경로는 전부 봉투로 나간다.** 남은 것은 봉투가 아니라 **화면에 봉투로 나가지 않는
  자리**(쓰기·실행 경로)이고, 그건 전환 대상이 아니라 `with_store_prose`로 드러내는 대상이다.
  전환 도중 실제로 결함 넷을 꺼냈다(`Error: ` 접두, 틀 이중 적용, `store-ready`의 키 갈라짐,
  export 본문에 봉투 키가 섞일 뻔한 것).
- **화면 안의 문자열**(버튼·제목)은 아직 리터럴이다. 위 전환이 끝나기 전에는 옮길 이유가 없다 —
  옮겨도 반쪽이고, 그 사이 UI는 계속 바뀐다.
- **미번역 표시의 시각 처리**는 두 번째 언어가 생길 때 정한다. 지금은 언어가 하나뿐이라 원문과
  번역이 같은 문장이므로, `data-untranslated`만 남기고 눈에 보이는 처리는 하지 않는다.
- 분리를 **시작할 신호**: 위 전환이 끝나고, 한국어가 아닌 사용자가 실제로 생겼을 때. 앞의
  조건 없이 뒤의 신호만 오면 반쪽 번역을 배포하게 된다.

## 3.16 M3 기능의 UI 배선 — 배선할 수 있는 것과 먼저 풀어야 하는 것

M3에서 다섯 기능의 코어를 만들었고(Autopilot·Hooks·Skills·세션 메모리·PR), 다섯 다 "UI 미배선"으로
남아 있었다. 배선해 보니 **둘로 갈렸다.**

### 3.16.1 지금 배선한 것 — 끝난 작업에 대한 질문

`BlockedPanel`(24.8절)과 `PullRequestPanel`(28절)은 **태스크가 끝난 뒤에** 묻는 것이고, 둘 다
기존 활성 호스트로 답할 수 있다. 그래서 Tauri 명령 두 개(`task_blocked`, `open_pull_request`)와
패널 두 개로 끝났다.

`open_pull_request`는 **별도 스레드로 보낸다.** push가 승인 모달을 띄우고 그 답을 기다리는데,
같은 스레드면 `respond_approval`이 처리되지 못해 교착된다 — `start_task`가 이미 겪은 것과 같다.

판정은 화면이 아니라 `src/lib`에 둔다(`blockedAdvice.ts`, `prOutcome.ts`). 그 둘이 막는 거짓말이
각각 하나씩 있다:

- **`humanOnly` 정지를 "이 스위치를 켜세요"로 뭉개지 않는다.** 열리는 플래그가 있으면 그것만
  보여주고 싶어지는데, 그러면 사용자는 켜고 다시 돌렸다가 같은 자리에서 또 멈춘다.
- **"PR을 만들었습니다"라고 쓰지 않는다.** 우리는 만들지 않았다(28.1절). 그렇게 쓰면 사용자는
  GitHub에 가서 없는 PR을 찾는다.

### 3.16.2 ~~먼저 풀어야 하는 것~~ → 풀었다 — **정책의 수명**

Autopilot·Skills·검증 명령 자동 승인은 전부 **태스크마다 다른 `TaskPolicy`** 를 필요로 한다.
그런데 UI 경로에서 Rust `TaskPolicy`는 **워크스페이스를 열 때 고정되고 태스크마다 바뀌지
않는다.** 그건 실수가 아니라 결정이었다 — `session.rs`에 그 이유가 적혀 있다: *"UI에서 켠
스위치가 신뢰 경계의 위험 등급을 낮출 수 있으면 그건 게이트가 아니다."*

그래서 이 셋을 배선하려면 그 결정을 다시 봐야 하고, 다시 볼 때 지켜야 할 규칙은 이렇다:

| 필드 | 방향 | 태스크별로 받아도 되는가 |
|---|---|---|
| `allowedTools`(Skills) | **좁힌다** | 된다 — 어떤 도구도 새로 허용되지 않는다(26.3절) |
| `unattended`(Autopilot) | 넓히지도 좁히지도 않는다 | 된다 — 승인을 *묻지 않고 멈춘다*(24.2절) |
| `autoApproveVerification` | **넓힌다** | 조건부 — 대상 집합을 **Rust가 매니페스트에서 유도**하고 시작 시점에 고정하기 때문에만 성립한다(24.5절) |

**넓히는 방향은 이 셋이 마지막이어야 한다.** 다음에 누가 "UI 토글로 승인 등급을 낮추자"고 할 때
근거로 쓸 수 있는 표가 아니다 — 위 셋이 통과하는 이유는 각각 다르고, 그 이유가 없는 필드는
통과하지 못한다.

Hooks는 또 다른 이유로 남았다: 등록이 **워크스페이스 수명**의 설정이라(태스크가 아니라) 설정
화면이 필요하고, 그건 MCP 서버 등록(23.10절)과 같은 자리에서 함께 만들어야 한다.

#### 3.16.2.1 갈아끼우지 않고 **태스크마다 하나씩 만든다**

정책을 가변 필드로 바꿔 태스크마다 갈아끼우는 것이 가장 짧은 길인데, 그러면 **진행 중인
태스크의 게이트가 도중에 바뀔 수 있다.** 승인 화면이 보여준 근거와 실행 시점의 근거가
달라지고, 그건 이 게이트가 파는 성질을 직접 깨뜨린다.

그래서 `TaskProfile`을 태스크마다 하나씩 만든다(정책 + 그 정책으로 만든 게이트 + 검증 명령
고정). 등록은 **한 번뿐**이고(`begin_task`), 두 번째 등록은 오류다 — 그 오류가 "정책은 태스크
수명 동안 불변"이라는 문장의 실체다.

등록되지 않은 태스크는 **워크스페이스 기본값**으로 판정된다. 없는 것을 오류로 만들지 않는
이유는 되돌리기·PR·복구처럼 **태스크가 끝난 뒤에 도는 경로**가 있기 때문이다. 그 동작들은
사용자의 것이지 그 태스크의 실행이 아니다 — 그 태스크가 스킬로 도구를 좁혔더라도 그 제한은
"모델이 무엇을 요청할 수 있는가"였다.

#### 3.16.2.2 곁가지로 문서와 코드가 갈라져 있었다

24.5절은 검증 명령 자동 승인의 대상을 **태스크 시작 시점**에 고정한다고 적었는데, 고정은
`TaskHost`를 만들 때 일어나고 있었다. 헤드리스 호스트는 태스크마다 새로 만들어지므로 같은
말이었지만, **호스트가 워크스페이스 수명을 갖는 UI 경로에서는 "워크스페이스를 열 때"였다.**

프로필이 태스크마다 만들어지면서 문서대로 동작하게 됐다. 이건 이 리팩터의 부산물이 아니라
**같은 결함의 다른 얼굴**이다 — 둘 다 "정책과 그로부터 유도된 것의 수명이 태스크가 아니었다"는
하나의 사실에서 나왔다.

#### 3.16.2.3 무인 여부도 정책이 정한다

종전에는 승인 게이트웨이를 `UnattendedStop`으로 바꿔 끼우는 것으로 무인 실행을 표현했다.
게이트웨이는 호스트 수명이라 **태스크마다 다른 무인 여부**를 표현할 수 없다.

이제 `execute_tool`이 `policy.unattended`를 보고 승인 왕복 자체를 건너뛴다. 게이트웨이 쪽
`UnattendedStop`은 지우지 않았다 — 이 짧은 길이 어떤 이유로 우회되더라도 그쪽이 **같은 답**을
내야 하기 때문이다. 두 규칙이 아니라 같은 답의 두 겹이다.

#### 3.16.2.4 다시 실행은 정책을 물려받지 않는다

"다시 실행"은 새 태스크다(16.6절). 무인 실행이었다고 이번에도 무인일 이유가 없고, 스킬을
골랐다고 이번에도 그것을 고를지는 사용자가 정할 일이다. 물려받게 하려면 화면이 **무엇을
물려받는지 보여준 뒤**여야 한다.

#### 3.16.2.5 화면이 미리 말하는 것

무인 실행만 켜고 검증 명령 자동 승인을 켜지 않으면 그 태스크는 **검증에서 멈춘다**(24.4절).
그건 정상 동작이지만, 멈춘 **뒤에** 알면 도구의 오작동으로 읽힌다. 그래서 토글을 두 개로
나누고, 한쪽만 켠 상태에서 그 사실을 미리 말한다.

### 3.16.3 배선 누락은 컴파일이 잡지 않는다

`#[tauri::command]`를 붙이고 `generate_handler![...]`에 넣지 않으면 **컴파일은 통과한다** —
붙이기만 한 함수는 "안 쓰는 함수"일 뿐이다. 화면이 그 명령을 부르면 런타임에 없고, 그건 앱을
띄워야만 보인다. 그런데 이 저장소의 개발 환경은 Linux라 tauri 껍데기 크레이트가 **컴파일되지도
않는다**(GUI 시스템 라이브러리 부재) — 띄워 보는 것으로 대신할 수도 없다.

그래서 `apps/desktop/test/commandWiring.test.ts`가 선언과 등록을 **양쪽 소스에서 유도해** 대조한다.
`win_job.rs`와 같은 처지의 코드에 대해 할 수 있는 검사를 하는 것이고, **이 검사가 통과했다고
그 명령이 동작한다는 뜻은 아니다.**
